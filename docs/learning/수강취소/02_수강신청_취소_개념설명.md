## 1. 요약

- **수강신청**은 `POST /api/v1/enrollments`, **수강취소**는 `DELETE /api/v1/enrollments/<과목>` 요청 한 번으로 처리된다.
- 수강 정보는 `enrollments` 테이블의 한 줄(누가 · 어떤 과목)이다. 취소하면 이 줄과 거기에 딸린 출석 세션을 지운다.
- **최종 규칙**(01 문서 작성 이후 바뀜):
  - 수강취소: 수강 정보만 지운다.
  - **다시 수강신청: 그 과목의 진도·레벨 기록과 받지 않은 과목 보상을 지우고 0%에서 시작**한다.
  - **이미 받은 보상(포인트·경험치 장부)은 유지**한다. 그래서 취소·재신청을 반복해도 같은 보상을 또 받을 수 없다.
- 취소 확인창 문구도 이 규칙에 맞게 바꿨다: "다시 수강신청하면 진도는 처음(0%)부터 시작됩니다. 이미 받은 보상은 유지됩니다."
- 수강 관리는 실습 페이지가 아니므로 **CSRF 보호 · 본인 데이터만 처리** 같은 표준 규칙을 지킨다.

## 2. 개념 설명 (비유)

### 2-1. 전체 그림: 헬스장 회원권

```
 [수강신청]  POST /enrollments {course_slug}
      │
      ├─ 이미 수강 중? ──────────── 409 (화면은 "수강 중"으로 맞춤)
      ├─ 예전 기록 정리 ─────────── task_progress(진도·레벨) 삭제
      │                            받지 않은 과목 교환권 삭제
      │                            ※ 받은 보상 장부는 유지
      └─ enrollments 에 한 줄 추가 ─ 201

 [수강취소]  DELETE /enrollments/<course_slug>
      │
      ├─ 수강 중이 아님? ────────── 404 (화면은 "미수강"으로 맞춤)
      ├─ 출석 세션(자식) 먼저 삭제
      └─ 수강 정보(부모) 삭제 ────── 204
```

- **회원권(수강 정보)** 을 해지하면 출입 명단에서 이름이 빠지고, 명단에 붙어 있던 출입 기록(출석 세션)도 정리된다.
- **다시 등록**하면 새 회원 카드를 받아 운동 기록표(진도)를 처음부터 쓴다.
- 하지만 예전에 받은 **사은품(받은 보상)** 은 다시 주지 않는다. 해지·재등록을 반복해 사은품을 계속 받는 것을 막기 위해서다.

### 2-2. 왜 "취소할 때"가 아니라 "다시 신청할 때" 초기화하나

- 취소만 하고 다시 신청하지 않는 학생은 진도를 지울 필요가 없다(관리자가 이전 기록을 볼 수 있음).
- 다시 신청하는 순간 "새로 시작"이 분명해지므로, 그때 예전 기록을 정리한다.
- 결과적으로 학생 입장에서는 **"수강신청 = 0%에서 시작"** 하나만 기억하면 된다.

## 3. 용어 설명

| 용어 | 쉬운 뜻 |
|---|---|
| 수강(Enrollment) | "누가 어떤 과목을 듣는 중인가" 기록. `enrollments` 테이블의 한 줄 |
| AttendanceSession | 수강에 딸린 출석 세션 기록. `enrollment_id` 로 수강을 가리킨다 |
| 부모 행 / 자식 행 | 다른 줄이 가리키는 줄(부모) / 다른 줄을 가리키는 줄(자식) |
| 외래키(FK) | 자식이 부모를 가리키는 연결. 부모를 먼저 지우면 DB가 거부한다 |
| course_slug | 과목을 주소에서 구분하는 영문 이름 (예: `csrf`, `xss-dom`) |
| REST | "주소는 대상(자원), 메서드는 동작"으로 API 를 설계하는 방식 |
| HTTP 메서드 | 요청의 동작 종류. `GET`(조회) · `POST`(생성) · `DELETE`(삭제) 등 |
| 201 Created | 새로 만들기 성공 |
| 204 No Content | 삭제 성공, 돌려줄 내용 없음 |
| 401 | 로그인 필요 |
| 404 Not Found | 대상 없음 (없는 과목 / 이미 수강 중이 아님) |
| 409 Conflict | 이미 그 상태라 충돌 (이미 수강 중) |
| 동기화 | 화면의 상태를 서버의 실제 상태와 맞추는 것 |
| CSRF 토큰 | 우리 화면에서만 발급한 번호표. 다른 사이트가 몰래 보낸 취소 요청을 막는다 |
| `encodeURIComponent` | 주소에 넣을 문자열의 특수문자를 안전하게 바꾸는 함수 |
| `window.confirm` | "확인/취소" 버튼이 있는 브라우저 기본 확인창 |

## 4. 구조와 코드

### 4-1. REST 로 본 수강 API

| 동작 | 메서드 · 주소 | 성공 응답 | 의미 |
|---|---|---|---|
| 내 수강 목록 | `GET /api/v1/enrollments` | 200 | 수강 중인 과목 slug 목록 |
| 수강신청 | `POST /api/v1/enrollments` + `{course_slug}` | 201 | 수강 정보 "생성" |
| 수강취소 | `DELETE /api/v1/enrollments/<course_slug>` | 204 | 수강 정보 "삭제" |

- 같은 주소(`/enrollments`)에 **메서드만 바꿔** 조회·생성·삭제를 표현한다. 주소만 봐도 무엇을 다루는지 알 수 있다.

### 4-2. 수강신청 (초기화 포함)

```python
# backend/app/enrollments.py (요약)
if Enrollment.query.filter_by(user_id=user.id, course_id=course.id).first():
    return jsonify(message="이미 수강 중인 과목입니다."), 409

_reset_course_progress(user.id, course)          # ① 예전 진도·레벨·미수령 과목 보상 정리
db.session.add(Enrollment(user_id=user.id, course_id=course.id))
db.session.commit()                              # ② 수강 정보 생성
return jsonify(course_slug=course.slug), 201

def _reset_course_progress(user_id, course):
    TaskProgress.query.filter_by(user_id=user_id, course_id=course.id).delete()
    Reward.query.filter(Reward.user_id == user_id, Reward.claimed_at.is_(None), <이 과목 ref>).delete()
```

| 데이터 | 다시 수강신청 시 | 이유 |
|---|---|---|
| 미션 완료 · 레벨 통과 · 확인 문제 통과 기록 | 삭제 | 0%에서 새로 시작 |
| 받지 않은 과목 교환권 | 삭제 | 새 수강에서 다시 조건을 채워야 함 |
| 받은 보상(포인트·경험치 장부) · 레벨 · 출석 | 유지 | 반복 신청으로 같은 보상을 또 받는 것 방지 |

- ① 과 ② 가 같은 트랜잭션(한 번의 `commit`)이라, 중간에 실패하면 둘 다 취소된다.

### 4-3. 수강취소 (자식 먼저)

```python
# backend/app/enrollments.py
enrollment = Enrollment.query.filter_by(user_id=user.id, course_id=course.id).first()
if not enrollment:
    return jsonify(message="수강 중인 과목이 아닙니다."), 404

AttendanceSession.query.filter_by(enrollment_id=enrollment.id).delete()   # ① 자식
db.session.delete(enrollment)                                              # ② 부모
db.session.commit()
return "", 204
```

```
enrollments (부모) ◀── attendance_sessions (자식, enrollment_id 로 연결)
```

| 줄 | 의미 | 없으면 생기는 일 |
|---|---|---|
| `user_id=user.id` 조건 | 로그인한 본인의 수강만 찾음 | 다른 사람의 수강을 지울 수 있음 |
| ① 자식 먼저 삭제 | 출석 세션을 먼저 지움 | 부모를 먼저 지우면 외래키 오류로 취소 실패 |
| `204` | 성공, 본문 없음 | - |

### 4-4. 화면의 응답 처리 (동기화)

```javascript
// frontend/src/stores/enroll.js (요약)
async function enroll(id) {
  try { await client.post("/enrollments", { course_slug: id }); item.enrolled = true; }
  catch (e) { if (e.response?.status === 409) { item.enrolled = true; return; } throw e; }
}
async function cancel(id) {
  try { await client.delete(`/enrollments/${encodeURIComponent(id)}`); item.enrolled = false; }
  catch (e) { if (e.response?.status === 404) { item.enrolled = false; return; } throw e; }
}
```

| 응답 | 상황 | 화면 |
|---|---|---|
| 201 / 204 | 정상 | 버튼 즉시 변경, "수강 중 N/8" 갱신 |
| 409 (신청) | 다른 탭에서 이미 신청함 | 오류 대신 "수강 중"으로 맞춤 |
| 404 (취소) | 다른 탭에서 이미 취소함 | 오류 대신 "미수강"으로 맞춤 |
| 400 (CSRF) | 토큰 만료 | 토큰 재발급 후 1회 자동 재시도 |
| 그 외 | 서버 오류 | "수강취소에 실패했습니다." 등 |

- 409·404 를 오류로 띄우지 않는 이유: 결과적으로 사용자가 원한 상태(수강 중 / 미수강)가 이미 이루어져 있기 때문이다.
- 처리 중에는 버튼을 비활성화해 **중복 클릭**을 막고, 취소 전 **확인창**으로 실수 클릭을 막는다.

## 5. 동작 흐름 예시

```
1. Command Injection 수강 중, 진도 67% (하·중·상 통과, 퀴즈 미완)
2. [수강취소] → 확인창 "다시 수강신청하면 진도는 처음(0%)부터…" → 확인
   → DELETE → 출석 세션 · 수강 정보 삭제 → 204 → 버튼 "수강"
3. [수강] → POST → 예전 진도·레벨 기록, 받지 않은 교환권 삭제 → 수강 생성 → 201
   → 진도 0%, 실습은 하 레벨부터
4. 예전에 받은 레벨 보상·미션 보상은 장부에 남아 있음
   → 다시 하 레벨을 통과해도 "이미 이 레벨의 클리어 보상을 받았습니다."
```

## 6. 주의점과 한계

- **01 문서의 "진도는 보존되어 재수강 시 이어서 진행"은 지금 규칙과 다르다.** 이후 "수강신청 = 0%부터"로 바뀌었고, 확인창 문구도 함께 고쳤다.
- **재수강하면 이미 받은 보상은 다시 받지 못한다.** 학생이 "보상이 안 나온다"고 느낄 수 있으므로 화면 문구("이미 받은 보상")로 안내한다.
- 취소만 하고 다시 신청하지 않으면 **진도 기록은 남아 있다**(다음 수강신청 때 정리됨). 관리자 화면에서는 수강 중인 과목만 진도에 반영된다.
- 출석(계정 단위)과 레벨·포인트는 과목과 무관하므로 수강취소·재신청의 영향을 받지 않는다.

## 7. 핵심 정리

- 수강신청은 `POST`(201), 수강취소는 `DELETE`(204). 같은 주소에 메서드로 동작을 구분하는 **REST** 방식이다.
- 취소는 **출석 세션(자식) → 수강 정보(부모)** 순서로 지워 외래키 오류를 피한다.
- 다시 수강신청하면 그 과목은 **0%부터**, 이미 받은 보상은 **유지**되어 중복 지급이 없다.
- 화면은 409·404 를 오류가 아닌 **상태 동기화**로 처리하고, 확인창·버튼 비활성화로 실수를 막는다.
- 발표용 한 문장: **"수강 관리는 REST 방식의 생성·삭제 요청으로 처리하고, 다시 신청하면 진도는 처음부터 시작하되 이미 받은 보상은 남겨 중복 지급을 막았다."**
