# 01. 보안 응답 헤더(CSP 등) · 404 페이지

> 대상: 웹 보안을 처음 배우는 입문자
> 목표: 팀 ZAP 진단에서 지적된 "CSP 미설정 · 클릭재킹 방어 헤더 누락"을 Nginx 에서 고치고, 의도적으로 취약한 XSS 실습은 그대로 동작하게 만드는 방법을 이해한다. 임시 404 화면을 정식 화면으로 바꾼다.
> 작성: 2026-10-09 · 오현명
> 📘 개념 설명(용어·헤더 의미·최종 구조)은 `02_보안헤더_개념설명.md` 참고.

## 1. 요약

- Nginx 가 모든 응답에 **보안 헤더**를 붙인다: `Content-Security-Policy` · `X-Frame-Options` · `X-Content-Type-Options` · `Referrer-Policy` · `Permissions-Policy`, 버전 표시(`server_tokens`) 숨김.
- 경로마다 정책을 다르게 했다: **앱 화면(엄격)** / **API(가장 엄격)** / **XSS 실습 프레임(인라인 스크립트 허용, 대신 외부 통신 전부 차단)**.
- 문제: XSS 실습은 `<iframe srcdoc>` 를 썼는데, srcdoc 프레임은 **부모 페이지의 CSP 를 그대로 물려받아** 엄격한 CSP 를 켜면 실습이 동작하지 않는다.
- 해결: 실습 HTML 을 그리는 전용 페이지 **`/practice-frame.html`** 을 만들고, 앱이 그 프레임에 `postMessage` 로 HTML 을 보낸다. 이 경로에만 실습용 CSP 를 붙인다.
- **404 페이지**를 정식 화면으로 교체: 안내 문구 · 요청 주소(안전하게 텍스트로) · 대시보드/이전 페이지 버튼 · 자주 찾는 메뉴.
- 백엔드 · DB 변경 없음.

## 2. 개념 설명 (비유)

**건물 출입 규칙**과 같다.

- CSP 는 건물 입구에 붙인 **"반입 허용 목록"** 이다. "우리 회사에서 만든 물건(스크립트)만 들여올 수 있음". 누가 몰래 쪽지(주입된 스크립트)를 끼워 넣어도 목록에 없으니 실행되지 않는다.
- X-Frame-Options · frame-ancestors 는 **"우리 건물 사진을 남의 전단지에 붙이지 마시오"**. 다른 사이트가 우리 화면을 투명하게 덮어 클릭을 훔치는 것(클릭재킹)을 막는다.
- XSS 실습실은 **방폭 실험실**이다. 실험(스크립트 실행)은 허용하지만 문은 밖에서 잠겨 있다(sandbox), 전화선도 끊겨 있다(connect-src 'none'). 실험실 안의 규칙은 건물 전체 규칙과 다르게 따로 붙인다(`/practice-frame.html` 전용 CSP).
- srcdoc 은 **건물 안에 칸막이만 친 실험 공간**이라 건물 규칙("우리 물건만")이 그대로 적용돼 실험을 못 한다. 그래서 별도 실험실(별도 페이지)을 만들었다.

## 3. 용어 설명

| 용어 | 뜻 |
|---|---|
| CSP (Content-Security-Policy) | 이 페이지가 어디서 스크립트·스타일·이미지 등을 불러와도 되는지 브라우저에 알려주는 헤더 |
| 'self' | 같은 출처(우리 사이트)만 허용 |
| 'unsafe-inline' | HTML 안에 직접 쓴 `<script>` · `onerror=` 같은 인라인 코드를 허용. XSS 방어력이 크게 떨어지므로 앱 화면 스크립트에는 쓰지 않는다 |
| frame-ancestors | 누가 이 페이지를 iframe 으로 감쌀 수 있는지. X-Frame-Options 의 최신 버전 |
| X-Frame-Options | 구형 브라우저용 클릭재킹 방어 헤더. `DENY`(전부 금지) / `SAMEORIGIN`(우리 사이트만) |
| X-Content-Type-Options: nosniff | 브라우저가 파일 종류를 추측하지 못하게 함 (텍스트를 스크립트로 오해해 실행하는 것 방지) |
| Referrer-Policy | 다른 사이트로 이동할 때 주소 정보를 얼마나 넘길지 |
| Permissions-Policy | 카메라 · 마이크 · 위치 같은 브라우저 기능 사용 허용 여부 |
| srcdoc | iframe 내용을 주소 대신 HTML 문자열로 바로 넣는 속성. **부모의 CSP 를 상속** |
| sandbox="allow-scripts" | 스크립트는 허용하되 출처를 "없음(opaque)"으로 만들어 쿠키 · 세션 · 부모 화면 접근을 막는 iframe 옵션 |
| postMessage | 서로 다른 출처의 창끼리 메시지를 주고받는 브라우저 기능 |

## 4. 화면 & 동작

### 404 화면

```
┌──────────────────────────────────────────┐
│                  [S]                      │
│                  404                      │
│          페이지를 찾을 수 없습니다          │
│ 주소가 잘못 입력되었거나, 페이지가 이동 …   │
│ ┌──────────── 요청한 주소 ─────────────┐  │
│ │ /no-such-page                        │  │
│ └──────────────────────────────────────┘  │
│  [⌂ 학습 대시보드로 이동] [← 이전 페이지]   │
│  ────────────────────────────────────     │
│   수강신청  학습 진도  자료실  마이페이지   │
└──────────────────────────────────────────┘
```

- 로그인 상태에서 없는 주소로 가면 헤더 · 푸터와 함께 이 화면이 보인다. 로그인 전이면 기존 라우터 규칙대로 로그인 화면으로 이동한다.
- 요청 주소는 `{{ }}` 텍스트 보간으로만 출력해 주소에 `<img onerror=…>` 를 넣어도 실행되지 않는다(테스트로 확인). 80자가 넘으면 줄여서 표시.
- [이전 페이지] 는 이전 기록이 없으면(주소를 직접 입력해 들어온 경우) 대시보드로 보낸다.
- 색은 모두 `var(--sq-*)` 토큰.

### XSS 실습 미리보기 (겉보기 변화 없음)

학생 입장에서는 이전과 똑같다. 내부 동작만 바뀌었다.

```
[변경 전]  XssPractice ──srcdoc=HTML──▶ <iframe sandbox>        ← 앱 CSP 상속 → 엄격 CSP 면 실습 불가

[변경 후]  XssPractice ─▶ PracticeFrame ─src=/practice-frame.html─▶ <iframe sandbox="allow-scripts">
                              ▲   ① 프레임: "sq-frame-ready" ──────────┘
                              └── ② 앱: postMessage({type:"sq-render", html})
                                  ③ 프레임: document.write(html)  (실습용 CSP 적용)
                                  ④ 감시 스크립트: alert 호출 시 flag postMessage → 기존 판정 그대로
```

### 관련 파일

| 파일 | 변경 | 역할 |
|---|---|---|
| `nginx/nginx.conf` | 수정 | 경로별 보안 헤더, `server_tokens off`, 실습 프레임 경로 추가 |
| `frontend/public/practice-frame.html` | 신규 | 실습 HTML 을 그리는 빈 페이지 |
| `frontend/public/practice-frame.js` | 신규 | 부모가 보낸 HTML 한 건만 받아 문서를 교체하는 로더 |
| `frontend/src/components/practice/PracticeFrame.vue` | 신규 | iframe + 준비 신호 · HTML 전송, HTML 바뀌면 프레임 새로 생성 |
| `frontend/src/components/practice/XssPractice.vue` | 수정 | srcdoc iframe → `PracticeFrame` |
| `frontend/src/components/practice/StoredXssPractice.vue` | 수정 | 위와 동일 |
| `frontend/src/views/NotFoundView.vue` | 수정 | 임시 화면 → 정식 404 화면 |
| `README.md` | 수정 | 보안 설계 표에 보안 헤더 행 추가 |

## 5. 경로별 헤더 정책

| 경로 | CSP | X-Frame-Options | 그 외 |
|---|---|---|---|
| `/` (앱 화면) | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; font-src 'self' data: https://cdn.jsdelivr.net; img-src 'self' data: blob:; connect-src 'self'; frame-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'` | SAMEORIGIN | nosniff · Referrer-Policy · Permissions-Policy |
| `/api/` `/pdf/` `/practice/` | `default-src 'none'; frame-ancestors 'none'` | DENY | nosniff (+ API 는 Referrer-Policy) |
| `/practice-frame.html` `.js` | `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src 'none'; form-action 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'self'` | SAMEORIGIN | nosniff · Referrer-Policy: no-referrer |

값을 이렇게 정한 이유:

| 항목 | 이유 |
|---|---|
| 앱 `script-src 'self'` | 앱 스크립트는 모두 파일(Vite 번들)이라 인라인 허용이 필요 없다. 주입된 `<script>` · `onerror=` 는 실행되지 않는다 |
| 앱 `style-src 'unsafe-inline'` | Vite 개발 서버와 Vue 가 `<style>` 태그를 직접 넣기 때문에 필요. 스타일 인라인은 스크립트보다 위험이 훨씬 작다 |
| `cdn.jsdelivr.net` | Pretendard 폰트 CSS · 폰트 파일 |
| `img-src data: blob:` | Bootstrap 이 아이콘을 data: SVG 로 쓰고, CSV 내보내기가 blob: 을 쓴다 |
| `connect-src 'self'` | API 호출과 Vite 개발 서버 HMR(WebSocket, 같은 주소)만 허용 |
| 실습 `'unsafe-inline'` | 실습 자체가 "인라인 스크립트 주입"이라 반드시 필요 (의도적 취약) |
| 실습 `connect-src 'none'` 등 | 실습 페이지에서 스크립트가 돌아도 **외부로 데이터를 보내거나, 폼을 전송하거나, 다른 페이지를 불러올 수 없다** |
| 실습 `img-src data:` | `<img src=x onerror=…>` 의 `x` 요청이 서버로 가지 않게 막는다. 막혀도 onerror 는 그대로 실행돼 실습에는 지장 없다 |
| `always` | 404 · 500 같은 오류 응답에도 헤더를 붙임 |

> Nginx 주의: `location` 안에 `add_header` 를 하나라도 쓰면 바깥(`server`)의 `add_header` 는 상속되지 않는다. 그래서 위치마다 필요한 헤더를 모두 적었다.

## 6. 테스트 결과

클라우드 테스트 환경에서 **실제 `nginx.conf`(호스트 이름만 127.0.0.1 로 치환) + Vite 개발 서버 + 실제 XSS 실습 빌더를 쓰는 가짜 API** 를 띄우고 Chromium(Playwright)으로 확인했다.

### 6-1. 헤더

| 요청 | 결과 |
|---|---|
| `nginx -t` | syntax is ok / test is successful |
| 앱 화면 | 위 앱 CSP · SAMEORIGIN · nosniff 응답 |
| `/practice-frame.html` | 실습 CSP · SAMEORIGIN 응답 |
| `/api/v1/auth/me` (401 응답) | `default-src 'none'` · DENY (`always` 덕분에 오류 응답에도 붙음) |

### 6-2. XSS 실습 12개 경우 (모두 PASS)

| 과목 | 하 | 중 | 상 | 안전 |
|---|---|---|---|---|
| Reflected | `<script>alert(1)</script>` 성공 | `<SCRIPT>…` 성공 | `<img src=x onerror=alert(1)>` 성공 | 실행 안 됨 ✅ |
| DOM | `<script>…` 성공 | `<img … onerror>` 성공 | `<details open ontoggle=alert(1)>` 성공 | 실행 안 됨 ✅ |
| Stored | Message `<script>…` 성공 | Name `<img … onerror>` 성공 | Name `<img … onerror>` 성공 | 실행 안 됨 ✅ |

### 6-3. 격리 · 차단 확인

| 확인 | 결과 |
|---|---|
| 같은 화면에서 두 번째 제출(프레임 새로 생성) | 정상 판정 |
| 실습 프레임에서 `fetch('https://example.com/steal')` | **차단** ("Refused to connect … connect-src") |
| 실습 프레임에서 `document.cookie` 읽기 | **SecurityError** (sandbox 로 출처 없음) |
| 앱 화면에 인라인 `<script>` 삽입 | **실행 안 됨** (앱 CSP) |

### 6-4. 앱 화면 CSP 위반 여부

로그인 · 회원가입 · 아이디/비밀번호 찾기 · 대시보드 · 마이페이지 · 자료실 · 수강신청 · 학습 진도 · 404 를 열어 **CSP 위반 · 스크립트 오류 0건**. Vite HMR 연결(`[vite] connected`)도 정상.

### 6-5. 404

- `/no-such-page/<img src=x onerror=alert(1)>` → 404 화면, 주소는 글자로만 표시, alert 없음.
- 로컬 프론트엔드 `vite build` 성공 (`practice-frame.html` · `.js` 가 결과물에 포함).

### 직접 확인하는 방법

```bash
docker compose up -d --build        # nginx.conf 변경 반영 (또는 docker compose restart nginx)
curl -sI http://localhost:8090/ | grep -i -E "content-security|x-frame|nosniff"
curl -sI http://localhost:8090/practice-frame.html | grep -i content-security
# 브라우저: XSS 과목 실습에서 힌트 예시 입력 → 성공 판정 확인
# 브라우저: http://localhost:8090/아무주소 → 404 화면
```

ZAP 을 다시 돌리면 "CSP Header Not Set" · "Missing Anti-clickjacking Header" 경고가 사라져야 한다(아직 재진단은 안 함).

## 7. 남은 한계 · 다음 작업

- **`style-src 'unsafe-inline'`** 이 남아 있다. 개발 서버(Vite) 구조상 필요하다. 운영용 정적 빌드로 바꾸면 해시/nonce 방식으로 줄일 수 있다.
- **HTTPS · HSTS 없음**: 지금은 HTTP(로컬 시연). HSTS 헤더는 HTTPS 를 켤 때 함께 추가해야 한다(점검표 #7).
- `/pdf/` · `/practice/` 경로는 점검표 #12 대로 정리(삭제) 예정이라 헤더만 붙여 두었다.
- 팀 ZAP 재진단으로 결과 확인.
