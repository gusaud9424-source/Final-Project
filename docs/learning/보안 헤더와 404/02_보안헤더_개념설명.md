# 02. 보안 응답 헤더 — 개념 설명

> 대상: 웹 보안을 처음 배우는 입문자 (발표에서 그대로 설명할 수 있도록)
> 목표: CSP · 클릭재킹 방어 헤더가 무엇을 막는지, 그리고 "일부러 취약한 실습"과 "안전한 서비스"를 한 사이트 안에서 어떻게 함께 운영하는지 이해한다.

## 1. 요약

- 보안 헤더는 **서버가 브라우저에게 주는 안전 수칙**이다. 코드 한 줄 안 고쳐도 브라우저가 대신 막아 준다.
- **CSP** 는 XSS 의 **마지막 방어선**이다. 출력 인코딩(1차 방어)이 뚫려도 주입된 스크립트가 실행되지 않게 한다.
- **X-Frame-Options / frame-ancestors** 는 **클릭재킹**을 막는다.
- SecuQuest 는 **경로별로 다른 정책**을 쓴다. 앱은 엄격하게, XSS 실습 프레임은 실행은 허용하되 밖으로 못 나가게.

## 2. 전체 구조

```
                         Nginx (헤더를 붙이는 곳)
 브라우저 ──요청──▶ ┌───────────────────────────────────────────────┐
                    │ /api/ /pdf/ /practice/  → CSP default-src 'none' │ ← JSON 만, 아무것도 실행 X
                    │ /practice-frame.*       → 실습 CSP (아래)        │ ← 실행 O, 외부 통신 X
                    │ /  (앱 화면)            → 앱 CSP (엄격)          │ ← 우리 파일만 실행
                    └───────────────────────────────────────────────┘

 앱 화면 (CSP: script-src 'self')
 ┌───────────────────────────────────────────────┐
 │ XssPractice                                    │
 │  └ PracticeFrame                               │
 │     <iframe sandbox="allow-scripts"            │
 │             src="/practice-frame.html">        │
 │     ┌───────────────────────────────────┐      │
 │     │ 실습 CSP: 'unsafe-inline' 허용      │      │
 │     │ connect-src 'none' · form 'none'   │      │
 │     │ 출처 없음(sandbox) → 쿠키 접근 X    │      │
 │     └───────────────────────────────────┘      │
 └───────────────────────────────────────────────┘
```

## 3. 각 헤더가 막는 공격

| 헤더 | 막는 공격 | 없으면 생기는 일 |
|---|---|---|
| `Content-Security-Policy` | XSS, 외부 악성 스크립트 로딩, 데이터 유출 | 게시글 · 주소에 `<script>` 가 끼어들면 그대로 실행 → 세션 탈취 · 화면 변조 |
| `frame-ancestors` / `X-Frame-Options` | 클릭재킹 | 악성 사이트가 우리 화면을 투명 iframe 으로 덮고 "경품 받기" 버튼 아래 [회원 삭제] 를 깔아 클릭 유도 |
| `X-Content-Type-Options: nosniff` | MIME 스니핑 | 업로드된 텍스트 파일을 브라우저가 스크립트로 추측해 실행 (File Upload 실습과 연결) |
| `Referrer-Policy` | 주소 정보 유출 | 외부 링크 클릭 시 내부 주소(쿼리값 포함)가 상대 사이트에 전달 |
| `Permissions-Policy` | 브라우저 기능 악용 | 주입된 스크립트가 카메라 · 위치 권한 요청 |
| `server_tokens off` | 정보 수집 | 응답에 Nginx 정확한 버전이 보여 알려진 취약점 검색에 이용 |

## 4. 핵심 개념: srcdoc 은 왜 안 됐나

```html
<!-- 부모 CSP: script-src 'self' -->
<iframe sandbox="allow-scripts" srcdoc="<script>alert(1)</script>"></iframe>
```

- `srcdoc` 문서는 **주소가 없어서(about:srcdoc) 자기 헤더를 받을 수 없다.** 브라우저는 부모의 CSP 를 그대로 적용한다.
- 그래서 앱에 엄격한 CSP 를 켜면 실습의 `<script>` 도 같이 막힌다 → "어떤 공격을 해도 실패"하는 실습이 된다.
- **방법 A**: 앱 CSP 에 `'unsafe-inline'` 추가 → 실습은 되지만 **앱 전체의 XSS 방어가 사라진다.** ❌
- **방법 B (채택)**: 주소가 있는 별도 페이지(`/practice-frame.html`)를 iframe 으로 열고, 그 경로에만 실습용 CSP 를 붙인다. 앱은 엄격한 CSP 를 유지. ✅

## 5. 코드 읽기

### 5-1. 실습 프레임 로더 (`public/practice-frame.js`)

```js
function onRender(event) {
  if (event.source !== window.parent) return;               // 부모 창이 보낸 것만
  var data = event.data;
  if (!data || data.type !== "sq-render" || typeof data.html !== "string") return;
  window.removeEventListener("message", onRender);          // 한 번만 받음
  document.open(); document.write(data.html); document.close();  // 문서 통째 교체
}
window.addEventListener("message", onRender);
window.parent.postMessage({ type: "sq-frame-ready" }, "*"); // "준비됐어요"
```

- `document.write` 로 그린 문서는 **이 페이지의 CSP(실습용)** 를 그대로 따른다.

### 5-2. 프레임 컴포넌트 (`PracticeFrame.vue`)

```js
watch(() => props.html, () => { renderKey.value += 1; });   // HTML 이 바뀌면 프레임을 새로 만든다

function onMessage(event) {
  const win = frameEl.value?.contentWindow;
  if (!win || event.source !== win) return;                 // 우리 프레임에서 온 것만
  if (event.data?.type !== "sq-frame-ready") return;
  win.postMessage({ type: "sq-render", html: props.html }, "*");
}
defineExpose({ getWindow });   // 부모가 판정 메시지 출처 확인용
```

- sandbox 프레임은 출처가 없어(opaque) 받는 쪽 주소를 지정할 수 없으므로 `"*"` 를 쓴다. 보내는 내용은 서버가 만든 공개 실습 HTML 뿐이라 문제없다.
- 판정은 기존과 같다: 감시 스크립트가 `alert` 을 가로채 flag 를 부모로 보내고, 부모는 `event.source` 가 우리 프레임인지 확인 후 서버에 제출한다.

### 5-3. Nginx (`nginx/nginx.conf`)

```nginx
location ~ ^/practice-frame\.(html|js)$ {
  proxy_pass http://frontend:5173;
  add_header Content-Security-Policy $sq_practice_csp always;   # 실습 전용
  ...
}
location / {
  proxy_pass http://frontend:5173/;
  add_header Content-Security-Policy $sq_app_csp always;        # 앱 (엄격)
  ...
}
```

## 6. 방어를 겹겹이 (Defense in Depth)

XSS 실습 프레임 하나에 방어가 4겹으로 걸려 있다.

| 겹 | 장치 | 실습 스크립트가 해도 결과 |
|---|---|---|
| 1 | `sandbox="allow-scripts"` (allow-same-origin 없음) | `document.cookie` → SecurityError, 부모 화면 DOM 접근 불가 |
| 2 | 실습 CSP `connect-src 'none'` · `form-action 'none'` · `img-src data:` | 외부로 fetch · 폼 전송 · 이미지 요청으로 데이터를 빼낼 수 없음 |
| 3 | 세션 쿠키 `HttpOnly` | (만약 읽을 수 있어도) 스크립트로 세션 쿠키 접근 불가 |
| 4 | 앱 CSP `script-src 'self'` | 실습 밖(앱 화면)에서는 주입 스크립트 자체가 실행 안 됨 |

## 7. 발표용 한 줄 설명

> "앱 전체에는 우리 파일만 실행되는 엄격한 CSP 를 걸고, XSS 실습은 별도 페이지에서 '실행은 되지만 밖으로는 아무것도 못 보내는' 전용 CSP 와 sandbox 로 가뒀습니다. 그래서 일부러 취약한 실습과 안전한 서비스가 한 사이트에 함께 있을 수 있습니다."
