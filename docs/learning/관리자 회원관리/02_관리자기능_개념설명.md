## 1. 요약

- 관리자 페이지(`/admin`)는 **회원관리 · 학생 진도 · 비밀번호 변경** 3개 탭이다.
- 관리자 기능은 회원을 지우고 비밀번호를 바꾸는 **강한 권한**이라, 실습 페이지와 달리 **표준 보안 규칙을 모두** 지킨다.
- 모든 관리자 요청은 **CSRF 검사 → 요청 횟수 제한 → 로그인 확인 → 관리자 역할 확인** 4개 관문을 통과해야 실행된다.
- 비밀번호는 원문을 저장하지 않고 **bcrypt 해시**로만 저장한다. 임시 비밀번호는 서버가 **예측 불가능한 난수**로 만들어 **한 번만** 보여준다.
- 회원 삭제는 그 회원을 가리키는 **자식 기록을 먼저 지운 뒤** 회원을 지운다. 관리자 계정은 대상에서 제외된다.
- 중요한 작업은 **감사 로그([AUDIT])** 로 "누가·무엇을·누구에게·어디서" 했는지 남긴다.

## 2. 개념 설명 (비유)

### 2-1. 전체 그림: 은행 금고실 출입

```
 관리자 요청
     │
     ▼
 ① CSRF 검사 ─────── 우리 화면에서 보낸 요청인가?          아니면 400
     ▼
 ② Rate Limit ────── 너무 자주 시도하지 않았나?            초과면 429
     ▼
 ③ 로그인 확인 ───── 신분증(세션)이 있나?                  없으면 401
     ▼
 ④ 역할 확인 ─────── 직원증(role=admin)인가?               아니면 403
     ▼
 처리 (목록 / 임시 비밀번호 / 삭제 / 비밀번호 변경)
     ▼
 ⑤ 감사 로그 ─────── 출입 기록부에 기록
```

- 은행 금고실에 들어가려면 **정문 확인(CSRF) → 출입 횟수 제한(Rate Limit) → 신분증(로그인) → 직원증(역할)** 을 차례로 통과해야 하고, 들어간 기록은 **출입 기록부(감사 로그)** 에 남는다.
- 하나라도 빠지면 그 틈으로 들어올 수 있으므로 **모든 관리자 API가 같은 관문**을 거치게 했다.

### 2-2. 비밀번호를 "되돌릴 수 없게" 저장하는 이유

- 비밀번호를 그대로 저장하면, DB가 유출되는 순간 모든 회원 비밀번호가 드러난다. 같은 비밀번호를 다른 사이트에서도 쓰는 사람이 많아 피해가 커진다.
- **해시**는 고기를 갈아 다짐육으로 만드는 것과 같다. 다짐육을 보고 원래 고기 덩어리로 되돌릴 수는 없다. 로그인할 때는 입력한 비밀번호를 **똑같이 갈아서** 저장된 다짐육과 같은지만 비교한다.
- **bcrypt** 는 일부러 갈기 어렵게(느리게) 만든 분쇄기다. 정상 로그인 1번은 문제없지만, 공격자가 수억 개 후보를 하나하나 갈아 맞춰 보는 것은 매우 오래 걸린다.
- **salt** 는 사람마다 다른 양념을 섞는 것이다. 같은 비밀번호라도 사람마다 다른 해시가 나와, 미리 계산해 둔 표로 한 번에 맞추는 공격을 막는다.

## 3. 용어 설명

| 용어 | 쉬운 뜻 |
|---|---|
| 관리자(admin) / 학생(student) | 계정의 역할(role). 관리자 API 는 `admin` 만 허용 |
| 인증(Authentication) | "누구인지" 확인 — 로그인 |
| 인가(Authorization) | "무엇을 할 수 있는지" 확인 — 역할 검사 |
| 세션 | 로그인 후 서버가 "이 브라우저는 누구"라고 기억하는 정보. 쿠키로 연결된다 |
| 401 / 403 | 401 = 로그인 안 함(인증 실패), 403 = 로그인했지만 권한 없음(인가 실패) |
| 400 / 404 / 429 | 400 = 요청 내용이 잘못됨, 404 = 대상 없음, 429 = 요청이 너무 많음 |
| CSRF 토큰 | 우리 화면에서만 발급한 일회용 번호표. 다른 사이트가 몰래 보낸 요청을 거절하는 데 쓴다 |
| Rate Limit | 같은 IP 의 요청 횟수 제한 (예: 비밀번호 변경 분당 5회) |
| 해시(hash) | 원문으로 되돌릴 수 없게 바꾼 값 |
| bcrypt | 비밀번호 전용 해시 방식. 일부러 느리게 계산한다 |
| salt | 해시할 때 섞는 무작위 값. 같은 비밀번호도 사람마다 다른 해시가 나온다 |
| salt round(cost) 12 | bcrypt 계산 반복 강도. 숫자가 1 오르면 계산 시간이 약 2배 |
| `secrets` | 파이썬의 암호학적으로 안전한 난수 모듈. 다음 값을 예측할 수 없다 |
| `random` | 일반 난수. 게임·보상 금액용이고 비밀번호·토큰에는 쓰면 안 된다 |
| 임시 비밀번호 | 관리자가 발급하는 10자리 무작위 비밀번호. 응답에서 한 번만 보여준다 |
| 외래키(FK) | "이 줄은 저 테이블의 몇 번 줄에 속한다"는 연결. 부모를 먼저 지우면 오류가 난다 |
| 자식 행 | 다른 테이블의 줄(부모)을 가리키는 줄. 예: 회원의 수강·진도·보상 기록 |
| 감사 로그(Audit Log) | 누가·무엇을·누구에게·어디서 했는지 남기는 기록 |
| 마스킹 | 개인정보 일부를 가려 보여주기 (`010-****-1234`) |
| CLI | 명령줄 도구. 서버 셸에서 `flask set-password` 같은 명령으로 실행 |

## 4. 구조와 코드

### 4-1. 관문 ③④: 로그인 · 역할 확인

```python
# backend/app/admin.py
def _require_admin():
    user = current_user()                                   # 세션으로 누구인지 확인
    if not user:
        return None, (jsonify(message="로그인이 필요합니다."), 401)   # 인증 실패
    if user.role != "admin":
        return None, (jsonify(message="권한이 없습니다."), 403)       # 인가 실패
    return user, None
```

- 모든 관리자 API 가 맨 처음 이 함수를 부른다.
- 화면(라우터)에서도 학생은 `/admin` 에 못 들어가게 막지만, **진짜 보안은 이 서버 검사**다. 화면 검사는 요청을 직접 보내면 우회되기 때문이다.

### 4-2. 관문 ①②: CSRF · Rate Limit

```python
# backend/app/__init__.py
csrf = CSRFProtect()                         # POST·DELETE 등 상태를 바꾸는 요청에 토큰 검사
limiter = Limiter(key_func=get_remote_address)   # IP 기준 요청 횟수 제한

# backend/app/admin.py (예)
@bp.post("/password")
@limiter.limit("5 per minute")               # 비밀번호 변경: 분당 5회
def change_own_password(): ...
```

| API | 요청 제한 |
|---|---|
| 회원 목록 `GET /admin/users?q=` | - (조회) |
| 임시 비밀번호 `POST /admin/users/<id>/reset-password` | 분당 10회 |
| 회원 삭제 `DELETE /admin/users/<id>` | 분당 10회 |
| 본인 비밀번호 변경 `POST /admin/password` | 분당 5회 |

- 화면의 Axios(요청 도구)가 상태를 바꾸는 요청마다 CSRF 토큰을 자동으로 붙이고, 토큰이 만료되면 새로 받아 1회 다시 시도한다.

### 4-3. 비밀번호 해시 저장

```python
def _hash(raw):
    # bcrypt salt round 12
    return bcrypt.hashpw(raw.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode("utf-8")

# 로그인/현재 비밀번호 확인 (auth.py · admin.py)
bcrypt.checkpw(입력값.encode("utf-8"), user.password_hash.encode("utf-8"))   # 같으면 True
```

| 부분 | 의미 | 없으면 생기는 일 |
|---|---|---|
| `gensalt(rounds=12)` | 사람마다 다른 salt + 강도 12 | 같은 비밀번호가 같은 해시 → 미리 만든 표로 한꺼번에 해독 |
| `hashpw` | 되돌릴 수 없는 값으로 변환 | DB 유출 시 원문 비밀번호 노출 |
| `checkpw` | 입력값을 같은 방식으로 해시해 비교 | 원문을 저장해야만 비교 가능 |

### 4-4. 임시 비밀번호 발급

```python
alphabet = 영문 대문자 + 소문자 + 숫자
value = "".join(secrets.choice(alphabet) for _ in range(10))   # 대·소문자·숫자 각 1자 이상 포함되게 생성
user.password_hash = _hash(value)                               # DB에는 해시만
_audit(admin, "reset_password", target)                         # 감사 로그 (비밀번호 값은 남기지 않음)
return jsonify(tempPassword=value)                              # 응답에서 한 번만 보여줌
```

- **왜 서버가 만드나**: 관리자가 직접 정하면 `1234` 같은 쉬운 값을 쓰기 쉽다.
- **왜 `secrets` 인가**: `random` 은 계산 방식상 다음 값을 추측할 수 있어, 비밀번호·토큰 같은 비밀 값에는 쓰면 안 된다.
- **왜 한 번만 보여주나**: 다시 볼 수 있으면 그만큼 노출 기회가 늘어난다. 잊어버리면 새로 발급하면 된다.
- 대상이 관리자 계정이면 거절(400)해, 관리자가 다른 관리자를 초기화할 수 없다.

### 4-5. 회원 삭제 (자식 기록 먼저)

```
users(회원) ◀── enrollments(수강) ◀── attendance_sessions(출석 세션)
            ◀── task_progress(진도·레벨·확인문제 표시)
            ◀── rewards(보상 교환권)
            ◀── point_ledger / xp_ledger(포인트·경험치 장부)
            ◀── verification_codes(인증코드)
```

```python
# 자식 → 부모 순서로 삭제
AttendanceSession  (수강에 딸린 출석 세션) 먼저
for model in (Enrollment, TaskProgress, Reward, PointLedger, XpLedger, VerificationCode):
    model.query.filter_by(user_id=target.id).delete()
db.session.delete(target)        # 마지막에 회원
db.session.commit()
_audit(admin, "delete_user", target)
```

- 부모(회원)를 먼저 지우면, 자식 기록이 "없는 회원"을 가리키게 되어 DB가 **외래키 오류**로 삭제를 거부한다.
- 그래서 가장 안쪽 자식(출석 세션)부터 바깥쪽 순서로 지운다. 삭제는 **되돌릴 수 없으므로** 화면에서 확인창을 한 번 더 띄운다.

### 4-6. 관리자 본인 비밀번호 변경

```
현재 비밀번호 bcrypt 비교 → 틀리면 400
새 비밀번호 8자 미만 / 기존과 같음 → 400
새 비밀번호 해시 저장 → [AUDIT] change_own_password
```

- **현재 비밀번호를 다시 묻는 이유**: 관리자가 잠시 자리를 비운 사이 다른 사람이 화면을 조작해도, 현재 비밀번호를 모르면 바꿀 수 없다.

### 4-7. 감사 로그

```python
def _audit(admin, action, target=None):
    current_app.logger.warning(
        "[AUDIT] admin_id=%s action=%s target_user_id=%s ip=%s", ...)
```

```
[AUDIT] admin_id=1 action=reset_password target_user_id=4 ip=172.18.0.5
```

- 확인 방법: `docker compose logs backend | grep AUDIT`
- 별도 테이블 대신 서버 로그에 남겨 DB 구조 변경 없이 적용했다. **비밀번호 값은 절대 남기지 않는다.**

## 5. 동작 흐름 예시

```
[학생이 비밀번호를 잊음]
1. 관리자: 회원관리 탭 → 학생 검색 → [임시 비밀번호] → 확인창
2. 서버: 관문 4개 통과 → 대상이 학생인지 확인 → secrets 로 10자리 생성 → 해시 저장 → [AUDIT]
3. 화면 상단에 임시 비밀번호 1회 표시 → 관리자가 복사해 학생에게 전달
4. 학생: 임시 비밀번호로 로그인 → 비밀번호 찾기에서 새 비밀번호로 변경

[학생 계정으로 관리자 API 를 직접 호출하면]
→ 관문 ④ 역할 확인에서 403 (실제 확인: 4개 API 모두 403)
[CSRF 토큰 없이 비밀번호 변경 요청을 보내면]
→ 관문 ① 에서 400
```

## 6. 주의점과 한계

- **감사 로그는 서버 로그**라서 컨테이너 로그가 지워지면 함께 사라진다. 오래 보관하려면 별도 저장소(테이블·로그 서버)가 필요하다.
- **임시 비밀번호를 학생에게 전달하는 경로**(메신저 등)는 시스템 밖이다. 전달 후 학생이 바로 바꾸도록 안내해야 한다.
- **관리자 비밀번호를 잊으면** 웹으로는 복구할 수 없고, 서버 셸에서 `docker compose exec backend flask set-password --username admin` 으로 재설정한다(서버 접근 권한이 있는 사람만 가능).
- **휴대폰 번호 마스킹**은 화면 표시용이다. 관리자 API 응답 단계에서도 최소한의 정보만 내보내는 것이 원칙이다.

## 7. 핵심 정리

- 관리자 기능은 강한 권한이라 **CSRF → Rate Limit → 로그인(401) → 관리자 역할(403)** 4개 관문을 모두 거치고, 변경 작업은 **[AUDIT] 로그**를 남긴다.
- 비밀번호는 **bcrypt(salt, 강도 12) 해시**로만 저장하고, 비교는 `checkpw` 로 한다.
- 임시 비밀번호는 **`secrets` 난수 10자리**를 서버가 만들어 **한 번만** 보여준다.
- 회원 삭제는 **자식 기록 → 회원** 순서로 지우고, 관리자 계정은 보호한다.
- 발표용 한 문장: **"관리자 기능은 실습과 달리 표준 보안을 모두 적용해, 네 겹의 관문을 통과한 관리자만 실행할 수 있고, 비밀번호는 되돌릴 수 없는 해시로만 저장하며 모든 변경 작업을 감사 로그로 남긴다."**
