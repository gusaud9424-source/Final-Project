# 01. 마이페이지 — 회원정보 변경 · 비밀번호 변경

> 대상: 웹 보안을 처음 배우는 입문자
> 목표: 로그인한 사용자가 **자기 정보를 스스로 고치는** 기능이 프런트·백엔드·DB에서 어떻게 맞물려 동작하는지, 왜 "현재 비밀번호 재확인"이 필요한지 이해한다.
> 작성: 2026-10-09 · 오현명
> 📘 개념 설명(용어·코드 의미·최종 구조)은 `02_마이페이지_개념설명.md` 참고.

## 1. 요약

- 새 화면 **마이페이지(`/mypage`)** 를 만들었다. 헤더 프로필 패널의 **[마이페이지 · 회원정보 변경]** 버튼으로 들어간다.
- 화면은 카드 3개: **계정 정보(읽기 전용)** · **회원정보 수정** · **비밀번호 변경**.
- 수정 가능 항목: **이름 · 닉네임 · 이메일 · 휴대폰 번호 · 비밀번호**. 아이디·역할은 바꿀 수 없다.
- 회원정보 저장과 비밀번호 변경 모두 **현재 비밀번호를 다시 확인**한 뒤에만 처리한다.
- 입력 규칙은 **회원가입과 같은 기준**을 그대로 재사용했다(서버 `auth.py` 의 정규식·비밀번호 규칙 import).
- 표준 보안 규칙 적용: **CSRF · Rate Limit(분당 5회) · bcrypt(12) · 감사 로그 · 세션 ID 재발급**.
- DB 구조(마이그레이션) 변경은 없다. 기존 `users` 테이블 컬럼만 수정한다.

## 2. 개념 설명 (비유)

**은행 창구에서 내 정보 바꾸기**와 같다.

- 창구 직원은 통장 명의인의 주소·전화번호를 바꿔 줄 수 있다(회원정보 수정).
- 그런데 이미 창구에 앉아 있어도(로그인 상태) **신분증을 한 번 더 보여 달라**고 한다(현재 비밀번호 재확인). 내가 잠깐 자리를 비운 사이 다른 사람이 앉아 바꾸는 걸 막기 위해서다.
- 계좌번호(아이디)는 바꿔 주지 않는다. 계좌 종류(역할)도 고객이 정할 수 없다.
- 비밀번호를 바꾸면 **번호표(세션 ID)를 새로 뽑아 준다.** 예전 번호표를 누가 주웠어도 쓸 수 없다.
- 무엇을 바꿨는지는 **업무일지**에 "주소 변경" 처럼 **항목 이름만** 적는다. 새 주소 자체는 적지 않는다(감사 로그에 개인정보 미기록).

## 3. 용어 설명

| 용어 | 뜻 |
|---|---|
| 마이페이지 | 로그인한 사용자가 자기 계정 정보를 보고 고치는 화면 |
| 재인증(Re-authentication) | 이미 로그인했어도 민감한 변경 전에 비밀번호를 다시 묻는 것 |
| PATCH | "일부 수정" 을 뜻하는 HTTP 메서드. 회원정보 저장에 사용 |
| 409 Conflict | 다른 사람이 이미 쓰고 있는 값(이메일·닉네임)과 겹칠 때 돌려주는 상태코드 |
| 세션 ID 재발급 | 같은 로그인 상태를 유지하면서 쿠키에 담긴 세션 ID만 새 값으로 바꾸는 것 |
| 감사 로그(Audit Log) | `[AUDIT] user_id=… action=…` 형식으로 누가 무엇을 했는지 남기는 서버 로그 |
| IntegrityError | DB 의 UNIQUE 제약에 걸려 저장이 거부될 때 나는 오류. 동시 요청의 마지막 방어선 |

- 넓은 화면은 3열, 1024px 이하는 1열로 쌓인다.

- 회원정보 저장 후에는 성공·실패와 관계없이 현재 비밀번호 칸을 비운다(화면에 남지 않게).
- 색은 모두 `var(--sq-*)` 토큰만 사용했다. 카드·입력칸 스타일은 자료실·관리자 비밀번호 폼과 같다.

## 5. 동작 원리

### 5-1. 공통 보안 관문

```
요청 ─▶ [CSRF 검사] ─▶ [Rate Limit] ─▶ [로그인 확인] ─▶ [현재 비밀번호 bcrypt 비교] ─▶ 처리 ─▶ [AUDIT 로그]
          실패 400       초과 429        없음 401          틀림 400
```

### 5-2. 회원정보 수정

```
[1] 입력 → 프런트 1차 검사 (이름 1~30자 · 닉네임 2~20자/허용 문자 · 이메일 형식 · 휴대폰 10~11자리 · 현재 비밀번호 입력)
[2] PATCH /profile/account { name, nickname, email, phone, current_password }
[3] 서버:
      - 현재 비밀번호 확인 → 틀리면 400
      - 공백 제거 · 이메일 소문자 · 휴대폰 숫자만 남김 (010-1234-5678 → 01012345678)
      - 형식 검사 (회원가입과 같은 정규식) → 400
      - 다른 회원과 닉네임 · 이메일 중복 → 409
      - 바뀐 항목이 없으면 "변경된 내용이 없습니다." 로 끝 (DB 쓰기 · 로그 없음)
      - 저장 → UNIQUE 충돌(동시 요청)이면 rollback 후 409
      - [AUDIT] action=update_account fields=name,email … (값은 기록하지 않음)
[4] 응답의 새 정보로 화면 · 헤더 · 프로필 패널 갱신
```

### 5-3. 비밀번호 변경

```
[1] 현재/새/확인 입력 → 프런트 1차 검사 (빈칸 · 8~64자 · 영문+숫자 · 확인 일치 · 기존과 다름)
[2] POST /profile/password { current_password, new_password }
[3] 서버:
      - 현재 비밀번호 확인 → 틀리면 400
      - 기존과 같음 → 400
      - 회원가입과 같은 규칙(_password_policy_error) → 400
      - bcrypt(12) 해시로 저장
      - 세션 ID 재발급 (로그인은 유지)
      - [AUDIT] action=change_password
[4] 성공 메시지, 입력칸 비움
```

### 왜 이렇게 설계했나

| 결정 | 이유 |
|---|---|
| 정보 수정에도 현재 비밀번호 요구 | 이메일·휴대폰은 **아이디 찾기 · 비밀번호 재설정의 수단**이다. 공용 PC에 로그인이 남아 있을 때 남이 이메일을 자기 것으로 바꾸면 계정을 통째로 빼앗긴다(계정 탈취). |
| 검증 규칙을 `auth.py` 에서 import | 회원가입과 마이페이지의 규칙이 달라지면 "가입은 되는데 수정은 안 되는" 모순이 생긴다. 한 곳만 고치면 둘 다 바뀐다. |
| 아이디 · 역할은 수정 불가 | 역할을 요청으로 받으면 학생이 스스로 `admin` 이 될 수 있다(권한 상승). 서버는 요청에 오는 `role` 을 아예 읽지 않는다. |
| 비밀번호 변경 후 세션 ID 재발급 | 비밀번호를 바꾸는 이유가 "유출이 의심돼서" 인 경우가 많다. 예전 세션 ID 를 누가 갖고 있었다면 더는 쓸 수 없게 한다. |
| 감사 로그에 항목 이름만 | 로그는 여러 사람이 보는 곳이다. 새 이메일·번호를 적으면 로그가 개인정보 저장소가 된다. |
| 중복 확인 + UNIQUE 이중 방어 | 미리 확인해도 두 요청이 동시에 오면 둘 다 통과할 수 있다. 마지막엔 DB 제약이 막고, 서버는 그 오류를 409 로 바꿔 돌려준다. |

## 6. 테스트 결과

로컬에서 Flask 테스트 클라이언트(SQLite 메모리 DB · 가짜 Redis)로 15개 경우를 확인했다. 전부 기대값과 같다.

| # | 경우 | 결과 |
|---|---|---|
| 1 | 로그인 없이 조회 | 401 |
| 2 | 로그인 후 조회 | 200, 아이디·이름·이메일·휴대폰·가입일 반환 |
| 3 | 현재 비밀번호 틀림 | 400 "현재 비밀번호가 올바르지 않습니다." |
| 4 | 다른 회원 이메일로 변경 | 409 "이미 사용 중인 이메일입니다." |
| 5 | 다른 회원 닉네임으로 변경 | 409 "이미 사용 중인 닉네임입니다." |
| 6 | 휴대폰 형식 오류 | 400 |
| 7 | 정상 변경 (`010-5555-6666` 입력) | 200, `01055556666` 으로 저장 |
| 8 | 같은 값으로 다시 저장 | 200 "변경된 내용이 없습니다." |
| 9 | 변경 후 `/auth/me` | 새 이름·이메일 반영 |
| 10 | 비밀번호: 현재 비밀번호 틀림 | 400 |
| 11 | 비밀번호: 숫자 없음 | 400 "영문과 숫자가 모두…" |
| 12 | 비밀번호: 기존과 같음 | 400 |
| 13 | 비밀번호: 정상 변경 | 200 |
| 14 | 변경 직후 같은 브라우저 | 로그인 유지 (세션 재발급 후에도 200) |
| 15 | 새 비밀번호로 다시 로그인 | 200 |

감사 로그 출력 예:

```
[AUDIT] user_id=1 action=update_account fields=name,nickname,email,phone ip=127.0.0.1
[AUDIT] user_id=1 action=change_password ip=127.0.0.1
```

프런트엔드는 `vite build` 로 빌드 오류 없음을 확인했다.

### 직접 확인하는 방법 (Docker)

```bash
docker compose up -d --build
# 브라우저: 로그인 → 헤더 오른쪽 이름 클릭 → [마이페이지 · 회원정보 변경]
```

## 7. 남은 한계 · 다음 작업

- **새 이메일 · 휴대폰 소유 확인 없음**: 지금은 형식만 확인한다. 운영 서비스라면 새 주소로 인증코드를 보내 확인한 뒤 바꿔야 한다(기존 `VerificationCode` 재사용 가능).
- **다른 기기 세션 종료 없음**: 비밀번호를 바꿔도 다른 브라우저의 로그인은 유지된다. Redis 세션을 사용자별로 찾아 지우는 기능이 필요하다.
- **회원 탈퇴 없음**: 관리자 삭제만 있다. 필요하면 마이페이지에 "탈퇴"(비밀번호 확인 + 기록 정리)를 추가한다.
- 다음 작업: `README.md` 작성 (Attribution 섹션 포함).

## 8. 후속 정리 (같은 날 추가)

### 8-1. 헤더 프로필 패널의 닉네임 변경 제거

- 마이페이지가 생겨 닉네임 변경 폼(입력칸 + [변경])을 패널에서 뺐다. 패널에는 **레벨 · 경험치 · 포인트 · [마이페이지 · 회원정보 변경]** 만 남는다.
- 그 폼이 쓰던 `PATCH /api/v1/profile` 도 삭제했다. 이 API 는 **현재 비밀번호 확인 없이** 닉네임을 바꿨기 때문에, 남겨 두면 마이페이지의 재인증 규칙을 돌아가는 뒷문이 된다. 삭제 후 호출하면 405(허용되지 않은 메서드).

```
변경 전 패널                    변경 후 패널
 Lv.3                            Lv.3
 ███████░░░ 70/100 XP            ███████░░░ 70/100 XP
 보유 포인트 149P                보유 포인트 149P
 닉네임 [        ] [변경]   ─▶   [ 마이페이지 · 회원정보 변경 ]
 [ 마이페이지 · 회원정보 변경 ]
```

### 8-2. 출석 완료 후 출석판 숨김

- 출석판에서 **[오늘 출석하고 포인트 받기]** 를 누르면 출석판이 닫히고 대시보드 상단에 "N일차 출석 완료! 포인트 +NP 적립" 이 4초 표시된다(기존 동작).
- 추가로, 오늘 출석을 마쳤으면 대시보드의 **[출석 체크]** 버튼이 **[✔ 오늘 출석 완료]** 로 바뀌고 눌러도 출석판이 열리지 않는다. 14일을 모두 채운 경우도 같다.
- 판단 기준은 서버 응답(`GET /attendance` 의 `claimedToday` · `completed`)이라 새로고침하거나 다시 로그인해도 같게 보인다. 다음 날이 되면 `claimedToday=false` 가 되어 버튼이 다시 열리고, 출석 가능하면 출석판이 자동으로 뜬다.

| 상태 | 버튼 | 클릭 시 |
|---|---|---|
| 오늘 아직 출석 안 함 | 출석 체크 | 출석판 열림 |
