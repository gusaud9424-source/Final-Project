# 02. 마이페이지 — 개념 설명

> 대상: 웹 보안을 처음 배우는 입문자 (발표에서 그대로 설명할 수 있도록)
> 목표: "로그인한 사람이 자기 정보를 바꾸는" 요청 한 번에 무슨 일이 일어나고, 각 보안 장치가 어떤 공격을 막는지 이해한다.
> 작성: 2026-10-09 · 오현명
> 작업 기록은 `01_마이페이지_회원정보변경.md` 참고.

## 1. 요약

- 마이페이지는 **"이미 있는 users 한 줄을, 본인만, 안전하게 고치는 일"** 이다.
- 회원가입(새 줄 추가)과 달리 **"누가 고치는가"** 가 핵심이다. 서버는 요청에 담긴 사용자 ID 를 믿지 않고 **세션에서 꺼낸 ID** 만 쓴다.
- 로그인 상태여도 **현재 비밀번호를 다시 확인**한다(재인증).
- 바꾼 뒤에는 **감사 로그**를 남기고, 비밀번호를 바꾸면 **세션 ID 를 새로 발급**한다.

---

## 2. 전체 구조

```
 [브라우저]                              [Flask 서버 profile.py]                     [MariaDB users]
 MyPageView.vue
  ① GET /profile/account  ───────────▶  로그인 확인 (session.user_id) ───────────▶ SELECT
     폼 채우기            ◀───────────  계정 정보 JSON
  ② 수정 + 현재 비밀번호
     PATCH /profile/account ─────────▶  CSRF · Rate Limit(5/분)
     (X-CSRFToken 자동 첨부)              bcrypt 로 현재 비밀번호 비교
                                         입력 정리 · 규칙 검사 (auth.py 재사용)
                                         닉네임 · 이메일 중복 확인 ─────────────▶ SELECT
                                         저장 (UNIQUE 가 마지막 방어) ──────────▶ UPDATE
                                         [AUDIT] fields=…
  ③ 헤더 · 패널 갱신      ◀───────────  200 / 400 / 409 / 429 + message
```

## 3. 이 기능이 막는 공격

| 공격 | 시나리오 | 막는 장치 |
|---|---|---|
| **IDOR** (남의 정보 수정) | 요청에 `user_id=2` 를 넣어 다른 사람 정보를 바꾸려 함 | 서버가 요청의 ID 를 받지 않음. `current_user()` 가 **세션**에서만 ID 를 꺼냄 |
| **권한 상승** | 요청 JSON 에 `"role": "admin"` 추가 | 서버가 `role` 필드를 읽지도 않음. 아이디·역할은 수정 대상이 아님 |
| **CSRF** | 악성 사이트가 로그인된 브라우저로 이메일 변경 요청을 몰래 보냄 | CSRF 토큰 검사 + **현재 비밀번호**(공격자는 모름) |
| **자리 비운 사이 탈취** | 공용 PC 에 로그인이 남아 있음 → 이메일을 공격자 것으로 바꾼 뒤 "비밀번호 찾기" | 정보 변경에도 **현재 비밀번호 재확인** |
| **비밀번호 대입** | 현재 비밀번호 칸으로 비밀번호를 계속 맞혀 봄 | Rate Limit **분당 5회** |
| **세션 고정 / 유출 세션 재사용** | 예전 세션 ID 를 가진 사람이 계속 접속 | 비밀번호 변경 시 **세션 ID 재발급** |
| **로그를 통한 개인정보 유출** | 서버 로그 열람자가 새 이메일·번호를 봄 | 감사 로그엔 **항목 이름만** 기록 |

> 💡 SecuQuest 의 CSRF 실습 페이지는 바로 이 "비밀번호 확인 없는 정보 변경" 을 **일부러 취약하게** 만든 것이다. 마이페이지는 그 실습의 **안전한 정답 버전**이라고 설명할 수 있다.

## 4. 코드 읽기

### 4-1. 현재 비밀번호 확인 (`profile.py`)

```python
def _check_current_password(user, raw):
    if not isinstance(raw, str) or not raw:      # 빈 값 · 문자열이 아닌 값은 바로 실패
        return False
    return bcrypt.checkpw(raw.encode("utf-8"), user.password_hash.encode("utf-8"))
```

- DB 에는 원문이 없고 해시만 있다. `checkpw` 가 입력값을 같은 방식으로 해시해 비교한다.

### 4-2. 바뀐 항목만 골라 로그 남기기

```python
changed = [field for field, old, new in (
    ("name", user.name, name),
    ("email", user.email, email), ...
) if old != new]
if not changed:
    return jsonify(message="변경된 내용이 없습니다.", ...)
...
_audit(user, "update_account", "fields=" + ",".join(changed))   # 값이 아니라 이름만
```

### 4-3. 동시 요청 마지막 방어

```python
try:
    db.session.commit()
except IntegrityError:          # 두 사람이 같은 이메일로 동시에 저장한 경우
    db.session.rollback()
    return jsonify(message="이미 사용 중인 닉네임 또는 이메일입니다."), 409
```

### 4-4. 세션 ID 재발급

```python
db.session.commit()
current_app.session_interface.regenerate(session)   # 로그인 정보는 그대로, ID 만 새 값
```

- 로그인 때 쓰는 것과 같은 함수(Flask-Session 0.8)다. 사용자는 로그아웃되지 않는다.

### 4-5. 화면에 바로 반영 (`MyPageView.vue`)

```js
if (authStore.user) {
  authStore.user.name = data.name;     // 헤더 이름
  authStore.user.email = data.email;   // 헤더 이메일
}
profileStore.nickname = data.nickname || data.name;   // 프로필 패널 닉네임
```

- Pinia 스토어 값은 반응형이라, 바꾸는 즉시 헤더가 다시 그려진다.

## 5. 프런트 검사 vs 서버 검사

| 구분 | 프런트(`MyPageView.vue`) | 서버(`profile.py`) |
|---|---|---|
| 목적 | 빠른 안내 (요청 전에 실수 알려주기) | **진짜 판정** |
| 우회 가능? | 가능 (개발자 도구 · curl) | 불가능 |
| 규칙 | 서버와 같은 값 복사 | `auth.py` 의 정규식 · 비밀번호 규칙 import |

→ 프런트 검사는 **편의**, 서버 검사는 **보안**이다. 둘 중 하나만 둔다면 반드시 서버.

## 6. 발표용 한 줄 설명

> "마이페이지는 세션으로 본인을 식별하고, 현재 비밀번호로 한 번 더 확인한 뒤에만 정보를 바꿉니다. CSRF 실습에서 공격했던 '확인 없는 정보 변경' 의 안전한 버전입니다."
