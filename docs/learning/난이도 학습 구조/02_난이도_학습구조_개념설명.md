## 1. 요약

- 실습마다 레벨이 4개 있다: **하(Low) → 중(Medium) → 상(High) → 안전(Impossible)**. DVWA의 레벨 구조를 따랐다.
- 발표 피드백("레벨이 섞여 있다, 하→중→상 순서로 학습해야 한다")을 반영해, **앞 레벨을 통과해야 다음 레벨이 열리게** 했다.
- 순서는 **화면(스테퍼)과 서버(403 거부)** 두 곳에서 지킨다. 화면만 막으면 요청을 직접 보내 건너뛸 수 있기 때문이다.
- 레벨 통과 기록은 새 테이블 없이 기존 `task_progress` 에 `tier_low` 같은 이름으로 저장한다.
- 레벨을 처음 통과할 때마다 **보물상자로 레벨 보상**이 나오고, 하·중·상을 모두 통과하면 **2회차 실습 성공 미션**이 완료된다.

## 2. 개념 설명 (비유)

### 2-1. 전체 그림: 게임 스테이지

```
 ┌─────────┐   통과   ┌─────────┐   통과   ┌─────────┐   통과   ┌─────────┐
 │ 1. 하   │ ───────▶ │ 2. 중   │ ───────▶ │ 3. 상   │ ───────▶ │ 4. 안전 │
 │ 방어 없음│          │ 단순 방어│          │ 강화 방어│          │ 올바른 방어│
 └─────────┘          └─────────┘          └─────────┘          └─────────┘
   항상 열림           하 통과 시 열림       중 통과 시 열림       상 통과 시 열림
```

- 1스테이지를 깨야 2스테이지 문이 열린다. 스테이지를 건너뛰면 "앞에서 배운 것이 왜 다음 단계에서 막히는지"를 놓친다.
- 마지막 "안전" 스테이지는 보스전이 아니라 **정답 해설**에 가깝다. 공격이 왜 막히는지 직접 보는 단계라서, 한 번 시도하면 통과다.

### 2-2. 레벨이 뜻하는 것 (8개 과목 공통)

| 레벨 | 서버 상태 | 학습 포인트 | 통과 조건 |
|---|---|---|---|
| 하 (Low) | 방어 없음 | 취약점이 생기는 기본 원리 | 실습 성공 |
| 중 (Medium) | 단순한 방어 (일부만 검사) | 흔한 방어가 왜 부족한가 | 실습 성공 |
| 상 (High) | 강화된 방어 (금지 목록 확장 등) | 금지 목록 방식의 근본 한계 | 실습 성공 |
| 안전 (Impossible) | 올바른 방어 코드 | 공격이 막히는 원리 | 1회 이상 시도 |

### 2-3. "화면과 서버 두 곳에서 지킨다"의 뜻

- **화면(브라우저)** 은 학생 컴퓨터에서 돌아간다. 버튼을 회색으로 만들어도, 개발자 도구로 요청을 직접 만들어 보낼 수 있다.
- 그래서 **서버도 같은 규칙을 다시 확인**한다. 잠긴 레벨로 실행·힌트 요청이 오면 거절(403)한다.
- 비유: 놀이공원 입구에 "키 120cm 이상" 안내판(화면)만 있으면 무시하고 들어갈 수 있다. 그래서 탑승구 직원(서버)이 키를 다시 잰다.
- 보안 학습 플랫폼이므로 **"클라이언트 검증만 믿지 않는다"** 는 원칙을 그대로 지킨 것이다.

## 3. 용어 설명

| 용어 | 쉬운 뜻 |
|---|---|
| 레벨(tier) | 같은 취약점 안의 단계. 코드에서는 `low` · `medium` · `high` · `impossible` |
| DVWA | Damn Vulnerable Web Application. 일부러 취약하게 만든 학습용 웹 앱. Low~Impossible 레벨 구조를 참고했다 |
| 통과(cleared) | 그 레벨의 조건을 채운 상태 (하·중·상은 실습 성공, 안전은 1회 시도) |
| 잠김(locked) | 바로 앞 레벨을 아직 통과하지 않아 선택·실행할 수 없는 상태 |
| 스테퍼(stepper) | 단계를 번호 순서로 나열하고 현재·완료·잠김을 표시하는 화면 요소 |
| 클라이언트 | 사용자 쪽 프로그램. 여기서는 브라우저와 그 안의 화면 코드(Vue) |
| 서버 | 요청을 받아 처리하는 쪽. 여기서는 Flask 백엔드 |
| 클라이언트 검증 | 화면에서 미리 막는 것. 편의용일 뿐 보안 장치가 아니다 |
| 서버 검증 | 서버가 요청을 받을 때 다시 확인하는 것. 진짜 보안 장치 |
| API | 화면과 서버가 주고받는 요청 주소와 규칙 (예: `GET /courses/<과목>/practice/tiers`) |
| HTTP 403 Forbidden | "요청은 이해했지만 조건이 안 맞아 거절한다"는 응답 번호 |
| task_progress | 미션 완료 기록 테이블. 레벨 통과도 `tier_<레벨>` 이름으로 여기에 저장 |
| 멱등 | 여러 번 해도 결과가 한 번 한 것과 같음. 같은 레벨을 다시 통과해도 기록은 하나 |
| 마이그레이션 | DB 테이블 구조를 바꾸는 작업. 이번에는 기존 테이블을 재사용해서 필요 없었다 |

## 4. 구조와 코드

### 4-1. 레벨 순서와 잠금 판정 (서버)

```python
# backend/app/progress.py
TIER_ORDER = ("low", "medium", "high", "impossible")
TIER_LABELS = {"low": "하", "medium": "중", "high": "상", "impossible": "안전"}

def is_tier_unlocked(tier, cleared):
    """첫 레벨은 항상 열림, 그 외에는 바로 앞 레벨을 통과해야 열림"""
    index = TIER_ORDER.index(tier)
    return index == 0 or TIER_ORDER[index - 1] in cleared
```

| 줄 | 의미 | 없으면 생기는 일 |
|---|---|---|
| `TIER_ORDER` | 레벨 순서를 한 곳에 정의 | 화면·서버가 서로 다른 순서를 쓰면 잠금이 어긋남 |
| `index == 0` | 첫 레벨(하)은 항상 열림 | 아무 레벨도 시작할 수 없음 |
| `TIER_ORDER[index - 1] in cleared` | 바로 앞 레벨을 통과했는지 확인 | 아무 레벨이나 바로 선택 가능 (피드백 이전 상태) |

### 4-2. 통과 기록 저장 (기존 테이블 재사용)

```python
def _tier_key(tier):
    return f"tier_{tier}"                         # 예: "tier_low"

def mark_tier_cleared(user_id, course_id, tier):
    return _upsert_progress(user_id, course_id, _tier_key(tier))   # 있으면 그대로, 없으면 생성(멱등)

def cleared_tiers(user_id, course_id):            # 통과한 레벨 집합: {"low", "medium"} 등
    ...
```

- 새 테이블을 만들지 않은 이유: 진도율·관리자 집계는 미션 키(`concept` · `practice` · `defense`)만 세도록 되어 있어서, `tier_*` 기록이 섞여도 진도율 계산에 영향이 없다. 마이그레이션 없이 바로 적용할 수 있었다.

### 4-3. API 세 곳에서 잠금 검사

| API | 하는 일 | 잠긴 레벨이면 |
|---|---|---|
| `GET /courses/<과목>/practice/tiers` | 레벨별 `{unlocked, cleared}` 목록 반환 | (조회만 함) |
| `GET /courses/<과목>/practice/hints?difficulty=<레벨>` | 해당 레벨 힌트 | **403** "이전 레벨을 먼저 통과해야…" |
| `POST /courses/<과목>/practice/run` | 실습 실행 | **403** (실행 자체를 하지 않음) |

```python
# backend/app/courses.py (실행 API 요약)
if not is_tier_unlocked(difficulty, cleared_tiers(user.id, course.id)):
    return jsonify(message=_TIER_LOCKED_MESSAGE), 403      # ① 서버 검증

result = builder.run(difficulty, user_input)                # ② 레벨별 실습 실행

if difficulty == "impossible" or result.success:            # ③ 통과 판정
    mark_tier_cleared(user.id, course.id, difficulty)
    _roll_tier_reward(user.id, course, difficulty)          # ④ 레벨 보상(보물상자, 레벨당 1회)

if {"low", "medium", "high"} <= cleared_now:                # ⑤ 하·중·상 모두 통과
    mark_task_complete(user.id, course.id, "practice")      #    → 2회차 미션 완료 + 미션 보상
```

| 번호 | 의미 |
|---|---|
| ① | 화면을 우회해 요청을 보내도 잠긴 레벨은 실행되지 않음 |
| ③ | 하·중·상은 성공해야 통과, 안전은 시도만 해도 통과 (막히는 것을 확인하는 단계라서) |
| ④ | 같은 레벨을 다시 통과해도 보상은 다시 생기지 않음 (ref `practice:<과목>:<레벨>`) |
| ⑤ | 2회차 "실습 성공"은 레벨 하나가 아니라 하·중·상 전체 통과가 조건 |

### 4-4. 화면: 스테퍼와 안내

```
 ┌──────────┐┌──────────┐┌──────────┐┌──────────┐
 │ ✓        ││ 2        ││ 🔒       ││ 🔒       │
 │ 하 (Low) ││ 중(Medium)││ 상 (High)││ 안전     │
 │ 통과     ││ 진행 가능 ││ 잠김     ││ 잠김     │
 └──────────┘└──────────┘└──────────┘└──────────┘
 ┃ 중 레벨 — 단순한 방어가 추가됩니다. 그 방어가 왜 충분하지 않은지 생각해 봅니다.
 ┃ 하 레벨 통과! 이제 중 레벨이 열렸습니다.    ← 통과 직후 안내
```

```javascript
// frontend/src/views/ChapterDetailView.vue (요약)
async function loadTiers() {                       // 화면을 열면 서버에서 레벨 상태를 받아옴
  const { data } = await client.get(`/courses/${slug}/practice/tiers`);
  tierList.value = data.tiers;
  selectedTier.value = firstOpenTier(data.tiers);  // 아직 통과하지 않은 첫 레벨을 자동 선택
}

function onResult(data) {                          // 실행 결과가 오면 스테퍼를 즉시 갱신
  tierList.value = data.tiers;
  if (data.tierCleared) tierNotice.value = "… 레벨 통과! 이제 … 레벨이 열렸습니다.";
}
```

| 상태 | 표시 | 클릭 |
|---|---|---|
| 진행 가능 | 번호(파란색) | 가능 |
| 통과 | 초록 체크 | 가능 (복습) |
| 잠김 | 회색 + 자물쇠 | 불가 |

- 레벨 의미 문구(하=방어 없음 …)는 `frontend/src/content/tierGuides.js` 의 `TIER_META` 한 곳에서 관리해 8개 과목이 같은 뜻을 쓴다.

## 5. 동작 흐름 예시 (처음 실습하는 학생)

```
1. 실습 페이지 열기 → 서버: 하만 열림 → 스테퍼에서 "하" 자동 선택
2. 중 레벨을 클릭 → 잠김(회색)이라 선택 안 됨
   (개발자 도구로 중 레벨 실행 요청을 직접 보내도 → 서버 403)
3. 하 레벨 실습 성공 → 하 "통과" + 보물상자에 하 레벨 보상 + "중 레벨이 열렸습니다"
4. 중 → 상 순서로 통과 (레벨마다 보물상자 보상)
   상까지 통과하면 → 2회차 "실습 성공" 미션 완료 → 미션 탭에서 미션 보상 수령
5. 안전 레벨에서 같은 방식으로 시도 → 막히는 것을 확인 → 안전 "통과" + 보상
```

## 6. 주의점과 한계

- **수강신청하면 레벨 기록도 초기화된다.** 다시 신청한 과목은 하 레벨부터 시작한다.
- **레벨 구조 도입 전에 실습에 성공한 기록**은 레벨 기록이 없으므로 하 레벨부터 다시 진행한다. 이전 "실습 완료" 기록은 하·중·상 통과 기록이 없으면 완료로 보지 않는다.
- **안전 레벨은 시도만으로 통과**한다. 목적이 "막히는 것을 확인"이기 때문이다.
- 레벨별 구체적인 접근 방법은 문서에 쓰지 않고 실습 페이지의 **힌트 보기**(현재 열린 레벨만 제공)로 안내한다.

## 7. 핵심 정리

- 실습 레벨은 **하 → 중 → 상 → 안전** 순서로만 열린다. 앞 레벨을 통과해야 다음 레벨이 열린다.
- 순서는 **화면(스테퍼)** 과 **서버(403)** 가 함께 지킨다. 화면만으로는 보안이 되지 않기 때문이다.
- 통과 기록은 `task_progress` 에 `tier_<레벨>` 로 저장해 마이그레이션 없이 적용했다.
- 레벨을 처음 통과할 때마다 보물상자 보상, 하·중·상을 모두 통과하면 2회차 미션 완료.
- 발표용 한 문장: **"레벨이 섞여 있다는 피드백을 반영해, 앞 레벨을 통과해야 다음 레벨이 열리도록 화면과 서버 양쪽에서 강제했고, 레벨마다 보상과 미션을 연결해 하→중→상 학습을 끝까지 이끈다."**
