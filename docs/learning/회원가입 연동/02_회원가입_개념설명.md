# 02. 회원가입 — 개념 설명

> 대상: 웹 보안을 처음 배우는 입문자 (발표에서 그대로 설명할 수 있도록)
> 목표: 회원가입 한 번에 프론트·서버·DB에서 무슨 일이 일어나는지, 각 보안 장치가 왜 필요한지 이해한다.
> 작성: 2026-10-09 · 오현명
> 작업 기록은 `01_회원가입_실제연동.md` 참고.

## 1. 요약

- 회원가입은 **"새 사용자 한 줄을 users 테이블에 안전하게 추가하는 일"** 이다.
- 화면(SignupView)이 입력을 받고 → 스토어(auth.js)가 서버에 보내고 → 서버(auth.py)가 **검사·중복 확인·암호화** 후 DB에 저장한다.
- 비밀번호는 **원문을 저장하지 않고 bcrypt 해시만** 저장한다.
- 역할(role)은 **서버가 `student`로 고정**한다. 사용자가 정할 수 없다.
- 요청은 **CSRF 토큰**으로 "우리 화면에서 보낸 것"인지 확인하고, **Rate Limit**으로 대량 자동 가입을 늦춘다.
- 실패 이유는 **HTTP 상태코드(400·409·429)와 한국어 문구**로 돌려준다.

## 2. 개념 설명 (비유)

### 전체 구조

```
 [브라우저]                          [Flask 서버]                         [MariaDB]
 SignupView.vue                      auth.py  POST /api/v1/auth/signup     users 테이블
  ① 입력 + 1차 검사                   ③ Rate Limit (1분 5회)
  ② auth.js signup() ──요청──▶        ④ CSRF 토큰 확인
     (JSON + X-CSRFToken)            ⑤ 입력 정리 (공백·소문자·숫자만)
                                     ⑥ _validate_signup (규칙 검사)
                                     ⑦ 아이디·이메일 중복 확인 ─────▶ SELECT
                                     ⑧ bcrypt 해시 + role=student
                                     ⑨ 저장 (UNIQUE가 마지막 방어) ──▶ INSERT
  ⑪ 성공: 알림 → /login   ◀──응답── ⑩ 201 / 400 / 409 / 429 + message
     실패: 빨간 문구 표시
```

### 비유: 도서관 회원증 발급 창구

| 회원가입 단계 | 도서관 창구 |
|---|---|
| 화면 1차 검사 | 신청서를 내기 전에 직원이 "빈칸 있어요" 하고 돌려줌 |
| Rate Limit | 한 사람이 1분에 신청서를 수십 장 내면 "잠시 후 오세요" |
| CSRF 토큰 | 도서관 안 창구에서 받은 **번호표**가 있어야 접수 (밖에서 몰래 넣은 신청서 거부) |
| 서버 검증 | 직원이 신청서 규칙(글자 수·형식)을 다시 확인 |
| 중복 확인 | 장부에 같은 회원번호·이메일이 있는지 찾아봄 |
| bcrypt | 비밀번호를 **봉인 도장**으로 바꿔 보관. 직원도 원래 비밀번호를 모름 |
| role 고정 | 신청서에 "관리자"라고 적어도 무시하고 "일반 회원"으로 발급 |
| UNIQUE 제약 | 두 창구에서 동시에 같은 번호를 발급하려 하면 장부 자체가 거부 |

### 핵심 문장 풀이

- **"화면 검사는 편의, 서버 검사는 보안"**: 화면의 자바스크립트는 사용자가 개발자 도구로 끄거나, 화면을 거치지 않고 직접 요청을 보낼 수 있다. 그래서 화면 검사는 "빨리 알려주기" 용도이고, **막는 일은 서버만** 할 수 있다.
- **"요청이 보낸 값을 그대로 믿지 않는다"**: 서버는 `username·password·name·email·phone` 다섯 개만 꺼내 쓰고, 그 밖의 값(`role` 등)은 아예 읽지 않는다.

## 3. 용어 설명

| 용어 | 뜻 |
|---|---|
| 프론트엔드 (Vue) | 브라우저에서 보이는 화면. `SignupView.vue` |
| 스토어 (Pinia) | 여러 화면이 함께 쓰는 상태·함수 모음. `stores/auth.js` |
| 백엔드 (Flask) | 요청을 받아 처리하는 서버 프로그램. `backend/app/auth.py` |
| Blueprint | Flask에서 관련 API를 묶는 단위. 여기선 `/api/v1/auth` |
| 엔드포인트 | API 하나의 주소 + 방식. `POST /api/v1/auth/signup` |
| POST | 서버에 새 데이터를 보내 만들 때 쓰는 요청 방식 |
| JSON | `{ "username": "..." }` 같은 키-값 데이터 형식 |
| payload | 요청 본문에 담긴 데이터 |
| axios | 프론트에서 서버로 요청을 보내는 라이브러리. `api/client.js` |
| 인터셉터 | 모든 요청/응답에 자동으로 끼어드는 함수 (CSRF 토큰 자동 첨부) |
| 검증 (Validation) | 입력이 규칙에 맞는지 검사 |
| 정규식 (Regex) | 문자열 규칙을 짧게 쓰는 표기. `^[A-Za-z0-9_]{4,20}$` = 영문·숫자·밑줄 4~20자 |
| 정규화 (Normalize) | 같은 의미의 값을 한 모양으로 맞춤 (이메일 소문자, 휴대폰 숫자만) |
| ORM / SQLAlchemy | 파이썬 객체로 DB를 다루는 도구. `User(...)` → INSERT |
| UNIQUE 제약 | DB가 같은 값을 두 번 저장하지 못하게 하는 규칙 (`username`, `email`) |
| IntegrityError | UNIQUE 같은 DB 규칙을 어겼을 때 나는 오류 |
| rollback | 실패한 저장 작업을 없던 일로 되돌림 |
| 해시 (Hash) | 원래 값으로 되돌릴 수 없게 바꾼 값 |
| bcrypt | 비밀번호 전용 해시. **salt**를 자동으로 섞고, **일부러 느리게** 동작 |
| salt | 해시마다 섞는 무작위 값. 같은 비밀번호도 해시가 매번 달라짐 |
| rounds (cost) | bcrypt 반복 강도. 12 = 2¹² 번 반복. 클수록 느리고 안전 |
| role | 계정 권한 (`student` / `admin`) |
| 대량 할당 (Mass Assignment) | 요청의 값을 통째로 저장해 사용자가 바꾸면 안 되는 필드(role)까지 바뀌는 취약점 |
| CSRF | 다른 사이트가 사용자 브라우저를 이용해 몰래 요청을 보내는 공격 |
| CSRF 토큰 | 우리 서버가 발급한 값. 요청 헤더 `X-CSRFToken`에 담겨 와야 통과 |
| Rate Limit | 정해진 시간에 보낼 수 있는 요청 수 제한. Flask-Limiter + Redis로 셈 |
| Redis | 빠른 메모리 저장소. 세션과 Rate Limit 횟수를 저장 |
| 상태코드 201 | Created — 새로 만들어짐 |
| 상태코드 400 | Bad Request — 규칙에 안 맞는 요청 (형식 오류, CSRF 오류) |
| 상태코드 409 | Conflict — 이미 있는 값과 충돌 (중복) |
| 상태코드 429 | Too Many Requests — 요청이 너무 많음 |
| 경쟁 상태 (Race Condition) | 두 요청이 거의 동시에 와서 순서가 꼬이는 상황 |
| 계정 열거 (Account Enumeration) | 응답 차이로 "이 아이디/이메일이 가입돼 있다"를 알아내는 것 |

## 4. 구조와 코드

### 4-1. 입력 규칙 상수 (`auth.py`)

```python
USERNAME_RE = re.compile(r"^[A-Za-z0-9_]{4,20}$")          # 영문·숫자·밑줄 4~20자
EMAIL_RE = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")      # 형식만 확인 (실제 존재 여부는 X)
PHONE_RE = re.compile(r"^01[0-9]{8,9}$")                    # 숫자만, 01로 시작 10~11자리
PASSWORD_MIN, PASSWORD_MAX = 8, 64                          # bcrypt는 72바이트까지만 사용
NAME_MAX = 30
```

| 줄 | 의미 | 없으면 생기는 일 |
|---|---|---|
| `USERNAME_RE` | `^`시작 `$`끝 사이 전체가 영문·숫자·`_` 4~20개여야 함 | 공백·`<`·한글 섞인 아이디, 1글자 아이디가 저장됨 → 화면 표시 깨짐, 다른 기능 오작동 |
| `EMAIL_RE` | `@` 앞뒤에 글자, 뒤쪽에 `.`이 있는지만 확인 | 인증코드를 보낼 수 없는 주소가 저장됨 |
| `PHONE_RE` | 하이픈 제거 후 `01`로 시작하는 숫자 10~11자리 | 비밀번호 재설정 문자 인증이 불가능한 번호 저장 |
| `PASSWORD_MAX = 64` | bcrypt는 72바이트 이후를 **무시**함 → 길이 상한을 둬서 오해 방지 | 아주 긴 비밀번호 뒷부분이 실제로는 검사되지 않는데 사용자는 모름 |

### 4-2. 검증 함수 (`auth.py`)

```python
def _validate_signup(username, password, name, email, phone):
    """회원가입 입력 검증: 문제가 있으면 안내 문구, 없으면 None"""
    if not USERNAME_RE.match(username):
        return "아이디는 영문·숫자·밑줄(_) 4~20자로 입력하세요."
    if not (PASSWORD_MIN <= len(password) <= PASSWORD_MAX):
        return f"비밀번호는 {PASSWORD_MIN}~{PASSWORD_MAX}자로 입력하세요."
    if not (re.search(r"[A-Za-z]", password) and re.search(r"[0-9]", password)):
        return "비밀번호에는 영문과 숫자가 모두 들어가야 합니다."
    if password.lower() == username.lower():
        return "비밀번호는 아이디와 같을 수 없습니다."
    ... (이름 · 이메일 · 휴대폰 검사, 요약)
    return None
```

- **하나라도 틀리면 그 이유를 바로 돌려준다** → 사용자는 무엇을 고칠지 정확히 안다.
- 아이디와 같은 비밀번호를 막는 이유: 아이디는 공개되는 값이라 가장 먼저 시도되는 비밀번호다.

### 4-3. 회원가입 API (`auth.py`, 요약)

```python
@bp.post("/signup")
@limiter.limit("5 per minute")                          # ① 1분 5회
def signup():
    payload = request.get_json(silent=True) or {}       # ② JSON이 아니면 빈 dict
    username = str(payload.get("username", "")).strip()
    password = str(payload.get("password", ""))         #    비밀번호는 공백도 문자로 인정
    name = str(payload.get("name", "")).strip()
    email = str(payload.get("email", "")).strip().lower()
    phone = _normalize_phone(str(payload.get("phone", "")))   # 숫자만 남김

    error = _validate_signup(username, password, name, email, phone)
    if error:
        return jsonify(message=error), 400              # ③ 형식 오류

    if User.query.filter_by(username=username).first():
        return jsonify(message="이미 사용 중인 아이디입니다."), 409
    if User.query.filter_by(email=email).first():
        return jsonify(message="이미 가입된 이메일입니다."), 409   # ④ 중복

    user = User(
        username=username,
        password_hash=bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode("utf-8"),
        role="student",                                 # ⑤ 서버가 고정
        name=name, email=email, phone=phone,
    )
    db.session.add(user)
    try:
        db.session.commit()
    except IntegrityError:                              # ⑥ 동시 가입
        db.session.rollback()
        return jsonify(message="이미 사용 중인 아이디 또는 이메일입니다."), 409

    current_app.logger.info("signup user_id=%s", user.id)   # 비밀번호·이메일은 로그에 안 남김
    return jsonify(message=f"{username} 님, 회원가입이 완료되었습니다. 로그인해 주세요."), 201
```

| 장치 | 하는 일 | 없으면 생기는 일 |
|---|---|---|
| `@limiter.limit("5 per minute")` | 같은 IP에서 1분 5회 초과 시 429 | 봇이 초당 수백 개 가짜 계정 생성, DB·bcrypt 연산으로 서버 과부하 |
| CSRF 검사 (`CSRFProtect`, 전역) | 헤더의 토큰이 서버 발급 값과 맞는지 확인 | 다른 사이트가 방문자 브라우저로 몰래 가입 요청을 보낼 수 있음 |
| `str(...)` 감싸기 | 숫자·목록 등이 와도 문자열로 바꿔 처리 | `{"username": 123}` 같은 요청에 `.strip()`에서 500 오류 |
| `.lower()` (이메일) | `Hong@x.com`과 `hong@x.com`을 같은 값으로 | 대소문자만 다른 이메일로 중복 가입, 아이디 찾기 실패 |
| `_normalize_phone` | `010-1234-5678` → `01012345678` | 같은 번호가 여러 모양으로 저장돼 재설정 문자 인증 조회 실패 |
| `bcrypt.hashpw(..., gensalt(rounds=12))` | salt 섞인 느린 해시만 저장 | DB가 유출되면 **모든 비밀번호 원문이 그대로 노출** |
| `role="student"` | 요청의 role을 읽지도 않음 | `{"role":"admin"}`을 끼워 보내 관리자 계정 생성 (대량 할당) |
| 중복 확인 (SELECT) | 친절한 409 문구 | DB 오류가 그대로 나가거나 이유를 모르는 실패 |
| `IntegrityError` + `rollback` | 동시 요청이 중복 확인을 함께 통과해도 DB UNIQUE가 막음 | 500 오류, 세션이 망가진 채로 다음 요청까지 실패 |
| 로그에 user_id만 | 기록은 남기되 개인정보·비밀번호는 제외 | 로그 파일에 민감정보가 쌓여 유출 위험 |

### 4-4. 429 응답을 JSON으로 (`__init__.py`)

```python
@app.errorhandler(429)
def handle_rate_limit(_error):
    return jsonify(error="rate_limit", message="요청이 너무 많습니다. 잠시 후 다시 시도하세요."), 429
```

- Flask-Limiter 기본 응답은 **HTML**이라 프론트가 `message`를 읽을 수 없었다. JSON으로 바꿔 화면에 그대로 표시한다.
- 로그인·인증코드 발송 등 **Rate Limit이 걸린 모든 API**에 함께 적용된다.

### 4-5. 프론트 스토어 (`stores/auth.js`)

```javascript
async function signup({ username, password, name, email, phone }) {
  try {
    const { data } = await client.post("/auth/signup", { username, password, name, email, phone });
    return { success: true, message: data.message };
  } catch (error) {
    return {
      success: false,
      message: error.response?.data?.message || "회원가입에 실패했습니다. 잠시 후 다시 시도하세요.",
    };
  }
}
```

- `client`(axios)가 **CSRF 토큰을 자동으로 붙인다** (`api/client.js` 인터셉터). 토큰이 만료되면 한 번 새로 받아 재시도한다.
- 성공/실패를 `{ success, message }` 한 모양으로 돌려줘 화면은 `message`만 보여주면 된다. (`login()`과 같은 모양)
- `error.response?.data?.message`: 서버가 안내 문구를 줬으면 그걸, 서버에 닿지도 못했으면(네트워크 오류) 기본 문구를 쓴다.

### 4-6. 화면 (`SignupView.vue`, 요약)

```javascript
// 화면 1차 검사: 사용자에게 빨리 알려주는 용도 (최종 판단은 항상 서버)
function validate() { ... 빈칸 · 아이디 규칙 · 비밀번호 규칙 · 비밀번호 확인 · 휴대폰 ... }

async function onSubmit() {
  if (loading.value) return;            // 연타 방지 (중복 요청 차단)
  errorMessage.value = validate();
  if (errorMessage.value) return;
  ...
  if (!result.success) { errorMessage.value = result.message; return; }   // 빨간 문구
  alert(result.message);
  router.push("/login");
}
```

| 부분 | 의미 | 없으면 생기는 일 |
|---|---|---|
| `validate()` | 서버와 같은 규칙으로 먼저 검사 | 오타 하나에도 서버 왕복 → 느리고 Rate Limit 횟수 낭비 |
| 비밀번호 확인 비교 | 화면에서만 검사 (서버는 비밀번호 하나만 받음) | 오타 난 비밀번호로 가입돼 로그인 불가 |
| `if (loading) return` | 처리 중 다시 누르면 무시 | 버튼 연타로 같은 요청이 여러 번 전송 |
| `errorMessage` + `role="alert"` | 오류를 입력칸 아래 빨간 글씨로, 화면 낭독기도 읽음 | 알림창을 닫으면 무엇이 틀렸는지 다시 볼 수 없음 |
| 자동 로그인 안 함 | 가입 후 로그인 화면으로 | (선택 사항) 로그인 흐름을 한 곳에 모아 세션 처리 단순화 |

## 5. 동작 흐름

**예시 1 — 정상 가입**

1. 아이디 `student_01`, 비밀번호 `abcd1234`, 이름 `홍길동`, 이메일 `Hong@Example.com`, 휴대폰 `010-1234-5678` 입력 → [가입하기]
2. 화면 검사 통과 → `auth.js`가 `POST /api/v1/auth/signup` 전송 (헤더에 `X-CSRFToken`)
3. 서버: Rate Limit 통과 → CSRF 통과 → 정리 결과 이메일 `hong@example.com`, 휴대폰 `01012345678`
4. 규칙 검사 통과 → 중복 없음 → bcrypt 해시(`$2b$12$...`) 생성 → `role=student`로 저장
5. 201 + "student_01 님, 회원가입이 완료되었습니다. 로그인해 주세요." → 알림 → `/login`
6. 같은 아이디·비밀번호로 로그인 성공

**예시 2 — 이미 있는 아이디**

1~3 동일 → 4. `SELECT`에서 같은 username 발견 → 409 "이미 사용 중인 아이디입니다." → 입력칸 아래 빨간 글씨

**예시 3 — 요청 조작 (role 끼워 넣기)**

- 개발자 도구로 본문에 `"role": "admin"`을 추가해 보내도 서버는 `role`을 읽지 않으므로 **student로 저장**된다.

**예시 4 — 자동 가입 봇**

- 같은 IP에서 1분에 6번째 요청부터 429 "요청이 너무 많습니다." → 1분이 지나야 다시 가능.

## 6. 주의점과 한계

| 항목 | 현재 상태 | 이유 / 개선 방향 |
|---|---|---|
| 이메일 소유 확인 | 하지 않음 (형식만 검사) | 남의 이메일로 가입 가능. 개선: 가입 시 이메일 인증코드(기존 `VerificationCode` 재사용) |
| 휴대폰 중복 | 허용 (DB에 UNIQUE 없음) | 가족이 번호를 공유할 수 있어 허용. 비밀번호 재설정은 아이디+번호로 찾으므로 동작함 |
| 계정 열거 | 아이디·이메일 중복 시 "이미 있음"을 알려줌 | 가입 화면에서는 사용성 때문에 흔히 허용. 대신 Rate Limit으로 대량 조회를 늦춤. (아이디 찾기·비밀번호 재설정은 일반 문구로 열거를 막고 있음) |
| Rate Limit 기준 | IP 기준 1분 5회 | 같은 와이파이를 쓰는 여러 명이 동시에 가입하면 걸릴 수 있음 |
| 비밀번호 규칙 | 길이 + 영문·숫자 | 유출된 흔한 비밀번호 목록 검사는 없음 |
| 닉네임 | 가입 시 받지 않음 | 마이페이지에서 설정 (nullable 컬럼) |
| 자동 로그인 | 하지 않음 | 로그인 화면에서 역할 선택·세션 재발급을 한 곳에서 처리 |
| 오해 주의 | "화면에서 막았으니 안전" ❌ | 화면 검사는 언제든 우회 가능, **서버 검사가 진짜 방어** |

## 7. 핵심 정리

- 회원가입 = **검사 → 중복 확인 → 해시 → 저장**, 모든 판단은 서버가 한다.
- 비밀번호는 **bcrypt 해시만**, 역할은 **서버가 student로 고정**.
- 앞단의 문지기: **CSRF 토큰**(우리 화면에서 온 요청인지) + **Rate Limit**(너무 많이 오지 않는지).
- 마지막 방어선: **DB UNIQUE 제약** (동시 가입까지 막음).
- 결과는 **201 / 400 / 409 / 429 + 한국어 문구**로 돌려줘 화면은 그대로 표시만 한다.

> **발표용 한 문장**: "회원가입은 화면에서 한 번, 서버에서 다시 한 번 검사하고, 비밀번호는 bcrypt로 봉인해 저장하며, 권한은 서버가 정하기 때문에 요청을 조작해도 관리자 계정을 만들 수 없습니다."
