# 03. 인증 화면 복원 · 로그인 회원가입 버튼 · 휴대폰 아이디 찾기

> 대상: 웹 보안을 처음 배우는 입문자 (발표에서 그대로 설명할 수 있도록)
> 목표: 아이디·비밀번호 찾기/회원가입 화면을 로그인 화면과 같은 이전 UI로 되돌린 이유, 깨진 회원가입 폼의 원인, 휴대폰으로 아이디 찾기가 동작하는 원리를 이해한다.
> 작성: 2026-10-09 · 오현명

---

## 1. 요약

- **화면 복원**: 아이디 찾기·비밀번호 찾기·회원가입 화면을 **로그인 화면과 같은 400px 카드 UI**(커밋 `230b88b` 이전 모습)로 되돌렸다.
- **회원가입 폼 깨짐 수정**: 개편 UI의 `AuthCard`는 정해진 칸 구조만 꾸며 주는데, 새로 넣은 안내 문구·오류 문구가 그 구조 밖이라 간격·정렬이 무너졌다. 이전 UI로 통일하며 해결.
- **로그인 화면에 회원가입 버튼** 추가 ("아직 계정이 없나요?" + 테두리 버튼).
- **아이디 찾기 두 방식 모두 실제 동작**: 이메일(기존 API) + **휴대폰(새 API, 이름 + 번호 → SMS 인증코드)**. 휴대폰 방식은 그동안 **mock**(가짜 성공)이었다.
- 같은 이름·번호로 가입한 계정이 여러 개면 **모두 보여준다**.
- 비밀번호 찾기도 아이디 찾기와 **같은 UI**(이메일/휴대폰 탭 → 인증코드 → 새 비밀번호)로 바꿨다. 인증은 **둘 중 하나**로 한다 (9장).

## 2. 개념 설명 (비유)

### 전체 구조

```
                 ┌──────────── 로그인 (/login) ────────────┐
                 │ 아이디 찾기 · 비밀번호 찾기              │
                 │ ─────────────────────────────            │
                 │ 아직 계정이 없나요?  [ 회원가입 ]  ← 추가  │
                 └──────────────────────────────────────────┘
                       │                 │              │
             /find-id ─┤                 │              └─ /signup
   [이메일로 찾기 | 휴대폰으로 찾기]    /find-password  [이메일로 찾기 | 휴대폰으로 찾기]
        │                 │                 │
  POST find-id/      POST find-id/       아이디 + 이메일/번호 → 코드 1개 확인
  send-code          send-sms-code       → 같은 브라우저에서만 새 비밀번호
  verify             verify-sms
        └───────┬─────────┘
       VerificationCode 테이블 (목적 find_id, target = 이메일 또는 번호)
```

### 비유: 은행 창구에서 "제 계좌번호가 뭐였죠?"

| 단계 | 은행 창구 | 우리 서비스 |
|---|---|---|
| 본인 정보 제시 | 이름 + 휴대폰 번호를 말함 | 이름 + 휴대폰 번호 입력 |
| 본인 확인 | 그 번호로 인증 문자를 보냄 | SMS 6자리 인증코드 발송 |
| 정보 없을 때 | "확인 후 문자 드립니다"라고만 말함 (가입 여부 비공개) | 계정이 없어도 **같은 안내 문구**, 문자는 안 보냄 |
| 확인 완료 | 문자 숫자를 맞게 말하면 계좌번호 알려줌 | 코드가 맞으면 아이디 표시 |
| 재사용 방지 | 한 번 쓴 인증번호는 끝 | 성공한 코드는 `verified=True` → 다시 못 씀 |

### 핵심 문장 풀이

- **"계정이 없어도 같은 문구"**: "그런 사람 없음"이라고 답하면, 남이 이름·번호를 넣어 보며 **누가 가입했는지 알아낼 수 있다(계정 열거)**. 그래서 결과와 상관없이 같은 말을 한다.
- **"목적은 같고 받는 곳(target)으로 구분"**: DB의 `purpose`는 정해진 값만 들어가는 **Enum**이라 새 값을 넣으려면 DB 구조 변경(마이그레이션)이 필요하다. 그래서 목적은 `find_id` 그대로 쓰고, 코드를 **어디로 보냈는지(target: 이메일 주소 or 휴대폰 번호)** 로 두 방식을 구분했다.

## 3. 용어 설명

| 용어 | 뜻 |
|---|---|
| AuthCard | 아이디 찾기·비밀번호 찾기·회원가입이 함께 쓰는 카드 틀 컴포넌트 |
| slot | 컴포넌트 틀 안에 바깥에서 내용을 끼워 넣는 자리. `<slot />`, `<slot name="links" />` |
| `:slotted()` | 슬롯에 끼워 넣은 요소를 꾸미는 CSS 문법. 정해 둔 클래스만 꾸며짐 |
| scoped 스타일 | 그 컴포넌트 안에서만 적용되는 CSS |
| router-link | 페이지 이동 링크 (새로고침 없이 화면만 바뀜). `replace`는 뒤로가기 기록을 남기지 않음 |
| props (라우터) | 주소에 따라 화면에 값을 넘김. `/find-id/phone` → `method: "phone"` |
| 세션 (session) | 서버가 브라우저별로 기억하는 값. 비밀번호 찾기에서 "이 브라우저가 인증을 마쳤다"를 기억 |
| mock | 진짜 기능 대신 "된 척"만 하는 임시 코드 |
| SMS / SOLAPI | 문자 메시지 / 문자를 보내 주는 외부 서비스 |
| 인증코드 | 6자리 숫자. 5분 유효, 5번 틀리면 무효 |
| VerificationCode | 인증코드 기록 테이블 (사용자, target, 목적, 코드 해시, 만료 시각, 시도 횟수, 확인 여부) |
| target | 코드를 보낸 곳 (이메일 주소 또는 휴대폰 번호) |
| purpose / Enum | 코드의 목적. Enum은 미리 정한 값(`find_id` 등)만 허용하는 DB 타입 |
| 마이그레이션 | DB 테이블 구조를 바꾸는 작업 (Alembic 스크립트) |
| SHA-256 해시 | 인증코드를 원문 대신 저장하는 방식 (`_hash_code`) |
| `hmac.compare_digest` | 비교에 걸리는 시간이 항상 같아 "몇 글자까지 맞았는지" 새지 않는 비교 함수 |
| 계정 열거 | 응답 차이로 가입 여부를 알아내는 것 |
| Rate Limit | 시간당 요청 횟수 제한 (발송 1분 5회, 확인 1분 10회) |

## 4. 구조와 코드

### 4-1. 회원가입 폼이 깨진 원인

```html
<!-- 개편 UI의 AuthCard: 슬롯 안의 .sq-auth-field 구조만 꾸밈 -->
::slotted(.sq-auth-field) { ... }
::slotted(.sq-auth-field__input) { ... }

<!-- 회원가입에 추가한 요소: 위 구조에 없는 클래스 → 꾸밈 X -->
<small class="sq-signup-hint">...</small>        ← 라벨 안에서 줄바꿈·간격 어긋남
<p class="sq-signup-error">...</p>               ← 카드 레이아웃(flex) 밖으로 흐름
```

- 개편 UI는 **정해진 모양(라벨 + 입력칸)** 만 예쁘게 되도록 만들어졌고, 회원가입에 6칸 + 안내 문구 + 오류 문구를 넣자 틀과 맞지 않았다.
- **해결**: 로그인과 같은 이전 `AuthCard`로 되돌리고 모든 화면이 같은 클래스(`sq-auth-form · sq-auth-label · sq-auth-input · sq-auth-hint · sq-auth-error · sq-auth-submit`)를 쓰게 통일.

| 이전 UI로 통일해서 좋은 점 | 없으면(따로따로면) 생기는 일 |
|---|---|
| 로그인과 같은 카드·버튼·탭 모양 | 화면마다 생김새가 달라 같은 서비스로 안 보임 |
| 공용 클래스 하나로 모든 화면 유지보수 | 한 화면 고치면 다른 화면이 깨지는 일 반복 |

### 4-2. 로그인 화면 회원가입 버튼 (`LoginView.vue`)

```html
<div class="sq-login-signup">
  <span>아직 계정이 없나요?</span>
  <router-link to="/signup" class="sq-login-signup__btn">회원가입</router-link>
</div>
```

- 로그인 버튼(채움)과 구분되도록 **테두리 버튼**으로 만들었다. 색은 `--sq-color-accent` 토큰만 사용.
- 관리자 계정은 가입으로 만들 수 없다 (서버가 role을 student로 고정, `02` 문서 참고).

### 4-3. 아이디 찾기 화면 (`FindIdView.vue`, 요약)

```javascript
const props = defineProps({ method: { type: String, default: "email" } });
const isPhone = computed(() => props.method === "phone");   // /find-id/phone 이면 true

// 발송: 방식에 따라 다른 API
isPhone.value
  ? client.post("/auth/find-id/send-sms-code", { name, phone })
  : client.post("/auth/find-id/send-code", { email });

// 확인: 아이디가 여러 개면 목록, 하나면 한 줄
foundUsernames.value = data.usernames || [data.username];

watch(isPhone, () => { /* 탭 바꾸면 코드·메시지·결과 초기화 */ });
```

| 부분 | 의미 | 없으면 생기는 일 |
|---|---|---|
| 주소로 탭 구분 (`/find-id`, `/find-id/phone`) | 새로고침·뒤로가기 해도 같은 탭 유지 | 새로고침하면 항상 이메일 탭으로 돌아감 |
| `watch(isPhone)` 초기화 | 탭 전환 시 이전 결과 제거 | 이메일 결과가 휴대폰 탭에 남아 헷갈림 |
| `data.usernames \|\| [data.username]` | 휴대폰(여러 개)·이메일(1개) 응답을 같은 모양으로 | 화면이 두 응답 모양을 따로 처리해야 함 |

### 4-4. 휴대폰 아이디 찾기 API (`auth.py`, 요약)

```python
@bp.post("/find-id/send-sms-code")
@limiter.limit("5 per minute")
def find_id_send_sms_code():
    name = str(payload.get("name", "")).strip()
    phone = _normalize_phone(str(payload.get("phone", "")))      # 010-1111-2222 → 01011112222
    user = User.query.filter_by(name=name, phone=phone).order_by(User.id).first() if name and phone else None
    if user:
        code, _ = _issue_code(user, phone, "find_id")            # target = 번호
        _try_send_sms(phone, f"[SecuQuest] 아이디 찾기 인증코드 {code} (5분 이내 입력)")
    return jsonify(message=GENERIC_SEND_MESSAGE)                  # 계정 유무와 관계없이 같은 문구


@bp.post("/find-id/verify-sms")
@limiter.limit("10 per minute")
def find_id_verify_sms():
    users = User.query.filter_by(name=name, phone=phone).order_by(User.id).all() if name and phone else []
    record = _latest_active_code(users[0].id, "find_id") if users else None
    if record and record.target != phone:                        # 최근 코드가 이메일용이면 인정 X
        record = None
    if not _code_valid_and_matches(record, code):                # 만료·5회 초과·불일치 확인
        if record: record.attempts += 1; db.session.commit()
        return jsonify(message="인증코드가 올바르지 않거나 만료되었습니다."), 400
    record.verified = True                                       # 한 번 쓰면 끝
    db.session.commit()
    return jsonify(username=users[0].username, usernames=[u.username for u in users])
```

| 장치 | 하는 일 | 없으면 생기는 일 |
|---|---|---|
| 이름 + 번호 둘 다 요구 | 번호만 아는 사람이 아이디를 못 찾게 | 번호만으로 남의 아이디 조회 시도 가능 |
| `_normalize_phone` | 하이픈·공백 제거 후 비교 | `010-1111-2222`로 입력하면 못 찾음 |
| 같은 안내 문구 | 가입 여부 비공개 | 이름·번호 조합으로 가입자 확인(계정 열거) |
| 계정 없으면 발송 안 함 | 엉뚱한 번호로 문자 X | 남에게 스팸 문자, 문자 비용 낭비 |
| `target != phone` 확인 | 이메일 코드와 휴대폰 코드를 섞어 쓰지 못함 | 다른 경로로 받은 코드로 인증 통과 |
| `_code_valid_and_matches` | 5분 만료 · 5회 초과 무효 · 해시 비교 | 6자리를 무한히 대입해 맞힐 수 있음 |
| `verified = True` | 한 번 쓴 코드는 다시 못 씀 | 코드가 남아 있는 5분 동안 반복 조회 |
| Rate Limit 5/10회 | 발송·확인 요청 속도 제한 | 문자 폭탄, 코드 무차별 대입 |
| 여러 계정 모두 표시 | 가족이 번호를 공유해 가입한 경우 대응 | 첫 계정만 보여 나머지 아이디를 못 찾음 |

## 5. 동작 흐름

**예시 1 — 휴대폰으로 아이디 찾기**

1. 로그인 → "아이디 찾기" → **휴대폰으로 찾기** 탭 (`/find-id/phone`)
2. 이름 `김철수`, 휴대폰 `010-1111-2222` → [SMS 인증코드 발송]
3. 서버: 번호를 `01011112222`로 정리 → 이름·번호가 맞는 계정 찾음 → 6자리 코드 해시 저장(5분) → 문자 발송 → "입력하신 정보가 유효하면 인증코드를 발송했습니다."
4. 받은 코드 입력 → [확인] → 코드 일치 → `verified=True`
5. 화면: "이 정보로 가입된 아이디입니다. **kim_a1**, **kim_b2**" (계정이 1개면 "회원님의 아이디는 ○○ 입니다.")

**예시 2 — 가입하지 않은 이름·번호**

- 같은 안내 문구가 나오지만 **문자는 오지 않는다** → 코드를 넣어도 "인증코드가 올바르지 않거나 만료되었습니다."

**예시 3 — 이메일로 아이디 찾기**

- `KIM@x.com`처럼 대문자로 넣어도 소문자로 정리해 찾음 → 이메일 코드 입력 → 아이디 표시.

**예시 4 — 회원가입 버튼**

- 로그인 화면 아래 [회원가입] → `/signup` → 가입 후 로그인 화면으로 돌아옴.

## 6. 주의점과 한계

| 항목 | 내용 |
|---|---|
| 아이디 전체 공개 | 인증을 통과하면 아이디를 가리지 않고 보여준다 (본인 확인 후이므로 허용). 더 엄격하게 하려면 `ki****`처럼 일부 가리기 가능 |
| 문자 발송 실패 | SOLAPI 오류 시 로그만 남기고 같은 안내 문구 → 사용자는 문자가 안 와서 알 수 있음. 재발송은 1분 5회 내에서 가능 |
| 이름이 다르게 저장된 경우 | 가입 때 이름과 **정확히 같아야** 찾음 (띄어쓰기 포함) |
| 휴대폰 중복 | 번호는 UNIQUE가 아니라 여러 계정이 나올 수 있음 → 모두 표시 |
| 개편 UI 디자인 토큰 | `design-tokens.css`의 `--sq-auth-*` 값은 남아 있지만 지금은 사용하지 않음 (정리 대상) |
| 오해 주의 | 화면을 이전 UI로 돌렸지만 **기능은 개편 때보다 늘었다** (휴대폰 찾기 실제 동작, 회원가입 실제 저장) |

## 7. 핵심 정리

- 인증 화면 4개(로그인·회원가입·아이디 찾기·비밀번호 찾기)가 **같은 카드 UI**를 쓴다.
- 회원가입 폼이 깨진 원인은 **틀(AuthCard)이 모르는 요소를 끼워 넣은 것** → 공용 클래스로 통일해 해결.
- 아이디 찾기는 **이메일 / 휴대폰(이름 + 번호)** 모두 실제 인증코드로 동작한다.
- 보안 장치: 같은 안내 문구(계정 열거 방지) · 5분 만료 · 5회 제한 · 1회용 코드 · target 확인 · Rate Limit.

> **발표용 한 문장**: "아이디 찾기는 이메일이나 이름+휴대폰 번호로 받은 1회용 인증코드를 확인한 뒤에만 아이디를 보여주고, 가입 여부는 끝까지 알려주지 않아 남의 정보를 캐낼 수 없게 했습니다."

## 9. 비밀번호 찾기 — 아이디 찾기와 같은 UI

### 9-1. 바뀐 점

| | 변경 전 | 변경 후 |
|---|---|---|
| 화면 | 아이디 · 이메일 발송 · SMS 발송 · 코드 2개 · 새 비밀번호를 한 화면에 나열 | **이메일로 찾기 / 휴대폰으로 찾기 탭** → 아이디 + (이메일 또는 번호) → 인증코드 → 새 비밀번호 |
| 인증 | 이메일 코드 **와** SMS 코드 둘 다 | 선택한 방식의 코드 **하나** (아이디 찾기와 같은 수준) |
| 새 비밀번호 규칙 | 8자 이상 | 회원가입과 같음: 8~64자, 영문+숫자, 아이디와 다르게 |
| API | `verify-codes` (코드 2개) | `verify-code` (`method`: `email`/`sms`, 코드 1개) |

```
[아이디 + 이메일(또는 번호)] → 발송 ─▶ 코드 입력 → [확인] ─▶ 인증 완료 시에만
                                                           [새 비밀번호 · 확인] → 변경 → 1.5초 후 /login
```

> **보안 수준 메모**: 두 곳 인증 → 한 곳 인증으로 바뀌었다. 대부분의 서비스가 쓰는 방식이며, 아래 장치로 보완한다. 더 엄격하게 하려면 이전처럼 두 코드를 모두 요구하도록 되돌릴 수 있다.

### 9-2. 코드 (`auth.py`, 요약)

```python
RESET_PURPOSES = {"email": "reset_password_email", "sms": "reset_password_sms"}

@bp.post("/reset-password/verify-code")
def reset_password_verify_code():
    purpose = RESET_PURPOSES.get(method)                 # email / sms 외의 값은 거부
    record = _latest_active_code(user.id, purpose)        # 고른 방식으로 받은 코드만
    if not _code_valid_and_matches(record, code): ... 400
    record.verified = True
    session["reset_user_id"] = user.id                    # 이 브라우저가 인증을 마쳤음
    session["reset_purpose"] = purpose

@bp.post("/reset-password/confirm")
def reset_password_confirm():
    error = _password_policy_error(new_password, username) # 회원가입과 같은 규칙
    if session.get("reset_user_id") != user.id: ... 400    # 다른 브라우저 차단
    record = _latest_verified_code(user.id, purpose)
    if record is None or record.expires_at < now: ... 400   # 인증 후 5분 안에만
    user.password_hash = bcrypt(...rounds=12)
    db.session.delete(record)                              # 인증 1회용
    session.pop("reset_user_id"); session.pop("reset_purpose")
```

| 장치 | 하는 일 | 없으면 생기는 일 |
|---|---|---|
| 아이디 + 이메일/번호 일치해야 발송 | 남의 아이디만으로 코드 발송 불가 | 아이디만 알면 피해자에게 코드 폭탄 |
| 같은 안내 문구 | 아이디·이메일 조합의 존재 여부 비공개 | 계정 열거 |
| `method` 허용 목록 | `email`/`sms` 외 값 거부 | 엉뚱한 목적의 코드(예: 아이디 찾기 코드)로 통과 시도 |
| 세션에 인증 기록 | 인증한 **그 브라우저**에서만 변경 | 남이 아이디만 넣고 confirm을 바로 호출해 비밀번호 변경 |
| 인증 기록 삭제 + 세션 정리 | 한 번 인증으로 한 번만 변경 | 같은 인증으로 여러 번 변경 |
| 5분 만료 | 인증 후 오래 방치된 화면 무효 | 공용 PC에 열어 둔 화면으로 나중에 변경 |
| 비밀번호 규칙 통일 | 가입과 재설정의 기준이 같음 | 재설정으로 약한 비밀번호(예: 8자 숫자만) 우회 |
