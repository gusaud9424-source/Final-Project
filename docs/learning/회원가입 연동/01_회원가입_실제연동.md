# 01. 회원가입 실제 연동 (mock → 서버 저장)

## 1. 요약

- **변경 전**: `stores/auth.js`의 `signup()`이 0.3초 기다린 뒤 "완료(mock)"만 띄웠다. **DB에는 아무것도 저장되지 않아** 가입한 아이디로 로그인할 수 없었다.
- **변경 후**: `POST /api/v1/auth/signup` API를 새로 만들어 **입력 검증 → 중복 확인 → bcrypt 해시 → DB 저장**까지 실제로 처리한다.
- 가입 화면에 DB 필수 항목인 **이름 · 휴대폰 번호**를 추가했다 (비밀번호 재설정 문자 인증에도 사용).
- 역할(role)은 **서버가 항상 `student`로 고정** → 요청을 조작해도 관리자로 가입할 수 없다.
- CSRF 토큰 검사, **1분 5회 Rate Limit**, 오류 문구를 화면 안에 표시(알림창 대신)까지 적용.
- 가입 후 자동 로그인은 하지 않고 **로그인 화면으로 이동**한다.

---

## 2. 개념 설명 (비유)

**도서관 회원증 발급 창구**와 같다.

- 예전: 창구 직원이 "등록됐어요!"라고 말만 하고 장부에 적지 않았다 → 다음에 와도 회원이 아니다. (mock)
- 지금: 직원이 신청서를 **검사**(빈칸·형식) → 장부에서 **같은 이름이 있는지 확인** → 비밀번호는 **봉인 도장(bcrypt)** 을 찍어 원문 없이 보관 → 장부에 기록.
- 회원 등급(일반/관리자)은 **신청서에 적어도 무시**하고 창구가 "일반"으로 정한다.

## 3. 용어 설명

| 용어 | 뜻 |
|---|---|
| mock | 진짜 기능 대신 "된 척"만 하는 임시 코드 |
| API | 화면(프론트)이 서버에 일을 시키는 주소와 약속. 여기선 `POST /api/v1/auth/signup` |
| 검증(Validation) | 입력값이 규칙(길이·형식)에 맞는지 검사 |
| bcrypt | 비밀번호를 되돌릴 수 없게 바꾸는(해시) 방식. 느리게 설계돼 무차별 대입에 강함 |
| 409 Conflict | "이미 있는 값과 충돌" (아이디·이메일 중복) |
| 400 Bad Request | "요청 내용이 규칙에 안 맞음" (형식 오류) |
| 201 Created | "새로 만들어졌음" (가입 성공) |
| 429 Too Many Requests | 짧은 시간에 요청이 너무 많음 (Rate Limit) |
| CSRF 토큰 | 우리 사이트 화면에서 보낸 요청인지 확인하는 값 |

## 4. 화면 & 동작

```
┌ 회원가입 ─────────────────────────────┐
│ 아이디        [          ]             │  영문·숫자·밑줄(_) 4~20자
│ 비밀번호      [          ]             │  8~64자, 영문과 숫자를 모두 포함
│ 비밀번호 확인 [          ]             │
│ 이름          [          ]   ← 추가    │
│ 이메일        [          ]             │  인증코드를 받는 주소
│ 휴대폰 번호   [          ]   ← 추가    │  숫자만 (예: 01012345678)
│ (빨간 글씨) 이미 사용 중인 아이디입니다. │  ← 오류는 화면 안에 표시
│ [            가입하기            ]     │
└────────────────────────────────────────┘
   성공 → "○○ 님, 회원가입이 완료되었습니다. 로그인해 주세요." → /login
```

| 상황 | 결과 |
|---|---|
| 빈칸 / 비밀번호 확인 불일치 | 화면에서 바로 안내 (서버 요청 안 함) |
| 형식 오류 (아이디·비밀번호·이메일·휴대폰·이름) | 400 + 해당 안내 |
| 아이디 중복 / 이메일 중복 | 409 + "이미 사용 중인 아이디입니다." / "이미 가입된 이메일입니다." |
| 1분에 6번째 요청 | 429 + "요청이 너무 많습니다. 잠시 후 다시 시도하세요." |
| 성공 | 201 → 알림 후 로그인 화면 |

### 관련 파일

| 파일 | 역할 |
|---|---|
| `backend/app/auth.py` | `POST /signup`, `_validate_signup()`, 입력 규칙 상수 |
| `backend/app/__init__.py` | 429(Rate Limit) 오류를 JSON 안내로 바꾸는 핸들러 |
| `frontend/src/stores/auth.js` | `signup()` mock 제거 → 실제 API 호출 |
| `frontend/src/views/SignupView.vue` | 이름·휴대폰 칸, 규칙 안내, 화면 1차 검사, 오류 표시 |

## 5. 동작 원리

```
[가입하기] → 화면 1차 검사 → POST /auth/signup (X-CSRFToken 자동 첨부)
   → Rate Limit(1분 5회) → 입력 정리(공백 제거, 이메일 소문자, 휴대폰 숫자만)
   → _validate_signup → 아이디/이메일 중복 확인 → bcrypt(rounds=12)
   → User(role="student") 저장 → 201
```

### 왜 이렇게 했나

- **검사를 두 번(화면 + 서버)** 하는 이유: 화면 검사는 사용자 편의용이고 쉽게 건너뛸 수 있다. **최종 판단은 항상 서버**가 한다.
- **role 고정**: 요청 본문의 값을 그대로 저장하면 누구나 관리자 계정을 만들 수 있다(대량 할당 취약점).
- **IntegrityError 처리**: 두 사람이 동시에 같은 아이디로 가입하면 중복 확인을 둘 다 통과할 수 있다 → DB의 UNIQUE 제약이 막고, 409로 안내한다.

## 6. 정리

- 회원가입이 **실제로 DB에 저장**되고, 가입한 계정으로 바로 로그인된다.
- 보안: 서버 검증 · bcrypt 해시 · role 고정 · CSRF · Rate Limit · 동시 가입 대비.
- 남은 일: 이메일 소유 확인(인증코드) 없이 가입됨, 닉네임은 가입 시 받지 않음(마이페이지에서 설정).
