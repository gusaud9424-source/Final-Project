## 1단계: 화면 용어 통일 (챕터/강의실 → 과목/대시보드)

### 1. 왜 했나

이 프로젝트는 처음 설계할 때 학습 단위를 "챕터"라고 불렀다. 그런데 프로젝트가 진행되면서 백엔드(서버) 쪽 데이터 구조는 "과목(Course)"이라는 이름으로 정리되었다. 문제는 **서버 쪽 이름은 "과목"으로 바뀌었는데, 화면에 보이는 글자(문구)는 예전 이름인 "챕터", "강의실"을 그대로 쓰고 있었다**는 점이다.

예를 들어 대시보드 페이지 제목은 "내 강의실"이라고 써 있는데, 같은 화면 안의 버튼은 "챕터 선택하러 가기"라고 되어 있어서, 사용하는 사람 입장에서는 "강의실"과 "챕터"가 서로 다른 개념인지 헷갈릴 수 있었다.

**안 하면 생기는 문제**
- 처음 보는 사용자가 "챕터"와 "과목"이 같은 것인지 다른 것인지 헷갈린다.
- 발표(데모)할 때 "저희는 과목 단위로 설계했습니다"라고 설명하면서 화면에는 "챕터"라고 떠 있으면 신뢰도가 떨어진다.
- 나중에 코드를 유지보수할 때, 화면 문구만 보고 "챕터라는 기능이 따로 있나?"라고 착각해서 엉뚱한 곳을 고칠 수 있다.

### 2. 무엇을 바꿨나

**중요: 이 작업은 화면에 "보이는 글자"만 바꾼 것이다. 버튼을 눌렀을 때 실제로 이동하는 주소(URL 경로)나, 서버와 데이터를 주고받는 코드는 전혀 건드리지 않았다.** 예를 들어 "과목 선택" 버튼을 눌렀을 때 이동하는 주소는 여전히 `/chapters`라는 예전 이름을 그대로 쓴다. 사용자 눈에 보이는 이름표만 바꾸고, 프로그램 내부에서 쓰는 "이름표를 찾아가는 주소"는 그대로 둔 것이다. (내부 주소까지 한꺼번에 바꾸면 관련된 다른 코드가 줄줄이 영향을 받아서, 이번엔 범위를 "눈에 보이는 글자"로만 좁혔다.)

| 파일 | 이 파일의 역할 | 무엇을 바꿨나 |
|---|---|---|
| `frontend/src/components/layout/AppHeader.vue` | 모든 화면 맨 위에 항상 떠 있는 헤더(상단 메뉴 바) | 상단 메뉴의 "챕터 선택" → "과목 선택" |
| `frontend/src/views/DashboardView.vue` | 로그인 후 처음 보는 "내 학습 현황" 화면 | 제목 "내 강의실" → "학습 대시보드", 설명 문구 2곳, 버튼 문구, 통계 라벨까지 총 5곳 |
| `frontend/src/views/AdminView.vue` | 관리자가 전체 학생 현황을 보는 화면 | 안내 문구 "챕터별 진도" → "과목별 진도" |
| `frontend/src/views/CourseDetailView.vue` | 과목 하나를 클릭했을 때 나오는 상세 화면(실습/미션/과목 정보 탭이 있는 곳) | 뒤로가기 링크 "내 강의실로 돌아가기" → "대시보드로 돌아가기" |

| `frontend/src/components/common/VulnerabilityPage.vue` | 실제로 실습(예: Command Injection 문제 풀기)을 진행하는 화면의 공통 틀 | 뒤로가기 링크를 "과목 상세로 돌아가기"라는 고정 문구 대신, 지금 풀고 있는 과목 이름을 직접 넣어서 "← Command Injection 과목으로 돌아가기"처럼 뜨게 함 |

### 3. 작업 흐름

이 단계는 **API도, 서버도, 데이터베이스도 전혀 관여하지 않는다.** 순전히 "화면에 어떤 글자를 보여줄지"만 바꾼 것이라서, 흐름이 아주 짧다.

```
[사용자 행동]                [화면(브라우저)]
사용자가 대시보드 페이지를  →  Vue가 DashboardView.vue 파일 안에
연다                           적혀 있는 글자를 그대로 화면에 그린다
                               (이 안에 "학습 대시보드"라는 글자가
                               직접 코드로 박혀 있음)

[API 호출]  →  없음 (이 글자를 보여주기 위해 서버에 따로 물어보지 않는다)
[서버]      →  관여 안 함
[저장소(DB)] →  관여 안 함
```

비교를 위해 참고하면, 예를 들어 "완료한 과목 개수: 3개"처럼 **숫자**가 들어가는 부분은 서버에서 API로 받아온 값을 화면에 끼워 넣는 것이지만, 이번에 바꾼 "학습 대시보드", "과목 선택" 같은 **제목·버튼 문구**는 서버에서 받아오는 게 아니라 Vue 파일 안에 직접 한글로 쓰여 있는 고정 텍스트다. 그래서 이 파일들만 고치면 바로 화면에 반영된다.

### 4. 동작 원리 (비유)

이 작업은 **가게 간판을 새로 다는 것**과 비슷하다.

어떤 가게가 원래는 손님 응대할 때 "저희 1지점입니다"라고 말하는데, 정작 가게 정문 간판에는 "1호점"이라고 적혀 있다고 해보자. 가게(진짜 매장, 물건, 직원)는 하나도 안 바뀌었는데, 손님 입장에서는 "1지점"이랑 "1호점"이 같은 곳인지 헷갈린다.

이번 작업은 이 간판 글자를 전부 "1호점"(= 과목/대시보드)으로 통일해서 다시 붙인 것이다. 가게 내부 시스템(포스기 번호, 창고 위치 등 = 서버 데이터 구조, 인터넷 주소)은 그대로 두고, **손님 눈에 보이는 간판 글자만** 새로 바꿔 단 것과 같다.

### 5. 코드 해설

`DashboardView.vue` 파일에서 실제로 바뀐 부분 중 하나를 그대로 가져와서 한 줄씩 설명한다.

```vue
<h1 class="sq-dashboard__title">
  {{ authStore.isAdmin ? "전체 학생 현황" : "학습 대시보드" }}
</h1>
```

- `<h1 ...>` : 이건 HTML(웹페이지를 만드는 기본 언어) 태그다. `h1`은 "가장 큰 제목"이라는 뜻이다. 뉴스 기사에서 제일 큰 글씨로 나오는 헤드라인을 떠올리면 된다.
- `class="sq-dashboard__title"` : 이 제목에 어떤 디자인(글자 크기, 색깔 등)을 입힐지 정해주는 이름표다. 실제 디자인 값은 다른 CSS 파일에 따로 정의되어 있다.
- `{{ ... }}` : Vue(이 프로젝트가 쓰는 프론트엔드 도구)에서 "이 중괄호 두 개 안에 있는 건 그냥 글자가 아니라 계산해서 나온 값을 보여줘라"는 뜻이다. 즉 `{{ }}` 안에 있는 내용은 상황에 따라 바뀔 수 있다.
- `authStore.isAdmin` : 지금 로그인한 사람이 "관리자"인지 아닌지를 나타내는 값이다. `true`(맞음) 또는 `false`(아님) 둘 중 하나다.
- `? "전체 학생 현황" : "학습 대시보드"` : 이건 "삼항 연산자"라는 문법으로, 한국어로 풀면 **"관리자이면 '전체 학생 현황'을 보여주고, 아니면(일반 학생이면) '학습 대시보드'를 보여줘라"**는 뜻이다. 오늘 바뀐 부분은 뒤쪽의 `"학습 대시보드"`인데, 원래는 `"내 강의실"`이라고 쓰여 있었다.

또 하나, 상단 메뉴 버튼도 살펴보자.

```vue
<router-link class="sq-tab" to="/chapters">과목 선택</router-link>
```

- `<router-link ...> ... </router-link>` : 일반 HTML의 `<a>` 태그(클릭하면 다른 페이지로 이동하는 링크)와 비슷한데, Vue Router(페이지 이동을 관리하는 도구)가 제공하는 특수한 링크 태그다.
- `to="/chapters"` : 이 버튼을 클릭하면 이동할 주소다. 여기 적힌 `/chapters`는 **바꾸지 않았다** — 이번 작업은 "주소"가 아니라 "화면에 보이는 글자"만 바꾸는 작업이었기 때문이다.
- `과목 선택` : 버튼에 실제로 표시되는 글자. 원래는 `챕터 선택`이라고 쓰여 있었는데 이번에 `과목 선택`으로 바뀌었다.

### 6. 전문 용어 정리

- **Vue(뷰)** : 이 프로젝트의 화면(프론트엔드)을 만들 때 쓰는 자바스크립트 도구(프레임워크). 데이터가 바뀌면 화면도 자동으로 다시 그려주는 게 특징이다.
- **컴포넌트(component)** : 화면의 한 조각을 담당하는 부품 파일. 예를 들어 `AppHeader.vue`는 "헤더(상단 메뉴 바)"라는 화면 조각을 담당하는 컴포넌트다. 레고 블록 하나하나라고 생각하면 된다.
- **템플릿(template)** : Vue 컴포넌트 파일 안에서 `<template>...</template>` 사이에 적는 부분으로, 실제 화면에 어떤 모양(HTML 구조)이 그려질지를 정의한다.
- **라우트(route) / 라우팅(routing)** : "이 주소(예: `/chapters`)로 오면 어떤 화면을 보여줄지" 미리 정해둔 규칙. 이번 작업에서는 이 규칙을 건드리지 않았다.
- **하드코딩(hard-coding)** : 값을 서버에서 받아오거나 계산하지 않고, 코드 안에 직접 고정된 값(예: "학습 대시보드"라는 글자)으로 박아 넣는 것. 이번에 바뀐 문구들이 전부 하드코딩된 텍스트였다.
- **git diff(깃 디프)** : 파일이 수정되기 전과 후를 비교해서 "어느 줄이 지워지고 어느 줄이 추가됐는지" 보여주는 명령어. 이 문서의 표에 나온 변경 내용도 git diff로 확인한 것이다.
- **커밋(commit)** : 변경한 내용을 하나의 "저장 지점"으로 기록하는 것. 이번 1단계 작업은 `60a0ac3`이라는 커밋 번호로 저장되어 있다(커밋 메시지: `fix(ui): unify terminology 챕터/강의실 → 과목/대시보드`).

## 2단계: 하드코딩 색상 → 디자인 토큰 교체 (`--sq-color-terminal-fg`)

### 1. 왜 했나

이 프로젝트의 규칙(CLAUDE.md)에는 "**모든 색은 `design-tokens.css`의 `var(--sq-*)` 토큰으로만 사용하고, 하드코딩된 hex 값(예: `#3b5bff`)은 절대 금지**"라는 조항이 있다. 이유는 나중에 사이트 전체 색상 테마를 바꾸고 싶을 때(예: 다크모드 추가, 브랜드 색 교체), 색이 한 파일(`design-tokens.css`)에만 정의돼 있어야 그 파일 하나만 고쳐서 전체 사이트에 한 번에 반영할 수 있기 때문이다.

그런데 Command Injection 실습 완료 여부를 점검하던 중, 실습 결과가 나오는 화면(검정 배경에 흰 글씨로 나오는, 마치 터미널 창 같은 상자)의 코드를 확인해보니 `color: #f5f5f5;`처럼 색상 값이 **코드 안에 직접 숫자·문자로 박혀 있는 것(하드코딩)**을 발견했다. 이건 위 규칙을 어긴 상태였다.

**안 하면 생기는 문제**
- 나중에 팀에서 "터미널 글자색을 좀 더 밝게 바꾸자"고 정해서 `design-tokens.css`의 색을 바꿔도, 이 한 줄(`#f5f5f5`)은 그 파일과 아무 연결이 없어서 **혼자 안 바뀌는 버그**가 생긴다.
- 코드 리뷰나 규칙 점검(grep 검사)에서 "하드코딩 금지 규칙 위반"으로 계속 걸린다.
- 어떤 색이 어디에 쓰이는지 한눈에 관리가 안 된다(디자인 토큰 파일 하나만 보면 전체 색상 체계를 알 수 있어야 하는데, 예외가 생기면 그게 깨진다).

### 2. 무엇을 바꿨나

| 파일 | 역할 | 바뀐 내용 |
|---|---|---|
| `frontend/src/assets/design-tokens.css` | 프로젝트 전체에서 쓰는 색상·간격 값을 한곳에 모아둔 "색상표" 파일 | `--sq-color-terminal-fg: #F5F5F5;`라는 새 토큰(이름표)을 추가 |
| `frontend/src/views/ChapterDetailView.vue` | 실습 문제 풀이 화면(입력→실행→결과 출력) | 결과 출력 상자의 글자색을 `#f5f5f5`(직접 값)에서 `var(--sq-color-terminal-fg)`(토큰 참조)로 교체 |

### 3. 작업 흐름

이 단계도 1단계와 마찬가지로 **API·서버·DB는 관여하지 않는다.** CSS(화면 디자인을 정의하는 언어) 파일 안에서만 일어나는 변경이다.

```
브라우저가 ChapterDetailView.vue의 화면을 그릴 때
  → "글자색은 var(--sq-color-terminal-fg)로 해라"라는 지시를 읽는다
  → 브라우저가 design-tokens.css에 정의된 :root { --sq-color-terminal-fg: #F5F5F5; }를 찾아본다
  → 거기 적힌 실제 값(#F5F5F5, 아주 밝은 회백색)을 가져와서 글자에 적용한다
```

이전에는 `#f5f5f5`라는 값이 `ChapterDetailView.vue` 파일 안에 직접 박혀 있어서, 색상표(`design-tokens.css`)를 아무리 찾아봐도 이 값의 존재를 알 수 없었다. 지금은 "이 값의 이름은 `--sq-color-terminal-fg`이고, 실습 터미널 출력 텍스트에 쓰인다"라고 색상표에 등록되어 있어서 누구나 찾아볼 수 있다.

### 4. 동작 원리 (비유)

**페인트 회사의 "표준 색상표"**에 비유할 수 있다.

페인트공(개발자)이 방마다(컴포넌트마다) "음... 이 정도 흰색이면 되겠지" 하고 눈대중으로 페인트를 섞어서(`#f5f5f5`를 직접 씀) 칠하면, 방마다 미묘하게 색이 다를 수 있고, 나중에 "전체적으로 좀 더 밝게 바꾸자"고 하면 **방을 하나하나 다시 찾아다니며 다시 칠해야** 한다.

대신 페인트 회사가 "표준 색상표 27번 = 이 흰색"이라고 미리 정해두고(디자인 토큰 = `--sq-color-terminal-fg`), 모든 방에 "27번 색으로 칠해주세요"라고 요청하면(`var(--sq-color-terminal-fg)`), 나중에 색상표 책자에서 **27번 정의 딱 한 줄만 바꾸면 그 색을 쓰는 모든 방이 한 번에 바뀐다.**

### 5. 코드 해설

**① `design-tokens.css`에 새 토큰 추가**
```css
:root {
  ...
  --sq-color-terminal-fg: #F5F5F5; /* 실습 터미널 출력 텍스트 */
  ...
}
```
- `:root` : "이 문서(웹페이지) 전체에서 공통으로 쓸 값들을 여기 정의한다"는 CSS 문법. 마치 회사 전체가 보는 "공용 색상표 책자"를 펼쳐둔 것과 같다.
- `--sq-color-terminal-fg` : 새로 만든 변수(토큰)의 이름. 앞에 `--`를 붙이는 건 "이건 CSS 커스텀 변수(사용자 정의 값)다"라는 표시다. `sq-`는 이 프로젝트(SecuQuest)의 모든 색상 변수에 붙이는 접두사, `color-terminal-fg`는 "터미널(실습 결과창)의 전경색(글자색, foreground)"라는 뜻이다.
- `#F5F5F5` : 실제 색상 값. 16진수(hex) 색상 코드로, 아주 밝은 회백색을 뜻한다.
- `/* 실습 터미널 출력 텍스트 */` : 이 토큰이 어디에 쓰이는 색인지 설명하는 한글 주석.

**② `ChapterDetailView.vue`에서 이 토큰을 사용**
```css
.sq-practice__output {
  ...
  color: var(--sq-color-terminal-fg);
  ...
}
```
- `.sq-practice__output` : 실습 결과가 출력되는 상자(터미널처럼 생긴 부분)를 가리키는 CSS 선택자(이름표).
- `color: ...` : 이 상자 안 글자의 색을 정하는 CSS 속성.
- `var(--sq-color-terminal-fg)` : "`--sq-color-terminal-fg`라는 이름의 변수 값을 여기서 가져와 써라"는 뜻. `var()`는 "변수(variable)를 꺼내 쓴다"는 CSS 함수다. 이 줄이 실행되면 결국 `color: #F5F5F5;`와 똑같이 동작하지만, **값이 어디서 왔는지(design-tokens.css) 추적 가능하다**는 차이가 있다.

### 6. 전문 용어 정리

- **CSS(씨에스에스)** : 웹페이지의 색깔, 글자 크기, 배치 등 "생김새"를 정의하는 언어. HTML이 "무엇을 보여줄지" 정한다면, CSS는 "어떻게 보이게 할지" 정한다.
- **디자인 토큰(design token)** : 색상·간격·글자 크기 같은 디자인 값에 이름을 붙여서 한곳에 모아둔 것. "27번 색상"처럼, 값 자체보다 "이름"으로 관리해서 나중에 값만 바꾸면 전체에 반영되게 하는 방식이다.
- **CSS 커스텀 프로퍼티(custom property) / CSS 변수** : `--이름: 값;` 형태로 정의하고 `var(--이름)`으로 꺼내 쓰는 CSS 기능. 디자인 토큰을 실제로 구현하는 방법 중 하나다.
- **`:root`** : 문서 전체에서 통하는 CSS 변수를 정의할 때 쓰는 선택자. "이 웹페이지 전체의 최상위"라는 뜻이다.
- **hex 색상 코드(헥스 코드)** : `#F5F5F5`처럼 `#` 뒤에 16진수 6자리로 색을 표현하는 방식. 앞 2자리는 빨강, 중간 2자리는 초록, 마지막 2자리는 파랑의 양을 나타낸다.
- **하드코딩(1단계에서도 나온 용어)** : 여기서는 "색상 값을 변수 없이 코드에 직접 써넣는 것"을 가리킨다.
- **grep(그렙)** : 여러 파일 안에서 특정 글자(패턴)를 찾아주는 명령어. 이번에 `#f5f5f5` 같은 하드코딩된 색상이 남아있는지 찾을 때 이 방법을 썼다.

### 7. 확인 질문

1. `color: var(--sq-color-terminal-fg);`라는 코드를 읽을 때, 브라우저는 실제 색상 값(`#F5F5F5`)을 **어느 파일**에서 찾아오는가?
2. 만약 나중에 팀에서 "터미널 글자색을 `#FFFFFF`(완전한 흰색)로 바꾸자"고 결정했다면, `design-tokens.css`와 `ChapterDetailView.vue` 중 **어느 파일**을 고쳐야 할까?

## 3단계: XSS 실습 보류 + 계획 문서 저장 (Phase 0)

### 1. 왜 했나

이 프로젝트는 6개 취약점(Command Injection, XSS 3종, SQL Injection, SQL Injection Blind, File Upload, CSRF)을 순서대로 만들어야 한다. 오늘은 그중 **Command Injection의 미션·퀴즈 기능**을 완성하는 게 목표였는데, 그 직전에 XSS(Reflected/DOM/Stored) 실습을 어떻게 만들지 미리 조사하고 설계 방향을 정해둔 게 있었다.

문제는, XSS는 Command Injection과 근본적으로 성격이 다르다. Command Injection은 "서버 컴퓨터"에서 명령이 실행되는 취약점이고, XSS는 "사용자의 웹 브라우저"에서 스크립트가 실행되는 취약점이다. 그래서 Command Injection에서 쓰던 방식(서버가 격리된 상자 안에서 명령을 대신 실행해주는 방식)을 XSS에 그대로 쓸 수 없고, **완전히 다른 안전장치(격리된 iframe)**가 필요하다는 게 조사 결과 드러났다.

이렇게 조사한 내용과 "어떻게 만들 것인가"에 대한 결론을 **글로만 이야기하고 끝내면, 나중에 다시 XSS를 만들 때 처음부터 똑같은 조사를 반복해야 한다.** 그래서 오늘은 실제 코드는 하나도 만들지 않고, **"나중에 이 문서를 보고 그대로 시작하면 된다"는 설계 문서만 저장**해두기로 했다.

**안 하면 생기는 문제**
- 다음에 XSS를 만들 때 "왜 iframe을 써야 하는지", "왜 3개 과목으로 나눠야 하는지" 같은 이유를 처음부터 다시 조사해야 한다(시간 낭비).
- 대화(채팅)로만 나눈 결론은 시간이 지나면 잊히거나, 다른 사람(팀원)에게 전달이 안 된다.
- 오늘의 핵심 목표(Command Injection 미션·퀴즈)에 집중하지 못하고 XSS까지 동시에 진행하면 범위가 너무 커져서 실수하기 쉽다.

### 2. 무엇을 바꿨나

이 단계는 **코드(프로그램이 실제로 동작하는 파일)를 하나도 바꾸지 않았다.** 오직 "설계 메모"에 해당하는 문서 파일 1개만 새로 만들었다.

| 파일 | 역할 | 바뀐 내용 |
|---|---|---|
| `docs/plans/xss-practice-plan.md` | XSS 실습 3종(Reflected/DOM/Stored)을 나중에 어떻게 만들지 정리한 설계 문서 | 신규 작성. 코드는 없고, "왜 이렇게 만들어야 하는지"와 "앞으로 만들 파일 목록", "미리 그려본 코드 변경 예시(diff)"가 담겨 있음 |

이 문서 안에는 실제로 아직 존재하지 않는 파일 이름들(예: `xss_reflected.py`)과, "이렇게 고칠 예정이다"라는 **미래의 코드 변경 미리보기(diff 형태)**가 적혀 있다. 하지만 이건 진짜로 파일을 만든 게 아니라 **"나중에 이렇게 만들 것이다"라고 적어둔 메모**라는 점이 중요하다.

### 3. 작업 흐름

이 단계도 화면·API·서버 동작과는 무관하다. "문서를 쓰는 것" 자체가 작업이었다.

```
[조사]                    [정리]                        [저장]
기존 Command Injection  →  "XSS는 브라우저에서 실행되니  →  docs/plans/xss-practice-plan.md
코드 구조를 살펴본다        iframe으로 격리해야 한다" 등      라는 파일에 마크다운(글) 형태로
                           결론을 정리한다                  저장한다(git 커밋까지 완료)
```

사용자가 웹사이트를 쓸 때 이 문서가 화면에 보이거나 동작에 영향을 주는 것은 전혀 없다. **개발자(우리)가 나중에 참고할 "설계도"**일 뿐이다.

### 4. 동작 원리 (비유)

**집을 짓기 전에 미리 그려두는 "설계도"**에 비유할 수 있다.

건축가가 2층집을 짓다가, "3층을 어떻게 올릴지"에 대한 아이디어가 떠올랐다고 해보자. 지금 당장 3층 공사를 시작하면 2층 공사에 집중을 못 하니, 일단 "3층은 이런 구조로, 이런 자재로 지으면 된다"는 **설계도만 그려서 서랍에 넣어두는 것**과 같다. 나중에 3층을 지을 사람(같은 사람이든 다른 사람이든)은 이 설계도를 펼쳐보기만 하면 되고, 처음부터 다시 고민할 필요가 없다.

### 5. 코드 해설

이 단계는 실제 프로그램 코드를 바꾸지 않았지만, 설계 문서 안에는 "나중에 이렇게 바뀔 것"이라고 미리 적어둔 코드 예시가 있다. 그중 하나를 가져와서 설명한다. (`docs/plans/xss-practice-plan.md`의 E번 항목)

```diff
--- a/backend/app/practice_builders/__init__.py
+++ b/backend/app/practice_builders/__init__.py
 from .command_injection import CommandInjectionBuilder
+from .xss_reflected import XssReflectedBuilder
+from .xss_dom import XssDomBuilder
+from .xss_stored import XssStoredBuilder

 PRACTICE_BUILDERS = {
     "command-injection": CommandInjectionBuilder(),
+    "xss-reflected": XssReflectedBuilder(),
+    "xss-dom": XssDomBuilder(),
+    "xss-stored": XssStoredBuilder(),
 }
```

- 이 블록은 **"diff(디프)" 형식**으로 쓰여 있다. 줄 앞에 `+`가 붙으면 "이 줄을 새로 추가할 예정", `-`가 붙으면 "이 줄을 지울 예정", 아무 기호가 없으면 "원래 있던 줄, 안 바뀜"이라는 뜻이다.
- `from .command_injection import CommandInjectionBuilder` : "`command_injection`이라는 파일 안에서 `CommandInjectionBuilder`라는 코드 조각(클래스)을 가져와 쓰겠다"는 파이썬(백엔드 언어) 문법. 이건 원래 있던 줄이라 기호가 없다.
- `+from .xss_reflected import XssReflectedBuilder` (와 그 아래 2줄) : 앞으로 만들 XSS용 파일 3개(`xss_reflected.py`, `xss_dom.py`, `xss_stored.py`)에서 각각의 "실습 채점 담당자" 역할을 하는 코드 조각을 가져오겠다는 뜻. `+`가 붙어 있으니 "아직 실제로 추가되지 않았고, 앞으로 추가할 예정"이라는 표시다.
- `PRACTICE_BUILDERS = { ... }` : "이 과목(슬러그)의 실습은 이 담당자가 채점한다"는 연결 목록(딕셔너리, 일종의 전화번호부)이다. `"command-injection": CommandInjectionBuilder(),`처럼 "과목 이름": 담당자 형태로 등록되어 있다.
- `+    "xss-reflected": XssReflectedBuilder(),` (등 3줄) : XSS 3개 과목도 이 전화번호부에 새로 등록하겠다는 계획. 이렇게만 등록하면, 이미 만들어져 있는 공용 채점 API(`/practice/run` 등)가 자동으로 XSS 채점도 처리할 수 있게 된다 — 그래서 "API 코드 자체는 안 바꿔도 된다"는 게 이 설계의 핵심 장점이다.

### 6. 전문 용어 정리

- **설계 문서 / 계획 문서(plan document)** : 코드를 쓰기 전에 "무엇을, 왜, 어떻게 만들지"를 글로 정리해둔 문서. 이 프로젝트에서는 `docs/plans/` 폴더에 모아둔다.
- **마크다운(Markdown, `.md`)** : `#`, `-`, `` ` `` 같은 간단한 기호로 제목·목록·강조를 표현하는 글쓰기 문법. 이 문서(작업이해.md)도 마크다운으로 쓰여 있다.
- **iframe(아이프레임)** : 웹페이지 안에 "또 다른 독립된 작은 웹페이지"를 끼워 넣는 HTML 기능. 안쪽 페이지는 바깥 페이지와 분리되어 있어서, 안에서 문제가 생겨도 바깥에 영향을 덜 준다 — 그래서 "격리(고립)"라는 표현을 쓴다.
- **클래스(class) / 빌더(Builder)** : 파이썬 같은 프로그래밍 언어에서 "특정 역할을 하는 코드 덩어리"를 만드는 방법 중 하나. 여기서는 "이 과목의 실습을 채점하는 담당자" 역할을 하는 코드 덩어리를 `~Builder`라고 이름 붙였다.
- **딕셔너리(dictionary)** : "이름표: 값" 쌍을 여러 개 모아둔 자료 구조. `PRACTICE_BUILDERS`는 "과목 이름: 채점 담당자" 쌍을 모아둔 딕셔너리다. 전화번호부(이름: 전화번호)를 떠올리면 된다.
- **flag(플래그) 토큰** : 보안 실습에서 "공격이 성공했다"는 것을 증명하기 위해 서버가 몰래 심어두는 임의의 문자열(비밀 값). 이번 XSS 설계에서는 이 값을 사용자가 정말로 스크립트를 실행시켰을 때만 꺼낼 수 있게 해서, 성공 여부를 서버가 확인하는 데 쓸 예정이다.
- **세션(session)** : 로그인한 사용자를 서버가 "누구인지, 지금 무엇을 하고 있는지" 잠깐 기억해두는 임시 저장 공간. 이번 결정에서는 XSS의 flag 값이나 임시 게시물을 **새 데이터베이스 표(테이블)를 만들지 않고** 이 세션 안에만 저장하기로 했다.

1. 이번 3단계에서 실제로 동작하는 프로그램 코드가 바뀌었을까, 아니면 "앞으로 어떻게 만들지 적어둔 문서"만 새로 생겼을까?
2. Command Injection은 "서버 컴퓨터"에서 명령이 실행되는 취약점인데, XSS는 어디에서 스크립트가 실행되는 취약점이라서 서로 다른 안전장치(iframe)가 필요하다고 했을까?

## A. 화면: 미션 카드 + 퀴즈 모달

### 1. 왜 했나

기존 "미션" 탭은 개념 학습/실습 성공/방어 퀴즈 3개 항목이 표 형태 한 줄씩으로만 나열되어 있었고, 방어 퀴즈도 문제 1개만 풀면 끝이었다. 참고 캡처(다른 교육 플랫폼의 미션 카드 화면)를 기준으로, 각 항목을 카드 형태(제목·상태·설명·제출 현황)로 보기 좋게 재구성하고, 방어 퀴즈는 50문항짜리 퀴즈 세트로 확장했다. 문제 1개만 맞히면 통과하던 것보다, 50문항 중 70% 이상을 맞혀야 통과하게 만들어서 실제로 개념을 이해했는지 더 정확히 확인할 수 있게 했다.

### 2. 무엇을 바꿨나

| 파일 | 역할 | 바뀐 내용 |
|---|---|---|
| `frontend/src/views/CourseDetailView.vue` | 과목 상세 화면(실습/미션/과목 정보 탭) | 미션 탭을 표 → 카드 목록으로 재구성(회차 뱃지, 완료·미완료 뱃지, 설명, "내 제출물" 박스, 미완료 항목엔 "이동" 버튼). 하단에 "퀴즈 풀기" 버튼 1개 추가 |
| `frontend/src/components/practice/QuizSetModal.vue` | 퀴즈 풀기 버튼을 누르면 뜨는 모달(팝업) 창 | 신규 작성. 문항을 하나씩 보여주고, 보기를 클릭하면 즉시 정답 여부를 서버에 물어봐서 화면에 초록(정답)/빨강(오답)으로 강조 표시한 뒤 1.5초 후 자동으로 다음 문항으로 넘어감. 이전 버튼 없음. 마지막 문항까지 끝나면 자동으로 채점 결과 화면으로 전환 |

### 3. 작업 흐름

```
사용자가 "퀴즈 풀기" 버튼 클릭
  → QuizSetModal.vue가 화면에 뜨면서 서버에 "문제 목록 주세요" 요청(GET)
  → 사용자가 보기 하나를 클릭
  → 그 즉시 서버에 "이 문항 이 보기 맞아요?" 요청(POST) → 서버가 정답 여부 응답
  → 화면이 정답/오답을 색으로 강조 → 1.5초 대기 → 다음 문항으로 이동
  → 마지막 문항까지 반복 후 서버에 "채점해주세요" 요청(POST)
  → 서버가 점수를 계산해 70% 이상이면 "방어 퀴즈 완료" 처리 + 보상 지급
  → 화면에 최종 점수·통과 여부 표시
```

### 4. 핵심 코드 해설

```js
const { data } = await client.post(`/courses/${props.slug}/quiz-set/answer`, {
  attemptId: attemptId.value,
  questionId: currentQuestion.value.id,
  choice: index,
});
selectedChoice.value = index;        // 사용자가 고른 보기 번호 기억
revealedAnswer.value = data.answer;  // 서버가 알려준 정답 번호 기억
revealTimer = setTimeout(advance, REVEAL_DELAY_MS); // 1.5초 뒤 advance() 실행 예약
```
- `client.post(...)` : 서버에게 "이거 채점해줘"라고 데이터를 보내는 요청. `await`는 "서버 응답이 올 때까지 여기서 기다린다"는 뜻.
- `attemptId` : "이번 퀴즈 시도" 하나를 구분하는 임시 번호표(사용자가 퀴즈를 다시 풀면 새 번호를 받는다).
- `data.answer` : 서버가 돌려준 "진짜 정답이 몇 번인지"에 대한 값. 이 값을 받아서 화면에 초록색으로 표시해준다.
- `setTimeout(advance, 1500)` : "1500밀리초(1.5초) 뒤에 `advance`라는 함수를 실행해라"는 자바스크립트 문법. 사람이 정답/오답을 눈으로 확인할 시간을 준 뒤 자동으로 다음 문제로 넘어가게 하는 장치.

### 5. 용어 정리

- **모달(modal)** : 화면 전체를 가리며 팝업처럼 뜨는 창. 닫기 전까지 뒤 화면을 조작할 수 없다.
- **Teleport** : Vue에서 컴포넌트를 원래 위치가 아니라 화면 최상단(`<body>`)에 직접 그리게 해주는 기능. 모달이 다른 요소에 가려지지 않게 하기 위해 쓴다.
- **`attemptId`(시도 번호)** : 퀴즈를 한 번 풀 때마다 서버가 새로 발급하는 임시 식별 번호.
- **`setTimeout`** : "지정한 시간 뒤에 특정 동작을 실행해라"는 자바스크립트 기본 기능.
- **뱃지(badge)** : 상태(완료/미완료 등)를 작은 알약 모양으로 표시하는 UI 부품.

## B. 서버: 50문항 퀴즈 은행 + 퀴즈 API 3개

### 1. 왜 했나

퀴즈 화면(모달)이 문제를 보여주려면, 그 문제들이 어딘가에 저장되어 있어야 한다. 그래서 Command Injection 방어 관련 문제 50개(문제·보기 4개·정답·해설)를 미리 만들어 서버에 저장해두고, 화면(프론트엔드)이 이 문제를 가져오고·답을 제출하고·채점받을 수 있는 통로(API) 3개를 새로 만들었다. 또한 "정답이 무엇인지"는 절대 화면에 미리 알려주면 안 되므로(치팅 방지), 이 부분을 서버에서만 관리하도록 설계했다.

### 2. 무엇을 바꿨나

| 파일 | 역할 | 바뀐 내용 |
|---|---|---|
| `backend/app/quiz_bank/command_injection.py` | 50문항의 실제 내용(문제·보기·정답·해설)을 담은 데이터 파일 | 신규 작성. 정답 번호가 1~4번에 골고루 분산되도록 검수 후 반영 |
| `backend/app/quiz_bank/__init__.py` | "어떤 과목이 어떤 문제 은행을 쓰는지" 연결해주는 파일 | 신규 작성 |
| `backend/app/courses.py` | 과목 관련 API(서버 창구)를 모아둔 파일 | 문제 목록 요청(`GET quiz-set`), 문항 1개 답 제출(`POST quiz-set/answer`), 최종 채점(`POST quiz-set/submit`) API 3개 신규 추가 |

### 3. 작업 흐름

```
[문제 은행 준비]                    [사용자가 퀴즈를 풀 때]
50문항을 command_injection.py   →  GET quiz-set: 서버가 "정답 빼고" 문제만 화면에 전달
파일에 저장                         POST .../answer: 문항 1개 답을 보내면
                                     서버가 세션(임시 기억 공간)에 답을 저장하고
                                     맞았는지/틀렸는지만 알려줌
                                     POST .../submit: 50문항 다 풀리면
                                     서버가 세션에 저장된 답을 모아 점수 계산
                                     → 70% 이상이면 "방어 퀴즈 완료" 기록 + 보상 지급
```

### 4. 핵심 코드 해설

```python
attempt = _load_attempt(course.slug, attempt_id)
if attempt is None:
    return jsonify(message="진행 중인 퀴즈가 없습니다."), 404

if question_id in attempt["answers"]:
    return jsonify(message="이미 응답한 문항입니다."), 409

attempt["answers"][question_id] = choice   # 이번 답을 세션에 기록
session.modified = True                    # "세션 내용이 바뀌었다"고 서버에 알림
return jsonify(correct=choice == question["answer"], answer=question["answer"])
```
- `_load_attempt(...)` : 지금 이 "시도 번호"가 진짜로 유효한지 확인하는 함수. 없으면 `404`(존재하지 않음) 응답.
- `if question_id in attempt["answers"]:` : 이 문항에 이미 답했는지 확인. 이미 답했다면 `409`(이미 처리된 요청) 응답으로 중복 제출을 막는다.
- `attempt["answers"][question_id] = choice` : 사용자가 고른 답을 세션(서버가 임시로 기억하는 공간)에 저장.
- `correct=choice == question["answer"]` : 사용자가 고른 답(`choice`)과 진짜 정답(`question["answer"]`)이 같은지 비교해서 `True`/`False`로 응답. 해설은 여기서는 안 알려주고, 최종 제출(`submit`) 때만 알려준다.

### 5. 용어 정리

- **API(에이피아이)** : 화면(프론트엔드)과 서버(백엔드)가 데이터를 주고받기 위해 미리 약속해둔 "요청 창구". 예: `GET quiz-set`은 "문제 목록 주세요"라는 약속된 요청 방식이다.
- **GET / POST** : API 요청의 종류. `GET`은 "데이터를 조회만 할 때", `POST`는 "서버에 새로운 데이터를 보내거나 처리를 요청할 때" 쓴다.
- **세션(session)** : 로그인한 사용자별로 서버가 임시로 기억해두는 저장 공간. 이번엔 "지금 몇 번 문제까지 풀었는지, 어떤 답을 골랐는지"를 여기에 저장했다.
- **404 / 409** : 서버가 요청을 처리하지 못했을 때 알려주는 상태 코드. `404`는 "요청한 대상이 없음", `409`는 "이미 처리돼서 충돌남"이라는 뜻.
- **문제 은행(quiz bank)** : 문제·보기·정답·해설을 미리 모아둔 데이터 묶음.

## C. 마무리: demo1 계정 + API 테스트 + 커밋 기록

### 1. 왜 했나

기능을 다 만들었어도 "진짜로 잘 동작하는지" 확인하지 않으면 안심할 수 없다. 그래서 세 가지를 했다: ① 발표·시연할 때 쓸 전용 테스트 계정(`demo1`)을 만들고, ② 새로 만든 퀴즈 API가 의도대로 동작하는지(정답 안 새는지, 중복 제출 막는지, 통과 시 보상 주는지, 재통과해도 중복 지급 안 되는지) 직접 확인했고, ③ 오늘 작업한 내용을 git(버전 관리 도구)에 단계별로 기록해서 나중에 되돌아볼 수 있게 했다.

### 2. 무엇을 바꿨나

| 파일 | 역할 | 바뀐 내용 |
|---|---|---|
| `backend/seed.py` | 서버에 테스트용 초기 데이터(계정 등)를 넣어주는 스크립트 | `demo1` 계정 추가(학생 권한, command-injection 수강 신청만 되어 있고 진도는 0인 깨끗한 상태 — 시연용). **주의: 시드 스크립트에 생성 로직만 추가한 상태이며, 실제로 브라우저에서 demo1로 로그인해 화면이 정상 뜨는지는 아직 확인하지 않았다.** |
| (테스트 스크립트, 저장소 코드 아님) | API가 실제로 잘 작동하는지 확인하는 curl(명령줄 도구) 스크립트 | GET/POST 요청을 순서대로 보내서 응답을 확인 |
| git 커밋 5개 | 오늘 변경 사항을 의미 단위로 나눠 저장 | 아래 6번 참고 |

### 3. 작업 흐름

```
seed.py 실행 → demo1 계정과 command-injection 수강 신청 데이터가 DB에 생성됨
      ↓
테스트 스크립트 실행 → student1로 로그인 → 퀴즈 API 3개를 순서대로 호출
      ↓
응답 확인 → "정답이 화면에 안 새는지" / "중복 제출 막히는지" / "70% 넘으면 완료되는지" /
            "다시 풀어도 보상이 중복 지급 안 되는지" 눈으로 확인
      ↓
문제 없으면 git commit → 나중에 "언제 무엇을 왜 바꿨는지" 기록으로 남음
```

### 4. 핵심 코드 해설

```python
def _seed_enrollment_only(user, course):
    """수강 신청만 생성(과제 진도·출석 데이터 없음)."""
    enrollment = Enrollment.query.filter_by(user_id=user.id, course_id=course.id).first()
    if enrollment:
        return                       # 이미 수강 중이면 아무것도 안 함(중복 방지)
    db.session.add(Enrollment(user_id=user.id, course_id=course.id))
    db.session.commit()              # 실제로 DB에 저장
```
- `Enrollment.query.filter_by(...)` : "이 사람이 이 과목을 이미 수강 신청했는지" DB에서 찾아보는 코드.
- `if enrollment: return` : 이미 있으면 아무 것도 안 하고 함수를 끝낸다 — `seed.py`를 여러 번 실행해도 계정이 중복 생성되지 않게 막는 안전장치.
- `db.session.add(...)` / `db.session.commit()` : 새 데이터를 "이제 저장할 준비를 해라"(`add`) → "진짜로 데이터베이스에 확정 저장해라"(`commit`) 순서로 실행하는 표준 패턴.

### 5. 용어 정리

- **seed(시드) / seed.py** : 프로그램을 테스트하기 쉽게, 미리 정해둔 계정·데이터를 DB에 심어주는 스크립트. "씨앗을 심는다"는 의미에서 따온 이름이다.
- **curl(컬)** : 터미널(명령줄)에서 API에 직접 요청을 보내고 응답을 확인할 수 있는 도구. 화면(브라우저) 없이도 서버가 잘 동작하는지 테스트할 때 쓴다.
- **DB(데이터베이스)** : 계정, 수강 신청 내역, 진도 같은 정보를 실제로 저장해두는 저장소.
- **커밋(commit)** : 변경 내용을 의미 있는 단위로 묶어서 "저장 지점"으로 기록하는 git 명령. 오늘 작업은 아래 5개 커밋으로 기록되어 있다(파일 목록은 `git show --stat` 기준 실제 값).
  - `60a0ac3` 용어 통일 — 화면 파일 6개(AppHeader.vue, DashboardView.vue, AdminView.vue, CourseDetailView.vue, StudentsOverview.vue, VulnerabilityPage.vue)
  - `77ee7de` 백엔드 4개 — `courses.py`, `quiz_bank/__init__.py`, `quiz_bank/command_injection.py`, `seed.py`
  - `17fdfcd` `CourseDetailView.vue` 1개(미션 카드 UI 재구성)
  - `884e637` 3개 — `QuizSetModal.vue`, `docs/plans/ci-quiz-bank-draft.md`, `docs/plans/xss-practice-plan.md`
  - `9e3dbaa` 토큰 2개 — `design-tokens.css`, `ChapterDetailView.vue`
- **회귀 확인(regression check)** : 새 기능을 추가한 뒤 "원래 잘 되던 기능이 혹시 고장나지 않았는지" 다시 확인하는 것. 이번엔 재통과 시 보상 중복 지급이 없는지를 이 관점에서 확인했다.
