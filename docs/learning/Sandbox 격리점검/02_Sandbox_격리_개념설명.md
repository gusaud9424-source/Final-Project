# 02. Sandbox 격리 개념 설명 (설정 하나하나의 의미와 남은 위험)

## 1. 요약

- SecuQuest에는 컨테이너(작은 독립 컴퓨터)가 여러 개 있다: **Nginx · Flask(backend) · MariaDB · Redis · sandbox**.
- 네트워크·쓰기·권한을 막은 것은 **sandbox 하나뿐**이다. 서비스 서버(Flask)와 회원 DB(MariaDB)는 평소대로 통신한다.
- sandbox는 **공격 실습 명령을 대신 실행해 주는 전용 방**이다. 학생의 공격이 "진짜로 성공"하는 곳이 여기다.
- 그래서 이 방에서 무슨 일이 일어나도 밖(Flask·MariaDB)으로 번지지 않게 문을 모두 잠갔다. 이것이 "격리"다.
- 격리 점검은 **문이 정말 잠겨 있는지 직접 손잡이를 돌려 본 것**이다.
- 단, 격리는 "실습 공격의 피해를 가두는 장치"일 뿐이다. 서비스 자체는 CSRF 토큰 · 요청 횟수 제한 · bcrypt 같은 **표준 보안**으로 따로 지킨다.

## 2. 개념 설명 (비유)

### 2-1. 전체 그림: 회사 건물

```
            ┌──────────────── SecuQuest 건물 ────────────────┐
 학생 ───▶ │ [안내데스크]  →  [사무실]  ↔  [금고]             │
 (브라우저)  │   Nginx         Flask        MariaDB(회원 DB)   │
            │                   │                            │
            │                   │ 우편함(소켓 파일)            │
            │                   ▼                            │
            │             [방폭 실험실] sandbox               │
            │   창문 없음 · 벽 낙서 금지 · 열쇠 없음 · 재료 제한   │
            └───────────────────────────────────────────────┘
```

- **안내데스크(Nginx)**: 학생 요청을 받아 사무실로 전달.
- **사무실(Flask)**: 로그인, 진도, 보상 등 실제 업무 처리.
- **금고(MariaDB)**: 회원 정보, 비밀번호 해시, 진도·보상 기록 보관.
- **방폭 실험실(sandbox)**: 위험한 실험(공격 실습)만 하는 방.

사무실 직원은 실험이 필요하면 **우편함에 쪽지(실행할 명령)를 넣고**, 실험실은 결과만 쪽지로 돌려준다. 실험실 사람은 사무실이나 금고로 걸어갈 **통로가 아예 없다.**

### 2-2. "공격이 성공해도 피해가 컨테이너 안에 머문다"의 뜻

학생이 Command Injection 실습에서 공격에 성공하면 **서버의 명령을 마음대로 실행**할 수 있게 된다. 이 일이 사무실(Flask)에서 일어나면 금고(DB)를 열 수도 있다. 하지만 SecuQuest에서는 그 명령이 **실험실 안에서만** 실행된다.

- 실험실에서 금고로 가는 길(네트워크)이 없다 → 회원 DB에 접속할 수 없다.
- 실험실 벽에 무언가를 새길 수 없다(쓰기 금지) → 악성 파일을 심어 둘 수 없다.
- 실험실 사람에게 열쇠가 없다(권한 없음) → 설정을 바꾸거나 더 높은 권한을 얻을 수 없다.

즉 "공격 성공"이 일어나는 장소 자체가 **아무것도 할 수 없는 빈 방**이라서, 성공해도 서버와 DB에는 닿지 못한다.

## 3. 용어 설명

| 용어 | 쉬운 뜻 |
|---|---|
| 컨테이너 | 한 컴퓨터 안에서 서로 분리되어 돌아가는 작은 독립 컴퓨터. Docker로 만든다 |
| sandbox(샌드박스) | 위험한 코드를 안전하게 실행하려고 따로 떼어 둔 공간. "모래 놀이터"처럼 밖을 더럽히지 않는다 |
| 격리 | 서로 영향을 주지 못하게 떼어 놓는 것 |
| 네트워크 | 컴퓨터끼리 주고받는 통신 길. 컨테이너끼리도 네트워크로 대화한다 |
| 파일 시스템 | 파일과 폴더가 저장되는 공간 |
| root(루트) | 리눅스의 최고 관리자 계정. 무엇이든 할 수 있다 |
| 권한(capability) | 관리자 능력을 잘게 나눈 조각 (네트워크 설정, 파일 소유자 변경 등) |
| 소켓 파일 | 같은 컴퓨터 안에서 프로그램끼리 쪽지를 주고받는 우편함 같은 파일 |
| 커널 | 운영체제의 핵심. 모든 프로그램이 하드웨어를 쓸 때 거쳐 가는 "건물의 기초 공사" |

## 4. 격리 설정 1~7 하나하나 보기

설정 위치: `docker-compose.yml` 의 `sandbox:` 부분, `sandbox/Dockerfile`, `sandbox/runner.py`

```yaml
  sandbox:
    build: ./sandbox
    network_mode: "none"            # ①
    read_only: true                 # ②
    tmpfs:
      - /tmp:size=16m               # ③
    cap_drop: [ALL]                 # ④
    security_opt:
      - no-new-privileges:true      # ⑤
    mem_limit: 128m                 # ⑥
    pids_limit: 64                  # ⑥
    cpus: 0.5                       # ⑥
    volumes:
      - sandbox_ipc:/ipc            # ⑦ (우편함)
```

```dockerfile
# sandbox/Dockerfile
RUN useradd -m runner ...
USER runner                         # ⑧ 일반 사용자로 실행
```

| # | 코드 | 의미 | 무엇을 막나 (없으면 생기는 일) | 점검 결과 |
|---|---|---|---|---|
| ① | `network_mode: "none"` | 네트워크 장치를 아예 주지 않는다 | 실험실에서 금고(DB)·사무실(Flask)·인터넷으로 접속하는 것. 없으면 DB에 직접 접속하거나 데이터를 외부로 빼돌릴 수 있다 | 외부 접속 `Network is unreachable`, DB 주소 `db` 를 찾지도 못함 ✅ |
| ② | `read_only: true` | 컨테이너 파일·폴더를 읽기만 가능 | 악성 파일 설치, 실행 코드(runner.py) 변조. 없으면 다음 실습 사용자까지 영향을 주는 파일을 심을 수 있다 | `/sandbox/test` 쓰기 → `Read-only file system` ✅ |
| ③ | `tmpfs: /tmp:size=16m` | 임시 작업용으로 `/tmp` 만 16MB 쓰기 허용, 컨테이너 재시작 시 삭제 | 실습(파일 업로드 등)에 필요한 최소한의 쓰기만 허용하고, 용량을 제한해 디스크 가득 채우기 방지 | `/tmp` 쓰기 `tmp-ok` ✅ |
| ④ | `cap_drop: [ALL]` | 관리자 능력 조각을 전부 버린다 | 네트워크 설정 변경, 다른 사용자 행세, 시스템 설정 조작 | 실제 설정 `capdrop=[ALL]` ✅ |
| ⑤ | `no-new-privileges:true` | 실행 도중 권한을 더 얻는 것을 금지 | 일반 사용자에서 관리자로 "승진"하는 공격(setuid 프로그램 악용 등) | 실제 설정 `no-new-privileges:true` ✅ |
| ⑥ | `mem_limit` · `pids_limit` · `cpus` | 메모리 128MB, 프로세스 64개, CPU 0.5개까지만 사용 | 무한 반복·프로세스 무한 복제로 PC 전체를 느리게/멈추게 하는 것(서비스 거부) | `mem=128MB pids=64 cpu=0.5` ✅ |
| ⑦ | `volumes: sandbox_ipc:/ipc` | Flask 와 공유하는 유일한 통로(우편함 = 소켓 파일) | 네트워크 없이도 실행 요청·결과를 주고받게 함. 다른 통로는 없음 | 설정 확인 ✅ |
| ⑧ | `USER runner` | root 가 아닌 일반 사용자(uid 1000)로 실행 | 관리자 권한으로 할 수 있는 모든 일 | `uid=1000(runner)` ✅ |

추가로 `sandbox/runner.py` 는 명령 하나당 **실행 시간 · CPU 2초 · 파일 크기 1MB** 를 제한하고, SQL 실습은 MariaDB가 아니라 **매번 새로 만들었다 버리는 메모리 SQLite** 에서 실행한다. 그리고 sandbox 에는 DB 비밀번호가 들어 있는 `.env` 를 전달하지 않는다(점검 6: 비밀값 없음, `GPG_KEY` 는 Python 공식 이미지의 공개 서명키 지문이라 비밀이 아님).

### 4-1. 그래서 서버·DB에 피해가 안 가는 이유 (연결고리)

```
공격 성공 = sandbox 안에서 명령 실행 가능
   ├─ DB에 접속하려면?      → 네트워크 필요 → ① 없음 → 불가
   ├─ Flask를 공격하려면?    → 네트워크 필요 → ① 없음 → 불가 (우편함은 Flask가 먼저 보낸 쪽지에 답장만 함)
   ├─ 악성 파일을 남기려면?  → 쓰기 필요     → ② 읽기 전용 → 불가 (/tmp는 재시작 시 삭제)
   ├─ 관리자가 되려면?       → 권한 필요     → ④⑤⑧ 제거·금지 → 불가
   └─ PC를 마비시키려면?     → 자원 필요     → ⑥ 제한 → 불가
```

## 5. 왜 격리 점검을 했나

1. **설정이 "적혀 있는 것"과 "실제로 적용된 것"은 다를 수 있다.** 오타, 다른 설정 파일(override)의 덮어쓰기, 오래된 컨테이너 등으로 설정이 빠질 수 있다. 그래서 실제 컨테이너에서 직접 시험했다.
2. **SecuQuest는 일부러 공격이 성공하게 만든 플랫폼**이다. 격리가 깨지면 학습용 공격이 진짜 사고가 된다. 가장 중요한 안전장치라서 확인이 필요하다.
3. **발표·설명 근거**가 된다. "안전합니다" 대신 "이 7가지를 직접 시험했고 결과가 이렇다"고 보여줄 수 있다.

## 6. 격리가 막지 못하는 것 (남은 위험)과 다른 보안 장치

### 6-1. 제한 대상 구분

| 구성 | 네트워크 | 파일 쓰기 | 상태 |
|---|---|---|---|
| Nginx · Flask · MariaDB · Redis | 정상 | 정상 | 로그인·진도·보상 등 서비스는 평소대로 동작 |
| **sandbox** | 없음 | `/tmp` 만 | 공격 실습 실행 전용 |

### 6-2. 커널 공유 (남은 위험 1)

- **커널**은 운영체제의 핵심, 건물로 치면 **기초 공사(땅과 기둥)** 다.
- 컨테이너는 방을 벽으로 나눈 것이지, 건물을 따로 지은 것이 아니다. **모든 방이 같은 기초 공사(커널) 위에 서 있다.**
- 그래서 만약 기초 공사 자체에 금(커널 취약점)이 있으면, 이론상 실험실 바닥을 뚫고 다른 방으로 갈 수 있다. 이것을 "컨테이너 탈출"이라고 부른다.
- SecuQuest는 ④⑤⑧(권한 제거·승진 금지·일반 사용자)로 이런 시도를 매우 어렵게 만들었다. 하지만 가능성이 0은 아니므로 **Docker와 운영체제를 최신으로 업데이트**하는 것이 중요하다.

### 6-3. iframe 격리 (XSS 실습 보호)

- XSS 실습은 sandbox가 아니라 **학생 브라우저**에서 스크립트가 실행된다.
- **iframe** 은 웹 페이지 안에 다른 웹 페이지를 끼워 넣는 "액자"다.
- SecuQuest는 취약한 실습 페이지를 `<iframe sandbox="allow-scripts">` 액자 안에서 보여준다. `sandbox` 속성이 붙은 액자는 **다른 출처(origin)로 취급**되어, 그 안의 스크립트가 SecuQuest 로그인 세션·쿠키를 읽거나 SecuQuest 로 요청을 보낼 수 없다.
- 비유: 유리 상자 안에서 폭죽을 터뜨리는 것. 불꽃은 보이지만 상자 밖 물건은 타지 않는다.
- (관련 파일: `frontend/src/components/practice/XssPractice.vue`)

### 6-4. 서비스 자체를 지키는 표준 보안

sandbox 격리는 "실습 공격"만 가둔다. 로그인·관리자·보상 같은 일반 기능은 아래 장치로 지킨다.

| 장치 | 쉬운 뜻 | SecuQuest 적용 위치 |
|---|---|---|
| **CSRF 토큰** | 중요한 요청(POST 등)에 "우리 화면에서만 발급한 일회용 번호표"를 함께 보내게 해서, 다른 사이트가 몰래 보낸 요청을 거절 | `backend/app/__init__.py` `CSRFProtect()` |
| **Rate Limit (요청 횟수 제한)** | 같은 사람이 짧은 시간에 너무 많이 요청하면 잠시 막음. 비밀번호 무작위 대입·반복 추론 공격 방지 | `Limiter(...)`, 각 API 의 `@limiter.limit("10 per minute")` 등 |
| **bcrypt** | 비밀번호를 원래 글자로 되돌릴 수 없는 "해시"로 바꿔 저장. 일부러 계산을 느리게 만들어 대량 추측을 어렵게 함. DB가 유출돼도 비밀번호 원문은 알 수 없음 | `backend/app/auth.py` `bcrypt.hashpw` / `bcrypt.checkpw` |
| **세션 쿠키 속성** | `HttpOnly`: 스크립트가 쿠키를 못 읽음 / `SameSite=Lax`: 다른 사이트 요청에 쿠키 자동 첨부 제한 | `backend/config.py` |

## 7. 핵심 정리

- 막은 것은 **sandbox 하나**다. Flask·MariaDB 등 서비스는 평소대로 통신한다.
- sandbox는 공격 실습이 "진짜로 성공"하는 방이라서, 네트워크(①)·쓰기(②③)·권한(④⑤⑧)·자원(⑥)을 막아 **성공해도 밖으로 나갈 길이 없게** 했다. 통로는 Flask와의 우편함(⑦) 하나뿐이다.
- 격리 점검은 이 설정이 **실제로 적용되어 있는지** 직접 시험한 것이고, 7개 항목 모두 통과했다.
- 남은 위험: 커널 공유(업데이트로 대비). XSS 실습은 iframe 격리로, 서비스 기능은 CSRF 토큰·Rate Limit·bcrypt·쿠키 속성으로 따로 보호한다.
- 발표용 한 문장: **"공격 실습은 통로가 막힌 격리 컨테이너에서만 실행되므로 성공해도 서비스 서버와 회원 DB에 닿지 못하고, 서비스 자체는 CSRF 토큰·요청 제한·bcrypt 등 표준 보안으로 따로 지킨다."**
