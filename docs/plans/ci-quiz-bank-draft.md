## 1. 기본 개념

**Q1.** Command Injection의 정의로 가장 정확한 것은?
1) SQL 쿼리에 악성 구문을 삽입하는 공격
2) 사용자 입력이 검증 없이 OS 셸 명령의 일부로 실행되는 취약점
3) 브라우저에서 악성 스크립트가 실행되는 취약점
4) 세션 토큰을 탈취해 인증을 우회하는 공격
정답: 2 / 해설: Command Injection은 애플리케이션이 사용자 입력을 셸 명령 문자열에 그대로 결합해 실행할 때 발생하는 서버 측 취약점이다.

**Q2.** Command Injection이 발생하기 위한 핵심 전제 조건은?
1) 서버가 HTTPS를 사용하지 않는다
2) 클라이언트가 쿠키를 저장한다
3) 서버가 사용자 입력을 셸에 전달해 실행한다
4) 데이터베이스가 원격 서버에 있다
정답: 3 / 해설: 입력값이 셸(또는 동등한 명령 해석기)로 전달되어 해석·실행될 때만 성립한다.

**Q3.** 다음 중 Command Injection과 가장 관련이 적은 것은?
1) ping 유틸리티를 감싼 웹 기능
2) 파일 압축 도구를 호출하는 백엔드 기능
3) 정적 이미지 파일을 그대로 반환하는 기능
4) 로그 검색어를 grep에 전달하는 기능
정답: 3 / 해설: 정적 파일을 그대로 반환하는 기능은 셸 명령 실행을 거치지 않으므로 무관하다.

**Q4.** Command Injection의 피해 범위로 가장 적절한 설명은?
1) 클라이언트 브라우저의 쿠키만 노출된다
2) 서버 프로세스 권한 범위 내에서 임의 명령 실행이 가능해질 수 있다
3) 데이터베이스 테이블 구조만 유출된다
4) 네트워크 트래픽 도청만 가능하다
정답: 2 / 해설: 주입된 명령은 애플리케이션 서버 프로세스 권한으로 실행되므로 그 범위 내에서 피해가 발생한다.

**Q5.** Command Injection과 OS Command Injection은 어떤 관계인가?
1) 서로 무관한 별개의 취약점이다
2) 사실상 같은 취약점을 가리키는 동의어에 가깝다
3) OS Command Injection은 클라이언트 취약점이다
4) Command Injection은 항상 원격 코드 실행과 무관하다
정답: 2 / 해설: 두 용어는 거의 같은 의미로, 운영체제 셸 명령을 주입·실행시키는 취약점을 가리킨다.

## 2. 셸 메타문자

**Q6.** 명령을 순차적으로 이어 실행시키는 셸 메타문자는?
1) `#`  2) `%`  3) `;`  4) `@`
정답: 3 / 해설: 세미콜론은 앞 명령의 성공 여부와 무관하게 다음 명령을 순차 실행시킨다.

**Q7.** `&&`가 뒤의 명령을 실행시키는 조건은?
1) 앞 명령이 실패해도 무조건 실행  2) 앞 명령이 성공(종료코드 0)했을 때만 실행  3) 두 명령을 병렬 실행  4) 사용자가 별도 Enter를 눌렀을 때
정답: 2 / 해설: `&&`는 앞 명령이 성공적으로 끝났을 때만 뒤 명령을 실행하는 조건부 연결 연산자다.

**Q8.** 파이프(`|`)의 역할로 옳은 것은?
1) 두 명령을 병렬 백그라운드 실행  2) 명령 결과를 파일로 저장  3) 주석 처리  4) 앞 명령의 표준 출력을 뒤 명령의 표준 입력으로 전달
정답: 4 / 해설: 파이프는 프로세스 간 출력-입력을 연결해 앞 명령 결과를 뒤 명령이 이어받게 한다.

**Q9.** 백틱(`` ` ``)이나 `$()`의 공통 기능은?
1) 변수 삭제  2) 파일 권한 변경  3) 명령 치환 — 안의 명령 실행 결과로 치환  4) 네트워크 소켓 열기
정답: 3 / 해설: 둘 다 괄호/백틱 안의 명령을 먼저 실행하고 그 출력으로 치환하는 명령 치환 문법이다.

**Q10.** 다음 중 명령 구분자로 쓰일 수 있는 문자가 아닌 것은?
1) `;`  2) `&&`  3) `|`  4) `_`
정답: 4 / 해설: 언더스코어는 일반적으로 식별자에 쓰이는 문자로 셸 명령 구분자가 아니다.

## 3. 블랙리스트 vs 화이트리스트

**Q11.** 블랙리스트 기반 필터링의 근본적 한계는?
1) 성능이 너무 느리다  2) 알려진 패턴만 차단해 새로운 우회 패턴에 뚫릴 수 있다  3) 항상 정규식을 써야 한다  4) 클라이언트에서만 동작한다
정답: 2 / 해설: 블랙리스트는 이미 아는 위험 패턴만 막기 때문에 목록에 없는 신규·변형 패턴에 무력하다.

**Q12.** `;`, `&&`만 차단하고 `|`는 차단하지 않았을 때 발생할 수 있는 문제는?
1) 아무 문제 없다  2) 파이프로 여전히 명령을 이어붙일 수 있다  3) 오히려 보안이 강화된다  4) 성능이 개선된다
정답: 2 / 해설: 차단 목록에 없는 구분자(`|`)로 여전히 임의 명령을 추가 실행할 수 있다.

**Q13.** 화이트리스트 검증 방식의 특징은?
1) 금지어 목록을 계속 추가해야 한다  2) 우회 가능성이 블랙리스트보다 항상 높다  3) 허용할 값의 패턴만 명시하고 그 외는 전부 거부한다  4) 입력 길이 제한과 무관하다
정답: 3 / 해설: 허용 가능한 형태만 통과시키고 나머지는 모두 거부해 훨씬 견고하다.

**Q14.** `^[A-Za-z0-9._-]+$`로 검증한 뒤 셸 없이 인자 배열로 실행한다면?
1) 여전히 셸 메타문자 우회가 가능하다  2) 셸 해석 자체가 없어 안전도가 높다  3) 화이트리스트가 무의미해진다  4) 성능이 크게 저하된다
정답: 2 / 해설: 셸을 거치지 않고 인자 배열로 실행하면 특수문자가 있어도 명령 해석기가 개입하지 않아 이중 방어가 된다.

**Q15.** 블랙리스트에 개행문자(`\n`)를 추가하지 않았을 때 위험한 이유는?
1) 개행은 셸에서 항상 무시되기 때문  2) 개행은 HTML 인코딩되므로 안전하다  3) 개행은 DB에서만 의미가 있다  4) 개행 뒤 문자열이 새 명령으로 해석될 수 있는 환경이 있기 때문
정답: 4 / 해설: 일부 실행 컨텍스트에서 개행이 명령 구분자 역할을 해 우회 경로가 된다.

## 4. 안전한 API/인자 배열

**Q16.** 셸 실행 대신 권장되는 방식은?
1) 문자열 결합 후 `system()` 호출  2) 언어 내장 API에 인자를 배열로 전달해 셸을 거치지 않고 실행  3) 더 긴 블랙리스트 작성  4) 입력값을 두 번 이스케이프
정답: 2 / 해설: 인자 배열 전달은 셸 해석 단계 자체를 없애 메타문자 주입을 원천 차단한다.

**Q17.** Python에서 `subprocess.run(cmd, shell=True)` 대신 권장되는 형태는?
1) `os.system(cmd)`  2) `eval(cmd)`  3) `subprocess.run(["cmd", arg1, arg2])` (shell=False)  4) shell=True를 유지하되 따옴표만 추가
정답: 3 / 해설: `shell=False` + 인자 리스트는 셸을 거치지 않아 메타문자가 그대로 인자 값으로만 취급된다.

**Q18.** Node.js에서 `child_process.exec()` 대신 권장되는 함수는?
1) `execSync()`를 문자열로 그대로 사용  2) `execFile()` 또는 `spawn()`에 인자 배열 전달  3) `eval()`  4) `Function()` 생성자
정답: 2 / 해설: `execFile`/`spawn`은 셸을 거치지 않고 프로세스를 직접 실행한다.

**Q19.** Java에서 셸 명령 실행 시 안전한 방식은?
1) `Runtime.exec(String command)`에 문자열 직접 결합  2) `ProcessBuilder`에 인자를 리스트로 전달  3) `Runtime.exec()`에 블랙리스트만 적용  4) 항상 관리자 권한으로 실행
정답: 2 / 해설: `ProcessBuilder`는 인자를 리스트로 분리 전달해 문자열 결합 위험을 줄인다.

**Q20.** 인자 배열 전달만으로 완전히 안전하다고 보기 어려운 경우는?
1) 인자 개수가 5개를 넘는 경우  2) HTTPS 미사용 시  3) 세션 만료 시  4) 실행 대상 프로그램이 내부적으로 입력을 다시 셸에 넘기는 경우
정답: 4 / 해설: 호출된 프로그램이 내부적으로 셸을 또 실행하면 인자 배열 전달만으로는 그 내부 주입까지 막지 못한다.

## 5. 언어별 안전한 함수

**Q21.** PHP에서 상대적으로 더 위험한 방식은?
1) 셸을 거치지 않는 내장 함수 대체 사용  2) 입력을 받지 않는 정적 스크립트  3) `escapeshellarg()`만 적용한 `shell_exec()`  4) `intval()`로 형변환된 값만 사용
정답: 3 / 해설: 이스케이프 함수는 보조 수단일 뿐 여전히 셸을 거쳐 우회 여지가 남는다.

**Q22.** Python `os.system()`의 문제점은?
1) 항상 셸을 통해 명령을 실행해 메타문자가 해석된다  2) 비동기 실행만 지원한다  3) 표준 출력을 가져올 수 없다  4) Windows에서만 동작한다
정답: 1 / 해설: `os.system()`은 내부적으로 셸을 호출하므로 사용자 입력이 섞이면 메타문자가 해석된다.

**Q23.** Go에서 외부 명령 실행 시 권장 패턴은?
1) `exec.Command(name, arg1, arg2, ...)` 인자 분리  2) 명령 전체를 문자열로 조립해 `sh -c`로 실행  3) 항상 goroutine으로 실행  4) 셸 스크립트 파일 생성
정답: 1 / 해설: 실행 파일명과 인자를 분리 전달하면 셸 해석 단계 없이 실행되어 안전하다.

**Q24.** Ruby에서 `system("ping " + user_input)`이 위험한 이유는?
1) Ruby는 외부 명령을 실행할 수 없음  2) `system` 호출은 항상 예외 발생  3) 성능 문제만 있을 뿐 보안과 무관  4) 문자열 결합으로 셸에 전달되어 메타문자가 해석될 수 있음
정답: 4 / 해설: 문자열을 그대로 셸 명령으로 넘기면 입력에 포함된 구분자가 해석될 수 있다.

**Q25.** 여러 언어에서 공통적으로 권장되는 근본 대책은?
1) 에러 메시지를 자세히 출력  2) 입력 길이를 무제한 허용  3) 셸을 거치지 않는 API + 화이트리스트 검증 병행  4) 클라이언트 자바스크립트 검증만 신뢰
정답: 3 / 해설: 언어와 무관하게 셸 해석 회피 + 화이트리스트 검증 병행이 핵심이다.

## 6. 우회 기법

**Q26.** URL 인코딩된 메타문자(`%3B` 등)가 위험할 수 있는 이유는?
1) 서버가 디코딩 후 셸에 전달하면 원래 메타문자로 복원되어 해석될 수 있음  2) URL 인코딩은 항상 무해하다  3) 브라우저에서만 디코딩된다  4) 인코딩된 값은 셸이 절대 처리 못함
정답: 1 / 해설: 디코딩 이후 필터링 없이 셸로 넘기면 인코딩은 방어가 되지 못한다.

**Q27.** 공백을 필터링했을 때 흔히 쓰이는 우회 방법은?
1) `${IFS}`나 탭 문자 등 공백 대체 문자 사용  2) 명령을 포기  3) 공백 대신 항상 줄바꿈 2개 사용  4) 공백 필터링은 우회 불가능
정답: 1 / 해설: `$IFS` 같은 셸 변수나 탭 문자로 공백을 대체해 필터를 우회하는 사례가 알려져 있다.

**Q28.** 특정 문자열(`cat`)만 블랙리스트로 막았을 때 우회 예시는?
1) 항상 우회 불가능  2) HTTPS 사용 시 우회 불가능  3) 인증 강화로 해결됨  4) `c''at`, `c\at` 등으로 분할해 필터를 피함
정답: 4 / 해설: 셸은 따옴표·이스케이프로 분할된 문자열도 이어 붙여 해석하므로 문자열 일치 필터는 쉽게 우회된다.

**Q29.** Time-based 방식으로 명령 실행 여부를 간접 확인하는 기법은?
1) 즉시 에러가 발생하므로 불필요  2) 클라이언트 캐시 확인  3) `sleep 5`처럼 지연 명령을 주입해 응답 시간 차이를 관찰  4) 쿠키 만료 시간 확인
정답: 3 / 해설: 결과가 화면에 안 보여도 지연 명령으로 응답 시간 차이를 관찰해 실행 성공을 추론할 수 있다(블라인드 기법).

**Q30.** 이미 필터링된 문자 대신 대체 표기를 쓰는 우회의 공통 원리는?
1) 필터는 정확히 일치하는 패턴만 잡고, 의미는 같지만 표기가 다른 입력은 통과시키는 경우가 많다  2) 모든 필터는 의미 기반이라 우회 불가능  3) 대체 표기는 셸이 인식 못해 무해하다  4) 우회는 항상 관리자 권한 필요
정답: 1 / 해설: 패턴 매칭 기반 필터는 표기상 변형에 취약하다는 것이 블랙리스트의 근본적 약점이다.

## 7. 방어 심화

**Q31.** 최소 권한 원칙을 Command Injection 방어에 적용한다면?
1) 프로세스를 관리자 권한으로 실행해 오류를 줄인다  2) 프로세스 권한을 필요한 최소 범위로 제한해 피해 범위를 줄인다  3) 모든 사용자를 관리자로 승격  4) 권한 설정은 성능과만 관련
정답: 2 / 해설: 주입이 성공해도 프로세스 권한이 제한적이면 공격 범위가 줄어든다.

**Q32.** 컨테이너 샌드박스(`network=none`, read-only rootfs 등)가 주는 효과는?
1) 입력 검증을 완전히 대체한다  2) 명령 주입 자체를 원천 불가능하게 만든다  3) 성능만 저하시킨다  4) 취약점 자체는 없애지 못하지만 성공 시 피해 확산을 제한한다
정답: 4 / 해설: 샌드박스는 심층 방어이며, 근본 원인(안전하지 않은 실행 방식)은 별도로 고쳐야 한다.

**Q33.** 실행 파일 화이트리스트(allow-list) 정책의 효과는?
1) 모든 프로그램을 자유롭게 실행하게 해준다  2) 입력 검증을 생략해도 되게 해준다  3) 지정된 실행 파일 외에는 실행되지 않도록 제한해 임의 명령 실행 범위를 줄인다  4) 네트워크 대역폭을 늘려준다
정답: 3 / 해설: 실행 가능한 바이너리를 제한하면 주입이 발생해도 임의 프로그램 실행으로 이어지기 어렵다.

**Q34.** 타임아웃·리소스 제한(CPU/메모리)을 두는 이유는?
1) 명령 주입 성공 시 무한 루프·자원 고갈형 후속 공격의 피해를 제한하기 위해  2) 응답 속도를 항상 빠르게 보이기 위해서만  3) 입력 검증을 생략해도 되게 하기 위해  4) 로그 용량을 줄이기 위해서만
정답: 1 / 해설: 자원 제한은 주입된 명령이 실행돼도 서비스 전체 영향을 제한하는 심층 방어다.

**Q35.** WAF만으로 Command Injection을 완전히 막을 수 없는 이유는?
1) 패턴 기반 탐지라 새로운 우회 페이로드에 뚫릴 수 있어 근본 대책이 아니다  2) WAF는 항상 모든 공격을 100% 차단한다  3) WAF는 SQL Injection에만 적용된다  4) WAF는 서버 코드를 자동 수정해준다
정답: 1 / 해설: WAF는 보조 수단이며, 근본적으로는 애플리케이션 코드 수준의 안전한 실행 방식이 필요하다.

## 8. 탐지/로깅

**Q36.** Command Injection 탐지에 유용한 로그 항목은?
1) 사용자의 화면 해상도  2) 브라우저 폰트 목록  3) CSS 파일 요청 여부  4) 실행된 외부 명령의 인자 전체와 호출 근거(요청 파라미터 등)
정답: 4 / 해설: 실제로 셸에 전달된 명령과 근거 입력을 로깅해야 이상 패턴을 추적할 수 있다.

**Q37.** 로그에 사용자 입력을 그대로 기록할 때 주의할 점은?
1) 로그는 항상 안전해 별도 처리 불필요  2) 로그에는 절대 사용자 입력을 남기면 안 된다  3) 로그 인젝션으로 포맷이 깨지거나 위조될 수 있어 개행 등도 이스케이프해야 한다  4) 로그 저장소는 암호화가 불필요하다
정답: 3 / 해설: 사용자 입력을 그대로 남기면 개행으로 가짜 로그 라인을 삽입하는 로그 인젝션이 가능하다.

**Q38.** 비정상적으로 짧은 시간에 반복되는 실행 요청을 제한하는 목적은?
1) 자동화된 블라인드 스캐닝·무차별 시도를 늦추기 위해  2) 서버 비용을 아끼기 위해서만  3) 사용자 경험 향상만을 위해  4) 로그인 실패와는 무관하다
정답: 1 / 해설: Rate limiting은 자동화 도구의 대량 시도를 어렵게 만들어 탐지·차단 시간을 벌어준다.

**Q39.** 실행 결과(stdout/stderr)를 그대로 노출하는 디버깅 페이지의 위험은?
1) 공격자가 실행 성공 여부와 시스템 정보를 즉시 확인해 공격을 가속화한다  2) 아무 위험이 없다  3) 오히려 보안에 도움이 된다  4) 성능에만 영향을 준다
정답: 1 / 해설: 결과를 그대로 노출하면 공격자가 피드백을 즉시 받아 페이로드를 빠르게 교정할 수 있다.

**Q40.** 이상 탐지 시스템이 주시해야 할 대표적 신호는?
1) CSS 파일 로드 빈도  2) 로그인 페이지 방문 횟수만  3) 이미지 파일 크기  4) 평소와 다른 프로세스(`/bin/sh`, `cat`, `wget` 등)가 애플리케이션의 자식으로 실행되는 패턴
정답: 4 / 해설: 애플리케이션이 평소 실행하지 않는 셸·유틸리티 프로세스가 자식으로 뜨는 것은 강한 신호다.

## 9. 실전 시나리오

**Q41.** ping 결과를 보여주는 기능의 IP 입력란에 `8.8.8.8; whoami`를 넣었더니 계정명이 출력됐다. 이 상황이 의미하는 것은?
1) DNS 캐시 문제  2) 네트워크 지연 문제  3) 입력값이 필터링 없이 셸 명령에 결합되어 실행됨  4) 브라우저 확장 프로그램 문제
정답: 3 / 해설: 세미콜론 뒤 명령까지 실행돼 결과가 노출됐다는 것은 입력이 검증 없이 셸에 전달됐다는 뜻이다.

**Q42.** 압축 파일명을 사용자가 입력하고 서버가 `zip {입력값}.zip ./data`를 실행한다면 가장 먼저 점검할 것은?
1) 입력값이 셸에 그대로 전달되는지, 파일명에 메타문자가 허용되는지  2) 압축 알고리즘의 압축률  3) 사용자의 화면 해상도  4) 서버 디스크 색상
정답: 1 / 해설: 파일명이라는 이유로 검증을 소홀히 하기 쉬운 흔한 발생 지점이다.

**Q43.** 로그 검색 기능에서 `; cat /etc/passwd`가 통했다면 가장 근본적인 수정 방향은?
1) 검색어를 grep 등에 셸로 넘기지 않고 언어 내장 검색이나 인자 배열 호출로 대체  2) 에러 메시지만 숨긴다  3) 해당 파일만 별도 암호화한다  4) 검색 기능 자체를 없앤다
정답: 1 / 해설: 근본 해결은 실행 방식을 안전하게 바꾸는 것이다.

**Q44.** 특수문자를 셸에 그대로 넘기되 블랙리스트만 강화했다면?
1) 완전히 안전해진다  2) 성능만 관련 있을 뿐 보안과 무관  3) 화이트리스트보다 항상 더 안전하다  4) 여전히 새로운 우회 패턴에 뚫릴 여지가 있다
정답: 4 / 해설: 블랙리스트를 아무리 강화해도 셸을 거치는 한 신종 우회 가능성이 남는다.

**Q45.** `Impossible` 티어가 화이트리스트 검증 후 인자 배열로 직접 실행하는 이유는?
1) 단순히 난이도를 올리기 위한 장식  2) 서버 성능을 낮추기 위해  3) 입력 형태를 제한하고 셸 해석 단계를 제거해 두 겹으로 방어하기 위해  4) 사용자 편의를 위해
정답: 3 / 해설: 화이트리스트 + 인자 배열 실행 조합이 실무 권장 근본 대책의 예시다.

## 10. 종합/복합 방어

**Q46.** Command Injection에 대한 "근본적" 대책에 가장 가까운 조합은?
1) 셸 비경유 실행 방식 + 입력 화이트리스트 검증  2) 블랙리스트 강화 + 에러 메시지 숨김  3) HTTPS + 쿠키 SameSite  4) 세션 타임아웃 단축 + CAPTCHA
정답: 1 / 해설: HTTPS·SameSite 쿠키나 세션 타임아웃·CAPTCHA는 각각 다른 취약점(도청, CSRF·세션 하이재킹) 대응이며, 블랙리스트 강화는 우회 가능한 임시방편이다.

**Q47.** "근본 대책"과 "심층 방어(보조)"를 나눌 때 심층 방어에 해당하는 것은?
1) 셸 미경유 실행 방식 채택  2) 최소 권한 실행, 샌드박스 격리, 리소스 제한  3) 인자 배열 전달  4) 화이트리스트 입력 검증
정답: 2 / 해설: 최소 권한 실행·샌드박스 격리·리소스 제한은 주입 성공 시 피해를 줄이는 보조 계층이고, 셸 미경유 실행·인자 배열 전달·화이트리스트 검증은 주입 자체를 막는 근본 대책이다.

**Q48.** 다음 중 Command Injection 방어와 가장 관련이 없는 조치는?
1) 인자 배열 전달  2) 화이트리스트 입력 검증  3) 셸 비경유 실행 API 사용  4) Prepared Statement 적용
정답: 4 / 해설: Prepared Statement는 SQL Injection 방어책으로 Command Injection과 직접 관련이 없다.

**Q49.** 실습 플랫폼처럼 실제로 명령을 실행시켜 학습하는 환경에서 안전성을 확보하는 조합으로 가장 적절한 것은?
1) 네트워크 차단·읽기 전용 루트 파일시스템·비루트 사용자·자원 제한을 갖춘 격리 컨테이너에서 실행  2) 격리 없이 운영 서버에서 바로 실행  3) 클라이언트 브라우저에서만 실행  4) 결과를 검증 없이 그대로 DB에 저장
정답: 1 / 해설: 실제 실행이 필요한 학습 환경에서는 프로세스·파일시스템·네트워크 격리 샌드박스가 필수다.

**Q50.** Command Injection 방어 설계에서 가장 우선순위가 높은 원칙은?
1) 블랙리스트를 최대한 길게 만든다  2) 클라이언트 검증만으로 충분하다  3) 에러 메시지를 자세히 보여줘 디버깅을 돕는다  4) 가능하면 셸 해석 단계 자체를 없애고, 불가피할 때만 엄격한 화이트리스트 검증을 추가한다
정답: 4 / 해설: 셸 비경유가 최우선이며, 부득이하게 셸을 써야 한다면 강한 화이트리스트 검증을 병행해야 한다.
